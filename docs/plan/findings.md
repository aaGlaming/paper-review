# 裁决

实现偏离三份依据文档时，把裁决写在这里。格式：`Ruling: 决定 — 原因 — 做错的代价`。

## 2026-10-20 P16 日志埋点：用 ContextVar 传 review_id

- Ruling: **`review_id` 通过 `ContextVar` 绑定、由 `log_event` 自动回填，而不是给每个埋点加形参** — 原因：`llm/client.py` 是最底层 HTTP 客户端，它的调用链上根本没有评审上下文，加形参要把 `review_id` 一路透传进 `chat` / `embed` / `rerank` 的签名，污染首期已验收的接口；`scoring.selection.apply_mention_guard` 虽已加形参，但三处调用方都没传，落库是 `null`。用 `ContextVar` 在 `create_review` / `resume_review` 入口绑一次，所有模块（含拿不到参数的最底层）都能被串进同一次预审，且显式传值优先、不覆盖 — 做错的代价：实测未做时 `llm` 日志 2244 条**零条**带 `review_id`、`scoring` 仅 67/1183，「用一条 review_id 串起一次预审全过程」这条 P16 判据直接不成立，而日志本身看起来完全正常，不逐模块统计根本发现不了。
- Ruling: **日志滚动测试的样本量按沙箱删除阈值下调，断言不动** — 原因：`_roll()` 每次滚动都 `unlink` 备份文件，原用例 80 条记录产生 40 次以上滚动，本机沙箱的批量删除保护在累计 50 次后直接终止进程（`[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED]`），表现为「单独跑通过、全量跑崩溃」 — 做错的代价：若靠猜，容易误判成 handler 有并发缺陷而去改产品代码；实际产品逻辑没问题，改的是测试样本量，且必须保留「备份数 ≤ 6」「出现 `.1`」两条断言，否则等于把用例测废。

## 2026-10-19 真实数据暴露的两个缺陷（第二期验收）

- Ruling: **向量检索的过滤条件必须包含 `review_id`，缺一不可；这条优先级高于重排与截断优化** — 原因：原先 `_where` 只按 `contest_id` / `rubric_id` / `section_type` / `doc_type` 过滤，而同一赛题下多篇论文共用一个 Chroma collection，于是 B 论文会召回 A 论文的父块。更隐蔽的是 `quote_is_substring` 校验**会通过**——它校验的父块本身就是别人的论文，于是「引用必须逐字取自父块」这条铁律被合法绕过，实测 50 维里有 26 维引用指向别的论文 — 做错的代价：报告里的引用无法回到被审论文，评审结论失去可复核性；这类缺陷在单篇样例下永远暴露不出来，231 条测试也拦不住（测试各自只跑一篇论文）。
- Ruling: **工具 schema 的 `band` 必须用 `Literal` 生成 enum，不接受 `str + description`** — 原因：`_force_submit` 的临时工具原本是空壳 `{"items": {"type": "array"}}`，`band` 无任何约束，模型于是自创 `high` / `medium`，被 `param_invalid` 逐条挡下，补交 0 条，轨迹以 `no_progress` 收尾，五维全「证据不足」。探针实测 5 条提交的 quote 全是论文原句、校验全过，唯一失败点就是档位取值 — 做错的代价：证据齐备却判不出档位，且现象与「模型偷懒不提交」几乎一样，排查方向会被完全带偏。
- Ruling: **改 `retrieve/parent_child.py` 或向量库结构后必须重启后端进程** — 原因：`_CLIENT` 是模块级单例，进程会一直持有删除前的 collection 句柄；实测删库后不重启，表现为「五维全证据不足 + 轨迹 0 行」，极易误判成检索逻辑坏了 — 做错的代价：多花半小时排查一个根本不存在的逻辑缺陷。

## 2026-10-19 文档编码纪律（四轮血案 · 已定位根因）

- Ruling: **写中文 markdown 一律用编辑器的文件写入能力（Write / Edit）或 Python `open(..., encoding="utf-8")`；禁止用 heredoc、`python - <<PY`、PowerShell here-string、`echo` 重定向直接传中文；每次写完必须跑 `python scripts/check_docs_encoding.py docs`，退出码 0 才算写完** — 原因：根因已定位。从 stdin 把含中文的脚本喂给 Python 时，Python 用 Windows 本地代码页（cp936）解码这段字节流，UTF-8 的中文被当成 GBK 读进内存，再以 UTF-8 落盘，于是产生双重编码；连续中文按 2 字节分组必然错位，行尾全角标点剩 1 字节无法配对，就被替换成 `?` 丢掉了。用 Write/Edit 直接写文件不经过 stdin，因此从不出错 —— 同一天里 `findings.md` 中由 Write 写的章节完好，由 heredoc 写的章节全坏，这就是对照实验 — 做错的代价：2026-10-19 一天内坏四次：① 整段 GBK；② UTF-8 被按 GB18030 解码回去（双重编码）；③ 中文全变成 `?`（216 处）；④ v2.2.1 执行记录 661 处 `?`。数字都在、过程全丢，一手记录只能降级成二手转述。
- Ruling: 编码事故的修复顺序固定为「**先 `git show HEAD:<path>` 取干净历史，再只重写增量段落**」，禁止对整份文件做 encode/decode 猜测 — 原因：双重编码是有损的，逐行还原的实测通过率只有 840/1688 行，且还原结果会混入 U+FFFD，比原样更难看懂；而 git 里的历史版本是干净的（实测乱码 0 处），可直接作底 — 做错的代价：我曾对已修好的行再做一次还原，把正确内容反向改坏，一层层套娃，最后只能整段重写。
- Ruling: 现有自检脚本 `check_docs_encoding.py` 判四类问题（非法 UTF-8 / U+FFFD / 双重编码乱码字 / 问号密集行），代码块内与正文里的合法 `?` 已排除 — 原因：只验「能否按 UTF-8 解码」是不够的，中文被替换成 `?` 后文件依然是合法 UTF-8，v2.2.1 的自检就栽在这里，它给出了 `utf8-ok`，而正文 661 个中文早已丢失 — 做错的代价：自检给绿灯、内容却已损坏，比没有自检更危险。

## 2026-10-19 v2.2.0

- Ruling: `critique` 做成 runner 的**后处理**而不是新增图节点 — 原因：冻结测试锁死 `next` / `score_node_calls` / `status` 三条，图结构不能加节点；五维结果与各维父块本来就在 runner 手里，做成节点还得先塞进 state 再取出来，多绕一圈。轨迹照样记 `node="critique"` — 做错的代价：若为它改图，`test_interrupt.py` 当场红，且检查点快照语义要重验。
- Ruling: critique **只降一档、不得提档、跳级直接拒、单篇配额 2 次** — 原因：让模型评审自己，它天然倾向给高分；只给「降」的权限是唯一能防住这种偏移的结构。允许跳级则一次就能从「充分」压到「不足」，绕过中间档的证据要求 — 做错的代价：无依据的降档比不降更糟，报告看起来更严格，实际是在编造依据。
- Ruling: 降档必须给 `chunk_id` + `quote`，且 quote 要过 `quote_is_substring`、chunk 要属于该维 — 原因：降档也是结论，同样要能回溯到原句 — 做错的代价：放宽这一条，引用可回溯这条卖点就只对「提交」生效、对「否定」失效。
- Ruling: critique 抛异常记 `ok=false` 后按原结果继续，不中断评审 — 原因：自检是增强，不是主链路 — 做错的代价：若让它中断，一次模型抖动就把整单打成失败。

## 2026-10-19 v2.1.2

- Ruling: 收工协议把「调用 `submit_dimension` 才算完成」写成硬约束 — 原因：上一轮 21 行轨迹里没有一条交付调用，模型把检索过程当成完成；协议要求缺维先交证据不足，再结束 — 做错的代价：不写这条，模型会把预算耗在重复回读上，五维最后由 runner 统一收口成「证据不足」，看起来像评完了，其实一条结论都没提交。
- Ruling: runner 增加收尾 `force_submit`，补交结果仍过 `band` 与 `quote_is_substring` 校验 — 原因：收工协议只能提高概率，不能保证；补提交是兜底，但兜底也必须过同一道校验口 — 做错的代价：若补交跳过校验，等于开后门写结论，唯一写口就名存实亡。
- Ruling: 默认 `max_model_calls` 由 8 改为 12 — 原因：五维各需一轮检索加一次提交，8 次必然不够，是「预算不够」伪装成「模型不配合」 — 做错的代价：预算给太少会让诊断走偏，把机制问题误判成 prompt 问题。

## 2026-10-19 v2.1.1

- Ruling: 无进展检测**只统计 `search_evidence` 与 `submit_dimension`** — 原因：这两类调用分别代表「新增证据」和「提交结论」；其余工具（`list_dimensions`、`get_constraints`、`read_parent`、`check_consistency`）不会改变证据或提交状态，计入会误杀合法的回读重试 — 做错的代价：统计口径放宽，正常的多读几次就被判「无进展」提前终止。
- Ruling: 响应新增 `agent_terminated_by` 字段，不改任何旧字段 — 原因：面板需要说明「为什么停」，但旧响应结构有前端与测试依赖 — 做错的代价：直接改旧字段会让既有断言与前端类型同时失效。
- Ruling: 前端轨迹面板区分四态——有数据 / 空 / 请求失败 / 带停止原因，**请求失败不许显示成空态** — 原因：把接口错误显示成「没有轨迹」，会让人误判 agent 没跑 — 做错的代价：故障被伪装成正常，排查时先怀疑业务逻辑，浪费一轮。

## 2026-10-19 v2.1.0：Agent 子图装配

- Ruling: agent 挂在既有 `score` 节点内部，不改主图结构 — 原因：`test_interrupt.py` 断言 `score_node_calls == 1`、`status == "完成"`、`next == ()`，独立新增 agent 节点会改变 resume 快照与这些断言，而该文件冻结 — 做错的代价：为「图更漂亮」去改冻结断言，等于拆掉首期唯一的防回归网。
- Ruling: agent 模式下 `retrieve` 短路，检索只由工具执行 — 原因：否则同一篇论文检索两遍，embed / rerank 成本翻倍，P25 的 3 分钟时限更紧张 — 做错的代价：重复检索不会报错，只会让账单和耗时悄悄变差。
- Ruling: 缺维直接补为「证据不足」并记 `reason=agent 未提交`，不让模型自动重跑 — 原因：预算闸必须是硬上限，结果收口必须确定 — 做错的代价：自动重跑会让轮次与预算脱钩，同一篇论文两次运行结论不一致。
- Ruling: 子图**不单独传 checkpointer**，与主图共用一个实例，`thread_id` 仍是 `review_id` — 原因：独立 checkpointer 会让 resume 时按 `thread_id` 找不到父图快照 — 做错的代价：`GET /reviews/{id}` 直接 404，而且现象像「记录丢了」，不像「检查点分家」。

## 2026-10-19 v2.0.3：轨迹与线性旁路

- Ruling: 先旁路跑工具而不直接接评分 — 原因：验证工具注册、检索与约束读取在真实请求里可用，同时把失败隔离在轨迹层；旁路不写 `results`、`score`、`change_list`，评分仍由既有链路负责 — 做错的代价：P12 就换主链，一旦出问题分不清是工具错了还是模型错了，而且此时还没有预算与 critique，等于拆了安全网。
- Ruling: 轨迹只存 sha256 摘要、命中数量、错误码和耗时，不存论文原文或 quote — 原因：接口要能审计调用顺序，又不能把论文内容复制进数据库与只读响应 — 做错的代价：原文落库既是版权问题，也让「谁能看到论文」这条边界失效。
- Ruling: 无记录时接口返回 200 + 空数组，不返回 404 — 原因：面板会把 404 误读成「评审不存在」 — 做错的代价：真实故障与「没跑过」混为一谈。

## 2026-10-19 v2.0.2：工具注册表与参数校验

- Ruling: 拒绝同一维度的重复 `submit_dimension`，返回 `not_allowed` 且保留第一次结论 — 原因：模型可能在多轮工具调用中反复覆盖档位，后一次引用或守卫结果未必更可靠；用 `submitted` 做一次性写入闸门，能让结论可复核，并防止模型通过重复提交刷档 — 做错的代价：若允许覆盖，轨迹只看到最后状态，无法证明哪次证据支撑了最终档位。
- Ruling: 错误码封闭在 `param_invalid`、`not_found`、`not_allowed`、`quote_not_substring`、`budget_exceeded` 五项白名单 — 原因：agent 编排、重试和预算中间件需要稳定地按错误类别处理，任意工具私造错误码会让模型提示与轨迹统计分叉；本版只产生前四类，`budget_exceeded` 留给 v2.0.3 之后的预算层 — 做错的代价：若放开错误码，缺参、越权、引用失败和预算耗尽会混成不可预期的字符串协议。
- Ruling: 工具参数校验自己写，不直接把 pydantic 的 `ValidationError` 塞进 `ToolMessage` — 原因：那玩意的字段名与格式随版本变化，模型学不到该补哪个参数 — 做错的代价：模型只能看到一坨校验栈，重试仍然缺同一个参数。
- Ruling: `ToolContext` 全部依赖注入（dimensions / constraints / retrieve_fn / read_parent_fn / findings_fn） — 原因：工具自己连库，测试就退化成集成测试 — 做错的代价：MockTransport 那套全离线契约当场作废，测试需要 MySQL 与 Chroma 才能跑。

## 2026-10-19 v2.0.1：P0 定级与适配器

- Ruling: P0 定级为**环境配置问题**，保住 E2E 原断言不动 — 原因：清除键后 Playwright 重启进程仍有 8 条评审链路失败；上下文显示页面仍在「处理中」，TestClient 栈显示首次数据库访问通过 `load_dotenv(override=False)` 回填 `.env` 的模型与重排配置，随后触发真实重排网络请求并连接失败。把四个模型键和三个重排键设为**空白占位**后，TestClient 确认路由 200 / 0.027 秒，Playwright 43/43 通过 — 做错的代价：误改 5 秒断言会掩盖环境回填并削弱门禁；只删键不占位，dotenv 仍会再次启用模型分支。
- Ruling: 用 `DeepSeekChatModel(BaseChatModel)` 与 `PaperRetriever(BaseRetriever)` 作为 LangChain 接口适配器 — 原因：模型只委托 `client.chat_with_tools`，保留唯一 HTTP 出口、超时、重试与密钥保护；检索只包装 `retrieve_dimension` 的父块结果，保留四键过滤、三路召回、父子块回填、合并去重、一次重排与四段截断 — 做错的代价：改用 `ChatOpenAI` 会创建第二个网络出口；改用 `VectorStoreRetriever` 会丢掉现有检索语义与父子块回填。
- Ruling: `bind_tools` 返回副本（`model_copy`），不原地改实例字段 — 原因：同一实例被多个 agent 复用时，原地改会让工具串味，而且极难复现 — 做错的代价：偶发的工具错乱，查一天也定位不到。
- Ruling: `ToolMessage` 的 `tool_call_id` 必须原样带回 — 原因：丢了它，下一轮模型对不上调用与结果，会重复调同一个工具 — 做错的代价：预算在几步内被同样的调用烧完，看起来像「模型不会用工具」。

## 2026-10-19 v2.0.0：采用标准 tool calling

- Ruling: 采用 A 路线，让 `chat_with_tools` 发送 OpenAI 兼容的 `tools` / `tool_choice` — 原因：一次性探针针对 `.env` 配置的 `deepseek-flash` 返回 HTTP 200、`finish_reason=tool_calls`，首个调用名为 `echo`，证明服务端实际返回标准工具调用结构；走文本 JSON 协议会绕开已可用的原生协议，并增加提示词约定与文本抽取的不确定性 — 做错的代价：在未验证的前提下写 B 路线，等于给一个能用原生协议的端点加一层易碎胶水。
- Ruling: 探针**不进 pytest** — 原因：它依赖真实端点、真实网络和 `.env` 密钥，放进自动测试会产生外部副作用与不稳定，也违反全离线 `MockTransport` 契约 — 做错的代价：CI 必须联网，且密钥会进测试路径。
- Ruling: `chat()` 一行不改，新能力旁挂为 `chat_with_tools` — 原因：159 个测试锁着它的签名与 payload 断言 — 做错的代价：改签名会让首期基线当场作废，出问题也无法整段回滚。

## 2026-10-19 期次重排：Phase-2 改为 Agent 化

- Ruling: **Agent 用 LangChain 1.x 的 `langchain.agents.create_agent`，不自建 plan-act-observe 循环** — 原因：`AgentExecutor` 在 1.x 已删除（实测 `ImportError`），1.x 的官方入口就是 `create_agent`；以子图方式融合能保住 `interrupt`、检查点、`weighted_sum()` 与子串校验，整体替换会把这些丢掉 — 做错的代价：选错入口就写成一堆调不通的胶水代码；整体替换等于放弃首期最值钱的三条硬约束。
- Ruling: 模型与检索都做成 LangChain 适配器（`BaseChatModel` / `BaseRetriever`），**不用 `ChatOpenAI`、不用 `VectorStoreRetriever`** — 原因：`ChatOpenAI` 会绕开 `client.py`，丢掉统一超时/重试/密钥保护；现有检索是「四键过滤 + 三路召回 + 合并去重 + 一次重排 + 4 段截断」，Chroma 原生 retriever 表达不了三路与父子块回填 — 做错的代价：前者让项目出现第二个 HTTP 出口，后者让检索质量直接掉一档且无法解释。
- Ruling: `requirements.txt` **只补 `langchain==1.4.5` 与 `langchain-core==1.6.10` 两行，不重装不升级** — 原因：三个包在共享环境里已经装着（`pip list` 实测），清单却只写了 langgraph；`pip install` 很可能把 langgraph 1.2.15 一起升级，直接改掉 159 个测试的基线环境 — 做错的代价：换机器按清单装会 `import langchain` 失败；重装则可能一次性红掉一片测试且难以定位。

## 2026-10-20 v3.1.1 权限与归属三条裁决

### 决定：详情/评审读取用 404 而不是 403，列表才用 403

原因：403 等于告诉调用方「这个 id 存在，只是不给你看」，id 本身可被枚举；404 把「无权」与「不存在」合成同一个响应体（含 detail 逐字节相同，不带 id），调用方无法区分。列表接口不存在单体枚举问题，用 403 明确拒绝。做错的代价：学生可逐个试 user_id/review_id 探活全站用户与评审。

### 决定：无 token 读无主记录放行，登录用户读无主仍需权限

原因：首期链路与 E2E 全是无 token 创建、无 token 读取（既有 269 条测试含裸调断言），过渡态（v3.1.2 才翻强制鉴权）不能把旧链路判 404；但登录用户身份已知，放行等于给已认证身份开匿名口子，所以仍要 `review:read:all`。做错的代价：要么 3 条既有测试红（违反不可改测试纪律），要么登录学生可读全站遗留评审。

### 决定：`Request | None` 不能出现在 FastAPI 依赖签名里，request 注入用 keyword-only 裸类型

原因：`request: Request | None = None` 会被 FastAPI 当成 Pydantic 响应字段解析，应用启动即 collection 报 `Invalid args for response field`；而 `request: Request = Depends()` 会被当成 query 参数校验，请求全变 422。正确写法是 keyword-only 无默认值 `(*, ..., request: Request)`，FastAPI 按类型特殊注入。做错的代价：门卫一加上 request 就全接口 422，表面像权限逻辑错，实际是签名写法错。

论文片段必须以 review_id 隔离，防止同赛题其他论文的父块进入候选；`doc_type=review_record` 则按 contest_id 搜索，不绑定单篇 review_id，供教师跨提交查找。结果仍携带命中的 review_id 和维度码，可供下一版回答引用，不会把论文检索改成跨论文。

### 决定：维度写入 parent_id，不扩展 ParentBlock

采用 `rr-{review_id}-{dimension_code}` 同时作为 parent_id 与 chunk_id，从尾段解析维度码。这样复用已有 `ParentBlock`、`ChildChunk` 与检索函数，不给已被多个模块依赖的 `ParentBlock` 增加字段；代价是维度码格式需保持不含额外的尾部连字符语义。

### 决定：当前不按 user_id 过滤评审记录

现有教师权限范围是全部评审记录，本轮用 contest_id 做赛题隔离并不额外缩小可见范围。未来若引入班级级权限，应先给子块元数据增加可审计的范围字段，再调整检索过滤；本版不借用请求身份暗中裁剪教师结果。

## 2026-10-20 v3.3.5 P19 回答与聚合合并裁决

### 决定：回答链路与聚合摘要合成一版

v3.3.2 与 v3.3.3 都未执行；检索结果形状、`chat_fn`、引用校验与审计字段属于共用边界，分开实现会有两套校验口径。本版让回答和摘要都调用同一个 `validate_citations` 与一次重试函数；代价是版本范围更大，因此测试分两批、先验证问答再实现聚合。

### 决定：检索为空时不调用生成模型

没有可用评审片段时直接返回固定无命中文案，不请求模型，既节省一次推理，也避免模型在缺证据时编造内容。空检索仍按成功问答落 user 与 assistant 消息。

### 决定：模型失败不保留半轮消息

问答只有在模型成功并完成引用校验后，才在单一事务写入 user、assistant 并更新会话；两次失败时不落任何消息。否则历史会出现悬空 user 节点，重试又可能留下重复记录。

### 决定：引用双向校验分别处理编造与遗漏

输出中不属于检索集合的引用标记会被剔除并计入 `rejected`；检索到但没有引用的片段计入 `unused`。二者只形成审计提示，不让整次回答失败；摘要可用证据不足 3 条时如实追加固定提示，不代模型补引用。

### 决定：聚合数字只由 SQL 与 Python 产生

档位计数、冲突类型与证据缺口在 `analytics.py` 查询并由 Python 汇总，摘要模型只负责组织文字。模型自行计算可能不准且重复请求会不一致；代价是新增统计逻辑必须同步覆盖 SQLite 与 MySQL 可用的通用查询。

### 决定：档位的两种不足写法只在聚合口径归一

真实数据同时有「不足」18 条与「证据不足」76 条。本版以唯一常量 `INSUFFICIENT_BANDS` 兼容二者，不 UPDATE 历史值；数据清洗应另立任务，避免在问询功能中隐式改写评审结论。

### 门禁阻断：当前 Chroma 持久库触发原生崩溃

`get_collection().count()` 与既有 review indexing 测试的 `Collection.delete` 在 Windows 原生层退出 `-1073741819`；停止 8077 后单测仍复现。全量 pytest 因此中断。全量 E2E 为 24/24、含 502 与超时，且结束后 8077 不再监听；E2E 与 Chroma 崩溃的具体时间因果未完全定位。本轮未清库、未改冻结测试，真实问答和摘要取证保持未完成。

## 2026-10-21 v3.3.10 向量库「存在但读不了」与写权限裁决

### 0xC0000005 不是回填脚本的错，是库读不了

在**副本**目录上复现，不碰生产：`get_collection` 成功（0.3 s），但 `count()` 崩在 `chromadb/api/rust.py:397`、`get()` 崩在 `:440`、`query()` 崩在 `:582`，三条读路径全是 access violation；同机同版本在**空目录**新建 collection，count/add/get/query 全过。故绑定本身正常，坏的是这份 24519 条、`data_level0.bin` 107 MB 的索引。

`scripts/index_review_records.py:174` 是 `get_collection()`、`:175` 是 `before = collection.count()`，**在写入之前**。两次正式回填的 stdout 只有接管锁那一行，`collection_count_before` 从未打印，段文件 mtime 仍停在 10-20 18:52 —— 两次崩溃都发生在读 count 的一秒，**生产库实际未被写入，也没有被写坏**。这是目前唯一的好消息。

`scripts/rebuild_chroma_from_parents.py:26` 同样先调 `count()`，所以「删库重建」这条路在旧库上也被同一个崩溃点堵住：必须先改名旧目录、建空目录，再跑重建，让 count 读的是空库。

### 已排除的四个假设

64 位地址空间（解释器为 `AMD64`，`sys.maxsize=2**63-1`）；两套解释器混用 chromadb（系统 3.12 未装）；段文件缺失（sqlite 两条 segment 与磁盘目录一一对应）；后端并发占用（停服后仍崩）。剩下的高优先怀疑是「这份索引文件本身」与「chromadb 1.5.9 在该规模下的原生缺陷」，需用副本探针分流。

### 纪律冲突必须写白名单，不能写「除 X 外只读」

v3.3.9 的 P2 要求 `ALTER TABLE chat_message` 与历史 `seq` 回填，纪律 1 却写「只允许索引回填写入 Chroma 与 `paper_parent`，其它 SQL 一律只读」。执行方按前者做是违规、按后者做是没完成，只能停工发问——整版空转的成本由规则写法造成，不是执行方的问题。v3.3.10 起改为**穷举写白名单**（W1~W4 + `paper_parent` 的间接例外），白名单外仍是只读。

### 门禁通过率不度量生产库可用性

381 项后端测试用的是隔离小库，空库探针也全绿，两处都碰不到这份 107 MB 索引。**测试绿 ≠ 生产向量库可读**，这两件事以前被混为一谈；P19 定点问答因为走 MySQL 才没受影响，而 P12 的逐维检索若仍在用向量，会全维静默「证据不足」而不报错。

### 闸门必须自带可复制命令与原始输出（2026-10-21 第二次空转）

v3.3.10 首次执行止步 P0，理由是「MySQL 3306 未检测到 LISTENING」。同一时点复核实测相反：`netstat` 显示 `0.0.0.0:3306` 与 `[::]:3306` 均 LISTENING（pid 19672），`socket.create_connection` 对 `127.0.0.1` 与 `::1` 均 OPEN，`tasklist` 确认该 pid 是 `mysqld.exe`。**MySQL 从未停止，停版是误判。**

根子不在执行方：v3.3.10 的 P0 原文只写了「netstat 3306 LISTENING」这半句话，没给可复制命令、没要求原始输出。判据留在后者脑子里，于是「一条命令没输出」被读成「环境坏了」。修法三条：① 环境判据给三类命令（socket / 端口表 / 进程名），**至少两条互证**才允许下结论；② 环境类闸门改为**可自愈**（本机 `MySQL84` 是 `StartType=Manual`，`net start` 被拒时用 `mysqld --defaults-file`），只有自愈失败才停；③ 判红必须附命令、退出码、原始输出，只有结论的不算。

一类是能修的（服务没起），一类是不能硬走的（测试数对不上）。**两类混在同一个「不符即停」里，就会在能修的地方停下、在不能修的地方硬走。**

**裁决三：八条 E2E 红指定接收方。** 它们在 P19～P23 五版 progress 里都以"沿用"出现，从未被修也从未被交接。根因属 P25（超时可见）范围，但必须写进 P23 报告的移交清单并要求 P25 三选一（修 / 改等待策略 / 书面豁免）。**长期挂账的待办在报告里长得像结论。**
