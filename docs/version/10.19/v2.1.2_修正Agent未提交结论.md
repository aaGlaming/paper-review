P14 的 `critique` 只能把「充分 / 基本」降一档。现在五维**全是「证据不足」**，critique 一行都跑不到——写了也是空转。

## 1. 诊断（先做，别猜）

### 1.1 三种可能，轨迹能直接分辨

| 症状（看 `agent_step`） | 结论 | 对应修法 |
|---|---|---|
| 21 行里**没有** `action=submit_dimension` | 模型压根没打算交卷 | prompt 强制 + 收尾补提交流程 |
| 有 `submit_dimension`，`ok=false` 且 `error_code=quote_not_substring` | 原句抄错（多半抄了 200 字摘要而不是全文） | 工具描述写清"quote 必须来自 read_parent 的全文"，并把摘要与全文的边界讲明 |
| 有 `submit_dimension`，`ok=false` 且 `error_code=not_allowed` | 重复提交被拒 | 检查是不是同一维提交了两次而第一次已成功（runner 应视为已提交） |
| `terminated_by=budget_exhausted` | 预算提前打断 | 放宽 `max_model_calls`，同时核对 3 分钟时限 |
| `terminated_by=all_submitted` 但五维仍空 | runner 映射 bug | 修 runner，不是修模型 |

查法（一次 SQL 或直接读接口）：

```text
GET /api/reviews/{review_id}/agent-steps
看 action 的去重计数、ok 的分布、error_code 的非空值
```

### 1.2 已知的弱引导点（无论诊断结果如何都要改）

1. **system prompt 没有"必须交卷"的硬约束**：现在写的是"每一维都必须调用一次 `submit_dimension`"，但那是建议口吻，模型跑满 16 次工具后很可能认为"证据都看过了，可以总结"。
2. **`submit_dimension` 的 description 只说了它做什么，没说"不调用会怎样"**：工具描述里应当写「本维的结论只能由这个工具记录；不调用等于没评这一维」。
3. **预算 8 次模型调用偏紧**：五维 × （查证据 + 交卷）≈ 10 次以上才够，现在 5 次就用完了前半程。**`max_model_calls` 从 8 提到 12**，同时墙钟仍是 150 s，模型调用变多不等于更慢（工具才是耗时大头）。

## 3. 为什么提示词要这么写（给你复核用）

| 约定 | 来源 | 为什么写进提示词 |
|---|---|---|
| **先诊断再修** | 21 行轨迹 = 5 model + 16 tools，submit 一次都没有 | 这可能是"没调"，也可能是"调了被拒"。两种修法完全不同，猜错就是白改一遍 prompt |
| **收工协议写死四条** | 模型跑到第 16 次工具时容易"自我感觉已完成" | 现在的 prompt 是建议口吻（"必须调用一次"），模型会理解成"应该"；改成协议 + 自查，才有硬约束 |
| **补提交必须校验子串** | 首期铁律：引用必须可回溯 | 补提交是最后一道口子，一旦让它跳过校验，前面所有引用校验都白做 |
| **补提交落 `force_submit` 轨迹** | "轨迹必落库"纪律 | 否则报告里会出现"模型自己补的"和"代码补的"分不清，P15 验收时说不清 |
| **预算 8→12** | 五维 × 两轮 ≈ 10～12 次 | 8 次是照"每维一次 chat"的老实现定的，现在每维要检索 + 交卷，必然不够 |
| **Playwright 先 mock 面板接口** | v2.1.1 新增了 `/agent-steps` 请求 | 面板在 `/scoring` 页挂载，E2E 没 mock 就会真发请求；这不是放宽断言，是补测试夹具 |
