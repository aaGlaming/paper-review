## 二、为什么判据 5 会零触发

`apply_mention_guard` 第一行就是：

```python
if band != BANDS[0]:        # BANDS[0] == "充分"
    return outcome
```

**只有「充分」才进降档分支。** 上一版实测 50 维里「充分」6 条，且都在 guard 允许范围内，于是 critique 无事可做。critique 的第二条路径（模型复核）在 `chat_fn=None` 时直接 `continue`（`critique.py:96`），所以零触发是必然的。

这不是 bug，是设计假设与真实产出分布不匹配：模型在真实论文上几乎判「充分」，而 guard 只拦「充分」。

**本版的做法**：不改产品语义，用一个自建赛题包把「充分」+「缺必提条件」这个组合**造出来**，让 guard 有对象可降。造完之后，判据 5 的答案由事实决定，不预设。

## 五、为什么这么写

**为什么不用改代码就能造出样例。** v2.3.0 把「构造样例」当成了必须新增接口的事，其实 `POST /api/imports` 的设计就是收整个数据包目录——量规和约束本来就在包里。复制一份、换 id、加一条关键词离谱的 mention 约束，三步就到位。这条路径不碰任何现有数据，也不写一句按题号分支的代码。

**为什么关键词要 grep 确认。** guard 的判定是 `any(keyword in text)`，看起来很宽松，但也正因为宽松，如果关键词碰巧出现在论文里（比如写了「校准」两个字），约束就不会触发降档，整个 P2 白跑。提示词里明确要求先 grep 确认 0 命中。

**为什么 P2 要分两支记录。** 我不知道 guard 会在哪一层拦下：如果 submit 阶段就降完了，critique 拿到手已是「基本」，按 `critique.py` 第 77 行会走到第二条路径，而 `chat_fn=None` 又让它直接 `continue`——于是零触发，且这属于设计如此，不算实现缺陷。预设一个答案再去找证据，就是先射箭再画靶。

**为什么本版明确禁止改语义。** `apply_mention_guard` 被首期评分链路和 agent 提交路径共用，动它会牵动已验收的部分。验收阶段掺进结构性重构，出了问题就分不清是验收发现的还是验收改出来的。

**为什么 P4 允许写「未改动」。** 首期 18 条里有 15 条与 agent 无关，本版确实没改那些模块。诚实标注「未改动 + git diff 佐证」比硬凑一次复跑更有信息量。

## 六、本版之后

判据 5 若仍判「部分满足」，挂账到 Phase-3：要么等有足够多「充分」样本后复验，要么显式放宽 critique 触发范围（后者属改产品语义，须先立 Ruling）。

三类交付补齐后，`report-V3.md` 就能按「五条判据全 ✅」的体例收口；若判据 5 仍缺，报告写「部分通过 + 明确挂账」，比五条全 ✅ 更可信。
