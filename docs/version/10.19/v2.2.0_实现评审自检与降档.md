### 本版主体：`critique` 只降不提

| 项 | 规则 |
|---|---|
| 触发范围 | 只检查 `band ∈ {充分, 基本}`；「不足 / 证据不足」不进自检 |
| 权限 | **只能降一档**：充分→基本、基本→不足；提档请求一律拒绝并记轨迹 |
| 依据 | 必须给 `dimension_code` + `chunk_id` + `quote`；`quote` 必须是**该维已检索父块**的连续子串，否则整条忽略 |
| 次数 | 每单最多 2 次降档，超出不采纳 |
| 输入 | 只用该维父块与该题 `constraints`，**不给全文** |
| 位置 | **不新增图节点**，在 runner 里作为 agent 之后的后处理；理由见 §1.3 |
| 记录 | 每次降档写一条 `agent_step(node="critique", action="downgrade")`；被拒的写 `action="rejected"` |

### 不做

前端新功能（轨迹面板已能显示 critique 行）、图结构改动、prompt 调优、无进展阈值调整。

## 1. 现状体检（实测，不是推测）

### 1.1 v2.1.2 的真实结果

| 指标 | 实测 |
|---|---|
| 演示稿 | `bench-dragon`，`review_id=6512941c...` |
| `source` | `model` |
| 端到端 | 21.522 s |
| 五维 | `assumption=基本`、`constraint_check=基本`、`modeling=基本`、`presentation=不足`、`solution=证据不足` |
| 写入来源 | 前四维由 `submit_dimension` 成功写入；`solution` 未过 quote 校验 |
| `force_submit` | 1 行，接受 0 条 |
| `terminated_by` | `budget_exhausted` |
| 轨迹 | 26 行（`model` 6、`tools` 20） |

### 1.2 `budget_exhausted` 的真实原因

`max_model_calls=12` 只用了 6 次，`max_tool_calls=24` 用了 20 次——**两个都没超**。26 行轨迹 ≈ 25 步，正好撞上 `config={"recursion_limit": 25}`。

所以"预算耗尽"这四个字现在把两件不同的事混在一起了：

- 递归深度顶格（LangGraph 层）
- middleware 的模型/工具/单维/墙钟四闸（业务层）

本版要求轨迹与 `terminated_by` 必须能区分：`budget_exhausted` 只用于四闸，递归顶格记 `recursion_limit_reached`。

### 1.3 为什么 `critique` 不做成图节点

冻结文件 `backend/tests/graph/test_interrupt.py` 断言 `final["score_node_calls"] == 1`、`next == ()`、`status == "完成"`。往 `score` 后面挂新节点看起来无害，但它会改变 `next` 在中间态的形状，且 `build_review_graph()` 的默认调用（测试里用的那个）会多一个节点要喂参数。

更关键的是：**critique 需要的输入（五维结果 + 每维父块）在 runner 里已经是现成的**，做成节点还得把这些数据塞进 state 再取出来，纯属多绕一圈。所以放在 runner 后处理：

```text
agent 子图 → force_submit → critique（后处理）→ weighted_sum → 返回
```

轨迹里用 `node="critique"` 标记，读者看到的效果与节点一致。

### 1.4 评测基线（不许倒退）

| 指标 | 当前基线（v1.9.2 验收） |
|---|---|
| 档位一致率 | **13/60（21.67%）** |
| 引用精确匹配 | 27/27 |
| 证据不足命中 | 2/2 |

critique 只会降档，所以一致率**可能下降**。判据是：**不得低于 13/60**；若下降，先看降的是不是 gold 里本来就该低的维度，把差异逐维写进 progress，不许改 prompt 凑分。

## 3. 为什么提示词要这么写（给你复核用）

| 约定 | 来源 | 为什么写进提示词 |
|---|---|---|
| **先分清递归与预算** | v2.1.2：model 6/12、tools 20/24 都没超，却记 `budget_exhausted`；26 行 ≈ 25 步 | 指标名字说错，后面所有排查都会跑偏。递归顶格与四闸超限是两种病，混着记就永远治不好 |
| **critique 不做图节点** | 冻结测试锁 `next`、`score_node_calls`、`status` | 加节点看着无害，实则让默认构造的图多一个要喂参数的节点；而后处理拿数据是现成的 |
| **确定性复核在前、模型复核在后** | `apply_mention_guard` 已经能判"该降不降" | force_submit 补交进来的档位绕过了 submit 时的守卫，先用确定性规则兜一遍，再让模型看，成本最低 |
| **跳两级直接拒** | P14 规则：只降一档 | 允许跳级，模型一次就能把「充分」按到「不足」，等于绕过了中间档的证据要求 |
| **配额 2 次/单** | 计划 §5.1 | 不封顶的话，critique 会把整篇都降成「不足」，评测一致率必崩 |
| **critique 异常不阻塞** | 首期纪律：增强功能不许让主流程挂 | 自检是加分项；它挂了还能出报告，总比整单 500 强 |
| **一致率不得低于 13/60** | v1.9.2 立的测评纪律 | critique 只会拉低分数，所以必须设下限，否则"越严越好"会把评测做废 |
