## 3. 为什么提示词要这么写（给你复核用）

**P0 必须排第一，不是流程洁癖。** 现在库里 96 条 critique 轨迹全来自假 ID，任何「critique 触发率」「平均步数」这类统计都是错的。更要紧的是：如果先做 P2 再清污染，新产生的真实轨迹会和测试残留混在一起，你分不清哪条是真的。**先清库，再取证**，顺序反了证据就废了。

**P1 只出结论、不改代码，是刻意的。** guard 在 submit 和 critique 两处参数相同，这是设计层面的取舍，不是笔误。直接改代码会牵动首期那条已验收的评分链路（`review_graph.py:405` 也调了同一个 guard），风险远大于收益。先定级、再决定改不改，比边改边想安全。

**判据 5 的写法留了两条分支，因为结果不可预判。** 如果 guard 在提交层就把档降了，那 critique 确实没有参与，这时报告该写「由 guard 满足」；如果提交层没降，就要求 critique 轨迹里出现 `downgrade`。**先如实记录是哪一层生效，再决定判据 5 算不算过**，这比预设一个答案去凑要可信得多。

**三条核心回归单独点名，因为它们是首期最值钱的承诺。** 「证据不足不计分」「引用失败不进加权」这两条一旦被 agent 化弄坏，整个项目的卖点就没了；而「不输出奖项」是需求里的硬约束，扫描关键词就能验，最便宜也最该做。

**token 明确写「不可测」而不是留空。** `agent_step` 没有 usage 字段，硬填数字就是编。表格里留一个「不可测 + 原因」，比一个假数字有用。
