## 1. 现状体检（实测，不是推测）

### 1.1 上一版留下的可用积木

| 积木 | 位置 | 关键事实 |
|---|---|---|
| `DeepSeekChatModel` | `backend/app/agent/chat_model.py` | pydantic 字段：`model_name` / `temperature` / `chat_fn` / `bound_tools`；`bind_tools` 返回 `model_copy`；`_llm_type = "deepseek-compatible"` |
| `PaperRetriever` | `backend/app/agent/retriever.py` | 字段：`contest_id` / `rubric_id` / `review_id` / `dimension_code` / `section_types` / `retrieve_fn`；返回 `Document`，metadata 四键；空结果返回 `[]` |
| 客户端 | `backend/app/llm/client.py` | `chat_with_tools(...)` 已按 A 路线实现；`_post_json` 负责超时与重试 |
| 选档确定性部分 | `backend/app/scoring/selection.py` | `quote_is_substring(quote, parents)`、`join_evidence(parents)`、`apply_mention_guard(band, evidence_text=..., constraints=..., dimension_section_types=...)` |
| 加总 | `backend/app/scoring/aggregate.py` | `BANDS = ("充分","基本","不足","证据不足")`；`weighted_sum()` 一行不用改 |
| 审查 | `backend/app/review/consistency.py` | `check_numbers_citations_ranges(text, constraints)` 返回 findings 列表 |

### 1.2 现在缺的是什么

- 没有任何 `BaseTool`：`create_agent` 现在拿不到工具，装上也只能聊天。
- `dimension_results` 现在只由状态图的 score 节点写；agent 形态下需要一个**受控写口**，否则模型能随便改档位。
- 工具需要的数据（量规、约束、父块、审查结果）全在装配层，工具必须是**纯注入**的，否则测试要连 MySQL 与 Chroma。

### 1.3 错误码约定（本版定死，后面不许扩）

| error_code | 含义 |
|---|---|
| `param_invalid` | 未知工具名、缺必填参数、类型错、枚举值非法 |
| `not_found` | 请求的 `parent_id` 不在本次检索白名单里 |
| `not_allowed` | 未绑定赛题、该维已有结论（重复提交）、越权操作 |
| `quote_not_substring` | 原句不是任何一段父块的连续子串 |
| `budget_exceeded` | 本版不产生，留给 v2.0.3 的预算中间件 |

一、ToolContext（backend/app/agent/tools.py）

用 dataclass（不用 pydantic 也行，但要能直接构造）：

  review_id: str
  contest_id: str
  rubric_id: str

  findings_fn: Callable | None      # () -> list[dict]

  retrieved: dict = {}              # dimension_code -> list[父块]（search_evidence 时缓存）

二、六个工具（名字与入参照抄，不要自创）

1. list_dimensions()                             读
   返回 {"dimensions":[{dimension_code,name,weight,section_types,evidence_prompts}]}
   未绑定赛题（dimensions 为空）→ not_allowed

2. search_evidence(dimension_code: str, query: str = "", section_types: list[str] | None = None)  读
   - dimension_code 必须在 dimensions 里，否则 param_invalid
   - 调 retrieve_fn，把 parents 按 parent_id 合并进 ctx.retrieved[dimension_code]
   - 返回摘要列表：[{parent_id, section_type, chunk_ids, excerpt}]，excerpt 最多 200 字
     **不许把父块全文塞进返回值**（上下文预算）
   - 空结果 → ok + []（证据不足是业务结论，不是错误）
   - retrieve_fn 为 None → not_allowed

3. read_parent(parent_id: str)                   读
   - 只允许读本次已检索到的 parent_id（遍历 ctx.retrieved 找），否则 not_found
   - 返回 {"parent_id","section_type","content"}；content 超过 4000 字截断并标 "truncated": true

4. check_consistency(kinds: list[str] | None = None)  读
   - 调 findings_fn()，按 kinds 过滤（kinds 为空返回全部）
   - 返回 {"findings":[...], "count": n}；无命中 → ok + 空列表

5. get_constraints()                             读
   - 返回约束的只读视图：[{name, check_type, params, section_types}]；不返回内部 id 之外的敏感字段
   - constraints 为空 → not_allowed

6. submit_dimension(dimension_code: str, band: str, chunk_id: str, quote: str)   **写（唯一）**
   - dimension_code 必须存在，否则 param_invalid
   - band 必须在 ("充分","基本","不足","证据不足") 里，否则 param_invalid
   - 已提交过 → not_allowed（**拒绝覆盖，防止模型刷分**）
   - quote 必须是 ctx.retrieved[dimension_code] 里某段的连续子串：
     用 scoring.selection.quote_is_substring(quote, parents) 判断；失败 → quote_not_substring，**不写入**
   - band == "证据不足"：直接写 {band:"证据不足", status:"证据不足", chunk_ids:[], quote:None}
   - 否则：用 apply_mention_guard(band, evidence_text=join_evidence(parents),
     constraints=ctx.constraints, dimension_section_types=该维 section_types) 复核，允许降档；
     写入 {band: guard["band"], status: guard["band"], chunk_ids:[chunk_id], quote, guard}
   - 返回 {"dimension_code","band","downgraded": bool}
   - **不在这里加总、不算分**：权重与总分仍归 weighted_sum()

三、统一入口与 LangChain 包装

call_tool(ctx, name: str, args: dict) -> dict
  - 未知 name → {"ok": False, "error_code": "param_invalid", "message": "未知工具 ..."}
  - 缺必填参数 / 类型不符 → param_invalid
  - 其余按上面六个工具的语义执行
  - 统一返回 {"ok": bool, "data": ..., "error_code": str | None, "message": str | None}

build_tools(ctx) -> list[BaseTool]
  - 用 langchain_core.tools.StructuredTool.from_function（或 @tool）生成六个工具
  - 每个工具的 description 写清「什么时候该调用」，参数用 pydantic 模型声明（名字与入参同上）
  - 工具内部只调 call_tool(ctx, ...) 并把结果 json.dumps(ensure_ascii=False) 作为 content，
    **不要**再写第二套业务逻辑
  - 返回列表长度必须是 6，名字唯一

## 3. 为什么提示词要这么写（给你复核用）

| 约定 | 来源 | 为什么写进提示词 |
|---|---|---|
| **工具纯注入，不 import 数据层** | 首期契约：检索器与模型一律外部注入 | 工具一旦自己连库，测试就得连 MySQL + Chroma，agent 的单元测试会退化成集成测试 |
| **唯一写口 + 拒绝重复提交** | 本期判据 2 与纪律「写结论只有一个口」 | 允许覆盖，模型就会反复改档位刷到满意，`chat_calls` 和预算都失控；拒绝重复提交是把"一次判定"钉死 |
| **错误码封闭五个** | §3.3 的三条纪律 + 本期 §1.3 | 错误码一旦发散，模型就没法按码纠错，只能瞎猜；封闭集合才能让重试变成确定性行为 |
| **不依赖 pydantic 的报错** | 1.x 的 `tool.invoke` 会把 `ValidationError` 原样塞进 ToolMessage | 格式不稳定、字段名暴露，模型学不到"该补哪个参数"。自己的 `param_invalid` 带一句人话更好用 |
| **`search_evidence` 只回摘要** | 上下文预算：每维最多 4 段父块，全文进上下文会撑爆 | 让模型先看摘要再决定 `read_parent`，等于把"读多少"的权限留给模型，但每次读都有白名单限制 |
| **`read_parent` 只读白名单** | 防模型顺着 `parent_id` 读别篇论文 | 不限制的话，模型能构造 id 读到别人的父块，这是数据边界问题，不是性能问题 |
| **E2E 用空白占位键** | v2.0.1 的 P0 实测：`load_dotenv(override=False)` 会回填 | 不写这条，下一轮执行者一定会重复"删环境变量 → 仍然走模型 → 41 条超时"的循环 |
| **不加总分** | 首期硬约束：权重与加总归代码 | 工具里算分等于把 `weighted_sum()` 复制一份，两份必然分叉 |
