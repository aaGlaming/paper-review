## 1. 现状体检（实测，不是推测）

### 1.1 已有的

| 积木 | 位置 | 关键事实 |
|---|---|---|
| agent 装配 | `backend/app/agent/graph.py` | `build_review_agent(ctx, chat_fn=..., system_prompt=...)`，middleware 已挂两个 |
| 结果收口 | `backend/app/agent/runner.py` | 缺维补「证据不足」，`terminated_by` 已能产出 `all_submitted` / `budget_exhausted` |
| 预算 | `backend/app/agent/middleware.py` | 四闸：`model_calls` / `tool_calls` / `dimension_steps` / `wall_clock` |
| 轨迹 | `backend/app/agent/trace.py` | `record_call()` / `load_steps()`；表 `agent_step` |
| 轨迹接口 | `backend/app/api/routes.py` | `GET /api/reviews/{review_id}/agent-steps`，无记录返回 200 + 空数组 |

### 1.2 还缺的

- **没有无进展检测**：模型可以拿同一段父块反复 `search_evidence`，每次都"成功"，预算烧完才停。budget 能兜住，但会白烧 24 次工具调用。
- **响应里没有 `terminated_by`**：前端想知道"为什么停了"没有数据来源。
- **前端看不到轨迹**：`agent_step` 落了一堆行，用户只能查 SQL。
- **v2.1.0 的真实调用还在天上**：没有它，面板做出来也没东西可显示。

### 1.3 无进展的判定规则（本版定死）

只对**两类**工具调用计入"是否有进展"：

| 工具 | 计入方式 |
|---|---|
| `search_evidence` | 比较调用后 `ctx.retrieved[dimension]` 的 `parent_id` 集合大小是否变大 |
| `submit_dimension` | 比较 `ctx.submitted` 大小是否变大 |
| 其余四个（`list_dimensions` / `get_constraints` / `read_parent` / `check_consistency`） | **不计入**，也不重置计数——它们是读，重复读不该被当成进展 |

连续 **2 次** 计入的调用都没有带来新增 → 抛 `BudgetExceeded("no_progress")`，runner 映射成 `terminated_by="no_progress"`，缺维照旧补「证据不足」。

**为什么不是"任何工具调用连续两次无变化"**：模型第一次 `search_evidence` 拿到 4 段、第二次换查询拿到同样 4 段，这时候它还没读完就被判死循环，是误杀。用"新增集合"判定能过滤掉"换词但同结果"的合法重试。

## 3. 为什么提示词要这么写（给你复核用）

| 约定 | 来源 | 为什么写进提示词 |
|---|---|---|
| **P0 补真实调用** | v2.1.0 记录：真实调用未执行；实测 DB 342 行、四个模型键齐全 | 装配完成不等于 agent 跑通。没有一次真调用，"模型在决策"这句话就是推测，面板做了也没数据 |
| **无进展只认两类工具** | 模型常见的空转是「换词重查」与「重复提交」 | 把 `read_parent` 也算进进展，会让「反复读同一段」永远判不出死循环；全算进去又会误杀正常的回读 |
| **连续 2 次而非任何 2 次调用** | 首期纪律：宁可漏报不可误报（对齐阈值同理） | 阈值太松，正常探索会被掐断；太紧，白烧 24 次工具调用。2 次"无新增"是可解释的折中 |
| **`agent_terminated_by` 用新增字段** | 响应形状被前端与 E2E 依赖 | 改既有字段要同步所有断言；新增字段零风险，旧页面拿到 `undefined` 也不炸 |
| **E2E 用 route mock** | 一次真实 agent 运行要几十秒且花钱 | E2E 断言的是"面板会渲染轨迹"，不是"agent 能跑"——后者由 P0 的真实调用负责 |
| **请求失败不许显示空态** | v1.9.2 的教训：别把缺失伪装成结论 | "接口挂了"与"没跑过 agent"对用户的含义完全不同，混在一起会误导排障 |
| **progress 必须 UTF-8** | 本次实测：v2.1.0 段被写成 GBK，整份文件不是合法 UTF-8 | 混合编码会让后续任何脚本按 UTF-8 读取时报错，且错误位置离现场很远，极难查 |
