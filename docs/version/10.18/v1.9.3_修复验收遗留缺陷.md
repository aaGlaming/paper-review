## 1. 问题定位（先读这节再动手）

### 1.1 断点：约束与证据清单都没进 prompt

首期验收 V1 的唯一 ❌ 级遗留（表里记 ⚠️，但根因是缺陷）：

> 板凳龙 `assumption` 维：`band=证据不足; quote=null`，而输入假设章节**确实含**"板凳宽度对判断碰撞的影响"原句。

逐层查下去，链路在三处断掉：

| 层 | 代码位置 | 断在哪 |
|---|---|---|
| ① 装配层读了约束，但没往下传 | `routes.py` 的 `resume_review_endpoint` | `inputs = load_review_inputs(...)` 拿到了 `inputs["constraints"]`，但建图/调图时**只把 `dimensions` 传了进去**，`constraints` 没有作为图的入参或状态传入 |
| ② 图的维度归一化丢了字段 | `review_graph.py:_normalize_rubric_dimensions`（约 298 行） | 只保留 `dimension_code` / `name` / `weight` / `section_types` 四个字段，**把量规里的 `evidence_prompts`（证据清单）丢掉了** |
| ③ prompt 因此缺两块信息 | `scoring/selection.py:build_scoring_messages`（136 行） | `required` 那段只列 `check_type == "mention"` 的约束名，而约束根本没传进来 → 恒为 `["- 无"]`；`evidence_prompts` 也没进 user 消息 |

**结果**：模型收到的 user 消息只有"维度：假设的合理性（assumption）+ 题目要求必须提到的条件：无 + 证据（父块全文）：[…]"。它既不知道"板凳宽度"是必提条件，也不知道这个维度该重点找什么证据，于是保守判「证据不足」。

> 注意：`build_scoring_messages` 本身写得没问题（它支持 `constraints` 参数），**问题是调用链路上没人把 constraints 交给它**。

### 1.2 三个佐证说明这不是模型问题

| 佐证 | 证据 |
|---|---|
| 原句确实在论文里 | `data/samples/bench-dragon.md` 假设章节含"忽略板凳宽度"相关表述 |
| 模型在证据充分时能选档 | 同一轮 smoke 里 `smoke` 样例的 `assumption` 维拿到 `充分` 并给出 quote（`calls/15-resume-smoke.json`） |
| 父块检索非空 | 板凳龙那轮 `constraint_check` 维拿到了 quote，说明 retrieve 节点有产出 parents |

**所以修法是接通链路，不是改 prompt 去"引导"模型**——验收纪律第 1 条仍然有效。

### 1.3 另外三个缺口（V1 报告 f 节挂账的三项）

| 缺口 | V1 判定 | 需求条目 |
|---|---|---|
| 评分页显示不了量规原文 | §12.3 第 1 条 ⚠️ | "页面能打开量规条款和论文原句"——原句能开，条款不能 |
| 单篇评测差异看不到 | §12.4 第 1 条 ⚠️ | "可点进单篇看差异" |
| 历史存档不含 `change_list` | §12.4 第 3 条 ⚠️ | "打开一条历史记录…当时的原句仍然在"（原句在，审查清单不在） |

## 3. 为什么提示词要这么写（给你复核用）

| 约定 | 来源 | 为什么写进提示词 |
|---|---|---|
| **F1 表述为"接通链路"而非"优化 prompt"** | §1.2 三个佐证：原句在论文里、模型在 smoke 样例能选档、父块非空 | 这是本版的核心判断。若写成"优化 prompt"，执行方极可能加引导语把结果掰成想要的样子——那是验收作弊 |
| **把断点定位到三处具体代码** | 逐层读码：routes 只传 dimensions、`_normalize_rubric_dimensions` 丢 `evidence_prompts`、`build_scoring_messages` 的 `required` 恒为"无" | 不让执行方重新调研；且三处必须一起修，只修一处（比如只在 prompt 里硬编码约束名）会复发 |
| **"修完重跑仍可能判证据不足"提前声明** | 模型判断有不确定性 | 防止执行方陷入"反复调 prompt 直到出想要结果"的循环。判 ⚠️ 附原文是合法结局 |
| **F2 的两个方案都列出并要求说明理由** | 改 `GET /api/contests` 会影响前端与 E2E 断言 | 改既有响应形状是高风险操作，让执行方显式决策并承担更新测试的义务 |
| **F3 无 gold 的演示稿要返回说明而非空数组** | 3 篇演示稿没有同名 json | 空数组会被读成"无差异"，与"没有标准答案"是两回事——本项目一贯的诚实性原则 |
| **F4 禁批量重算、禁删旧记录** | 库里 270 条 review | 旧数据是验收证据（V1 那条 `2525dc78...` 要被重读）。删了或重算了，复验就失去对照基线 |
| **报告升 V2 不覆盖 V1** | 用户要求报告有版本号 | V1 是第一期验收的历史存档；覆盖它等于抹掉"当时是什么状态"的证据链 |
| **复验只跑受影响的条目** | 4 项修复各影响 1～4 条 | 全量重跑要 150～250 次 chat；针对性复验约 10 次，省钱且聚焦 |
