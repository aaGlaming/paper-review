## 1. 验收总则

### 1.1 判定口径

| 标记 | 含义 |
|---|---|
| ✅ 通过 | 该条要求的全部子项都满足，且有可复现的证据（命令 + 输出 + 落盘的响应体） |
| ⚠️ 部分通过 | 主路径满足但某一子项不满足，**必须写明缺哪一项、为什么、缺的后果** |
| ❌ 不通过 | 主路径不满足，或无法给出证据 |

**18 条全 ✅ 才算首期验收通过**；出现 ⚠️ 需用户明确接受才能收口；出现 ❌ 则 v1.0.0 保持未通过。

### 1.2 真实调用的留档规范（验收的生命线）

每次真实模型调用的以下内容必须落盘到 `docs/plan/acceptance/`（新建目录）：

```text
docs/plan/acceptance/
├── calls/                          # 每次调用的请求与响应原文
│   ├── 01-contests.json
│   ├── 02-create-bench-dragon.json
│   ├── 03-resume-bench-dragon.json
│   └── ...
├── screenshots/                    # 页面截图（可选但建议）
└── report.md                       # 最终验收报告
```

单个调用文件的结构：

```json
{
  "step": "03-resume-bench-dragon",
  "at": "2026-10-18T17:20:00+08:00",
  "request": { "method": "POST", "url": "http://127.0.0.1:8077/api/reviews/{id}/resume", "body": { } },
  "response_status": 200,
  "response_body": { },
  "notes": "五维 band / quote / chat_calls 见 response_body.dimensions"
}
```

**禁止**：把 API key 写进任何落盘文件；把 key 打印到终端或日志。

### 1.3 成本与时间预估

| 动作 | 调用量级 | 预估耗时 |
|---|---|---|
| 三篇演示各跑一次完整预审 | 3 × 5 维 ≈ 15～30 次 chat | 1～3 分钟 |
| §12.5 第四道题导入 + 一次预审 | 5～10 次 chat | 1 分钟内 |
| §12.4 15 篇全量评测（`?force=model`） | 75～150 次 chat | 5～15 分钟 |
| §12.3 量规第 2 版发布 + 新旧各一次预审 | 10～20 次 chat | 2～4 分钟 |

**总量约 150～250 次 chat 调用**。按 `deepseek-flash` 输入 $0.15/M、输出 $0.6/M 计，一次预审输入约 2～5K tokens、输出约 200～500 tokens，**全部验收的成本在几元人民币量级**。纪律：**不重复跑同一条**；每次跑完立刻落盘；`/api/eval/summary` 不加 `?force=model` 不触发真实评测。

## 4. 为什么提示词要这么写（给你复核用）

| 约定 | 来源 | 为什么写进提示词 |
|---|---|---|
| **前置门槛四条，其中 rerank key 单列** | v1.9.1 progress.md 明言"真实 rerank 未验，因环境缺 `RERANK_API_KEY`" | 这是上一版唯一的遗留项，而 §12.5 恰好管模型接口。不先把门槛立起来，验收跑到一半才发现 rerank 是假的，整份报告的可信度就没了 |
| **拿不到 key 的降级路径写明** | 硅基流动要实名；用户可能一时拿不到 | 主链仍可验收（MySQL 无向量兜底），但 §12.5 只能记 ⚠️——**把"不通过"变成"诚实的部分通过"**，比假装全过或整体卡死都好 |
| **[规则] / [模型] / [页面] 三分类** | 需求 §12.2 的 9 个必现点来源不同 | 6 个规则点不过 = 确定性代码有缺陷（必须修）；3 个模型点不过 = 模型判断差异（记 ⚠️ 附原文）。混在一起就没法归因 |
| **禁止"改 prompt 引导出想要的答案"** | 模型类验收点的固有诱惑 | 这是验收最容易作弊的地方。明令禁止，且要求附模型输出原文，让判断可被复核 |
| **调用留档四要素** | §1.2 | 没有留档的验收不可复现、不可追责；且明确规定"不含密钥"，把泄露风险堵死 |
| **成本预估 + 不重复跑** | 150～250 次 chat | 让执行方有成本意识，同时给出省钱纪律（不加 force=model 不触发真实评测） |
| **§12.5 用 fixture-extra 当第四道题** | 需求原文"可以使用自建的第四道题" | 该数据包已在 `data/contests/fixture-extra/`，导入函数与正式赛题同一套（v0.3.0 验过），是现成的试验田 |
| **5.2 坏包用临时目录造** | 不能污染 `data/` | 复制到临时目录改权重和再导入，坏包整包拒绝的语义才验得到 |
| **5.3 会留下 v2 量规，提前声明"接受并记录行数"** | 无删除接口 | 发布第 2 版量规是 §12.5 的硬要求，副作用（库里多一条 rubric）必须提前告知，不能偷偷做 |
| **"原则上不改代码"写进总则** | 本版是验收不是开发 | 防止执行方顺手重构；只允许"最小化修复 + 补测试 + 先记 Ruling" |
| **总表 + 报告六节** | §4 | 产出物格式固定，用户才能一眼看完 18 条的判定与依据 |
