# 接入真实赛题与论文数据（全流程验证手册）

> 文档版本：v1.0.3 · 生成时间：2026-10-19
> 适用版本：Phase-1 收口 + Phase-2（Agent 化）后的代码基线
> 用途：从零准备「赛题 + 量规 + 论文」三类真实数据，导入系统，跑通一次端到端真实评审。
> 依据：`backend/app/importing/catalog.py`、`backend/app/graph/review_graph.py`、`backend/app/api/routes.py` 的实际实现。

---

## 0. 先说清楚一件事：三类数据里只有两类能下载

很多人以为「标准」也是现成的，可以直接下。**不是。**

| 数据 | 能否直接下载 | 实际情况 |
|---|---|---|
| **赛题**（题目原文） | ✅ 可以 | CUMCM 官网、中国大学生在线均公开，含历年 |
| **论文**（学生答卷） | ⚠️ 能拿到，但有版权 | 官方展示论文可看；直接下载全文用于入库需自行判断合规 |
| **标准**（量规 rubric） | ❌ 没有现成的 | 官方只发布「评阅要点/讲评」，不是机器可读的评分表，**必须自己编** |

系统的 `rubric.json` 是要一条条写出来的：五个维度、每维四档描述、权重、必提条件。这部分工作量的真相是——**它比找论文麻烦得多**，而且质量直接决定评审质量。

---

## 1. 官方评阅标准 → 系统五维的对应关系

编量规不是凭感觉。CUMCM 公开的四项评阅标准可以直接映射到系统的五个维度：

| 官方评阅标准 | 系统维度码 | 检查什么 |
|---|---|---|
| 假设的合理性 | `assumption` | 假设是否来自题目条件，是否进入模型 |
| 建模的创造性 | `modeling` | 是否针对本题改变问题表示或求解方式 |
| 结果的正确性 | `solution` | 结果是否满足原题，能否被独立复核 |
| 表述的清晰性 | `presentation` | 评委能否快速找到答案、模型与证据 |
| （赛题硬性要求） | `constraint_check` | 必提条件、数值范围、必需情形是否满足 |

前四项来自官方口径，第五项是本项目加的——因为「论文写得好但漏了题目硬条件」是竞赛里最常见的失分点，值得单列一维。

编量规时，**先读该赛题的官方讲评**（评阅要点），再写 `evidence_prompts`。这一步比抄模板重要。

## 2. 下载渠道

### 2.1 全国大学生数学建模竞赛（CUMCM，国赛）

| 渠道 | 地址 | 能拿到什么 |
|---|---|---|
| 竞赛官网 | `www.mcm.edu.cn` | 历年赛题、优秀论文汇总页、竞赛通知 |
| 中国大学生在线 | `dxs.moe.gov.cn`（栏目：数学建模） | 分年份的赛题打包下载（`.rar`）、按题号整理的优秀论文、**赛题讲评** |
| 知网 | `www.cnki.net` | 期刊版获奖论文、《工程数学学报》建模专栏、评委评析文章 |

**操作建议**：

1. 到中国大学生在线找对应年份的赛题页，直接下中文版 `.rar`（例：2024 年的直链在该年赛题页内）。
2. 同页往下翻，通常有「论文展示」与「赛题讲评」两个栏目。**先看讲评，再看论文**——讲评告诉你这道题评委在意什么，这直接是 `evidence_prompts` 的来源。
3. 赛题 `.rar` 里是 PDF，需要转文本（见第 6 节）。

### 2.2 美国大学生数学建模竞赛（MCM/ICM，美赛）

| 渠道 | 地址 | 能拿到什么 |
|---|---|---|
| COMAP 官网 | `www.contest.comap.com` | 历年赛题、Outstanding 论文、Results 报告 |

美赛论文是英文的。系统章节关键词表只有中文（假设/模型/求解/检验/结果），**英文论文要先把标题改写成含中文关键词的形式**，否则整篇会落进「未分类」。这一点见第 6.3 节。

### 2.3 论文的替代来源（推荐）

官方展示论文数量有限且分散。更省事、更合规的做法是自己准备：

| 做法 | 优点 | 代价 |
|---|---|---|
| 用官方展示论文 | 质量高、有代表性 | 数量少，版权需自行判断 |
| **自己写一篇完整论文** | 完全可控，可以精准构造「某维不达标」 | 要花时间，但比找论文快 |
| 拿自己或同学的旧参赛论文（脱敏） | 最真实 | 需去掉姓名、学校、队号 |

对本期「验证全流程」这个目的来说，**自写一篇 8000 字左右的论文最划算**——因为你还能顺手控制它的档位分布（比如故意让 `constraint_check` 缺一个必提条件，正好用来验证降档链路）。

## 4. 赛题入库：一个目录 + 五个 JSON

系统的赛题不是「上传一个文件」，而是**导入一个目录**。目录放在哪都行，只要路径能被后端读到。

### 4.1 目录结构

```
data/contests/<contest_id>/
├── contest.json          # 题目元信息 + 题面
├── constraints.json      # 赛题硬约束（必提条件 / 数值范围 / 必需情形）
├── rubric.json           # 五维量规（权重、证据提示、四档描述）
├── pitfalls.json         # 常见错误（喂给检索当反面素材）
└── exemplars.json        # 优秀片段范例（喂给检索当正面素材）
```

五个文件缺一不可，且 `contest_id` 字段必须处处一致，否则整包校验会拒收。

### 4.2 `contest.json`

```json
{
  "contest_id": "cumcm-2025-A",
  "year": 2025,
  "problem_code": "A",
  "title": "烟幕干扰弹的投放策略",
  "statement": "把赛题原文（或高度浓缩的题面）写在这里，包含所有硬条件：数值、几何关系、限制。这段文本会进检索，写得越全越好。",
  "status": "draft"
}
```

`status` 只能是草稿/已发布等固定值；导入后还要单独调用发布接口才能用于评审。

### 4.3 `rubric.json`（工作量最大的一步）

```json
{
  "contest_id": "cumcm-2025-A",
  "version": 1,
  "status": "draft",
  "dimensions": [
    {
      "code": "assumption",
      "name": "假设的合理性",
      "weight": 20,
      "evidence_prompts": [
        "是否说明云团扩散的物理机制与简化依据",
        "是否交代有效遮蔽的判定口径",
        "是否说明风向、风速的处理方式"
      ],
      "section_types": ["假设", "模型"],
      "bands": [
        { "band": "充分", "score": 20, "description": "假设逐条给出，说明物理依据与适用范围" },
        { "band": "基本", "score": 12, "description": "主要假设已给出，个别缺适用范围" },
        { "band": "不足", "score": 5, "description": "假设笼统，未说明对建模的影响" },
        { "band": "证据不足", "score": null, "description": "检索到的切片里找不到与假设有关的表述" }
      ]
    }
  ]
}
```

要点：

- **五维都要有**：`assumption` / `constraint_check` / `modeling` / `presentation` / `solution`。缺维会导致该维直接落「证据不足」。
- `weight` 五维加起来必须是 100。
- `bands` 必须四档，且「证据不足」的 `score` 是 `null`——这一档**不进加权**，是项目的硬规则。
- `section_types` 决定这一维去哪些章节取证。写错就会检索不到东西。

### 4.4 `constraints.json`

```json
{
  "contest_id": "cumcm-2025-A",
  "constraints": [
    {
      "constraint_id": "cumcm-2025-A-effective-range",
      "name": "云团中心 10 m 范围内、起爆后 20 s 内可有效遮蔽",
      "check_type": "mention",
      "params": { "keywords": ["10 m", "20 s"] },
      "section_types": ["假设", "模型", "求解", "检验"]
    },
    {
      "constraint_id": "cumcm-2025-A-speed",
      "name": "无人机速度不超过 20 m/s",
      "check_type": "numeric_range",
      "params": { "min": 0, "max": 20, "unit": "m/s" },
      "section_types": ["模型", "求解"]
    }
  ]
}
```

`check_type` 当前支持三类：`mention`（必提关键词）、`numeric_range`（数值范围）、`required_case`（必需情形）。

**`mention` 的判定规则很重要**：`keywords` 里**任意一个**出现就算满足（`any()` 而不是 `all()`），而且只有「充分」档才会被它降档。写约束时别误以为要全提。

### 4.5 `pitfalls.json` 与 `exemplars.json`

```json
{
  "contest_id": "cumcm-2025-A",
  "pitfalls": [
    {
      "pitfall_id": "cumcm-2025-A-p1",
      "contest_id": "cumcm-2025-A",
      "dimension_code": "constraint_check",
      "phenomenon": "只算了遮蔽时长，没有回到题目条件核对 10 m / 20 s 的口径",
      "action": "补一段遮蔽判定检验：按云团中心与目标距离逐时刻判断",
      "section_types": ["检验", "结果"]
    }
  ]
}
```

```json
{
  "contest_id": "cumcm-2025-A",
  "exemplars": [
    {
      "exemplar_id": "cumcm-2025-A-e1",
      "contest_id": "cumcm-2025-A",
      "dimension_code": "assumption",
      "band": "充分",
      "excerpt": "把云团视为球体并说明该近似只在起爆后 20 s 内成立，之后受风场影响显著。"
    }
  ]
}
```

这两份文件是检索的「反面素材」和「正面素材」，写得好能明显提升选档质量。数量不必多，每维 2～3 条就够。

## 5. 论文入库：两条路

### 5.1 路 A：放进样例目录（适合反复跑）

把论文写成 Markdown，放到 `data/samples/` 下：

```
data/samples/my-paper.md
```

文件名（去掉 `.md`）就是 `sample_id`。之后用：

```json
{ "sample_id": "my-paper", "contest_id": "cumcm-2025-A" }
```

**注意**：`data/samples/*.md` 会被系统当成"演示样例"（`is_demo=true`、`has_gold=false`）。如果想让它在评测里出现，要放到 `data/samples/eval/` 并配一份 `<name>.json`（含 `gold`）。

### 5.2 路 B：直接传文本（适合验证一次）

```powershell
$paper = Get-Content -Raw -Encoding UTF8 'D:\papers\my-paper.md'
$body = @{ paper_text = $paper; contest_id = 'cumcm-2025-A' } | ConvertTo-Json -Compress
$created = Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8077/api/reviews' `
  -ContentType 'application/json' -Body $body
$created | ConvertTo-Json -Depth 5
```

返回里会有 `review_id`、`sections`（章节树）和 `status`。**`status` 应该是「待确认」**——说明章节树已切好，正在等人工确认。

## 6. 论文怎么转成系统能用的格式（最容易踩坑的一节）

### 6.1 PDF / Word → 文本

```powershell
# PDF（poppler 的 pdftotext，装一次就行）
pdftotext -enc UTF-8 -layout .\paper.pdf .\paper.txt

# 或者用 Python（项目已装 pypdf）
& 'D:\LEARN\AI\programs\AgentTask\env\agent-task\Scripts\python.exe' -c `
  "from pypdf import PdfReader; r=PdfReader('paper.pdf'); open('paper.txt','w',encoding='utf-8').write('\n'.join(p.extract_text() or '' for p in r.pages))"
```

Word 用 `python-docx`（项目已装）：

```powershell
& '...\python.exe' -c `
  "import docx; d=docx.Document('paper.docx'); open('paper.txt','w',encoding='utf-8').write('\n'.join(p.text for p in d.paragraphs))"
```

转完**必须人工看一遍**：公式、表格、图注常常变成乱码或错行。这些内容进入证据池后，会直接影响选档判断。

### 6.2 章节必须用 Markdown 标题，且标题要含关键词

系统切章节靠的是 **ATX 标题**（`#`、`##`、`###`），然后按标题里的关键词归类：

| 关键词 | 归到哪一类 |
|---|---|
| 参考文献 / references / bibliography | `参考文献`（**优先级最高，先查**） |
| 假设 | `假设` |
| 模型 / 建模 | `模型` |
| 求解 | `求解` |
| 检验 | `检验` |
| 结果 | `结果` |
| 其他 | `未分类` |

第一个标题之前的正文会单独成一段，叫「开头正文」。

**两条容易踩的判定规则**：

1. **「参考文献」优先**：标题里只要有「参考文献」（或 references / bibliography），无论还含其他关键词，一律归 `参考文献`。
2. **多个关键词命中时，取位置最靠后的那个**。所以「五、模型的建立与求解」会归到 **`求解`**，不是 `模型`——因为"求解"在后面。

第二条规则的实际后果：`assumption` 维要取「假设」「模型」两类章节，如果论文只写了「模型的建立与求解」这一节，它归了 `求解`，`assumption` 就永远取不到「模型」类的内容。**所以最好把"建立"和"求解"拆成两节。**

**这一步是整个接入流程里最容易翻车的地方。** 真实论文的标题通常写成：

```
一、问题重述
二、问题分析
三、模型假设
四、符号说明
五、模型的建立与求解
六、模型的检验
七、结果分析
```

应改成：

```markdown
# 问题重述

# 问题分析

# 模型假设

# 符号说明

# 模型的建立

# 模型的求解

# 模型的检验

# 结果分析

# 参考文献
```

关键点：

- **用 `#` 开头**，不要用「一、」这种中文序号
- 标题里**必须出现**关键词。按上面的改法，各类都齐了：假设 → `假设`，模型的建立 → `模型`，模型的求解 → `求解`，检验 → `检验`，结果分析 → `结果`，参考文献 → `参考文献`
- 「问题重述」「问题分析」「符号说明」不含量化关键词，会落「未分类」——这没问题，它们本来也不该被某维取证
- 一篇论文如果所有标题都不含关键词，**整篇都会进「未分类」**，结果是五维全部「证据不足」。这不是模型不行，是格式没对上

### 6.3 英文论文（美赛）

系统的关键词表只有中文。英文论文要么翻译标题，要么在标题里补中文关键词：

```markdown
# Assumptions（模型假设）

# The Model（模型）

# Solution（求解）
```

括号里带中文关键词即可被归类，正文保持英文不影响。

### 6.4 长度要求

| 论文长度 | 实际后果 |
|---|---|
| 800～1000 字（现演示稿） | 五维基本只能判到「基本」，判不到「充分」 |
| 3000 字以上 | 「充分」开始出现，但需要论证密度够 |
| 8000 字以上（接近真实参赛论文） | 才能真实检验「充分 / 基本 / 不足」三档的区分度 |

**这条很关键**：如果只拿千字样例跑，看到「全是基本」不要以为模型坏了——是稿子本来就撑不起「充分」。

## 7. 跑通一次完整评审

### 7.1 创建

```powershell
$body = @{ sample_id = 'my-paper'; contest_id = 'cumcm-2025-A' } | ConvertTo-Json
$r = Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:8077/api/reviews' `
  -ContentType 'application/json' -Body $body
$reviewId = $r.review_id
$r.sections | ConvertTo-Json -Depth 4
```

**先检查 `sections`**：每个章节的 `section_type` 是不是你想要的那一类。如果全是「未分类」，回到 6.2 改标题，别往下走。

### 7.2 确认章节（触发检索与评分）

```powershell
$resume = @{ sections = $r.sections } | ConvertTo-Json -Depth 6
$done = Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:8077/api/reviews/$reviewId/resume" `
  -ContentType 'application/json' -Body $resume
$done | ConvertTo-Json -Depth 8
```

### 7.3 验收看四个东西

| 看什么 | 期望 | 不对说明什么 |
|---|---|---|
| `source` | `model` | 是 `deterministic` → 模型键没配全 |
| 五维 `band` | 有「充分/基本/不足」的区分 | 全「证据不足」→ 章节标题没对上，或检索为空 |
| `dimensions[].quote` | 是论文里的原句 | 为空 → 该维没找到证据 |
| `score` | 有值 | 全是 0 → 五维都落「证据不足」，不进加权 |

### 7.4 看 Agent 轨迹

```powershell
Invoke-RestMethod -Uri "http://127.0.0.1:8077/api/reviews/$reviewId/agent-steps" | ConvertTo-Json -Depth 5
```

返回按 `idx` 排序的步骤列表。正常应该能看到 `list_dimensions` → `get_constraints` → 多次 `search_evidence` → `read_parent` → `submit_dimension` → `final` 这样的序列。

**如果 `steps` 是空数组**：说明这次没走 agent 路径（比如没绑赛题），不是接口坏了。

## 10. 常见坑

| 现象 | 原因 | 解法 |
|---|---|---|
| 五维全「证据不足」 | 章节标题不含关键词，全落「未分类」 | 按 6.2 改标题 |
| 只有某一维总是「证据不足」，别的正常 | 标题「模型的建立与求解」被归到 `求解`（取最靠后关键词），`assumption` 要的「模型」类没着落 | 把「建立」和「求解」拆成两节 |
| `source` 是 `deterministic` | `.env` 里模型键没配全 | 补齐四个键，重启后端 |
| 导入报 `contest_id 必须与 contest.json 的 xxx 一致` | 五个文件里的 `contest_id` 写得不一致 | 逐文件核对 |
| 导入报「必须是非空数组」 | `constraints` / `dimensions` 写成空数组 | 至少一条 |
| 发布后仍不能评审 | 只导入了没发布 | 调 `/publish` |
| `agent-steps` 空数组 | 没绑赛题，走了 deterministic | 创建时带 `contest_id` |
| 跑 E2E 时确认卡 5 秒超时 | 进程里带着 `.env` 的模型键，真去调模型了 | 把 7 个键设成**空白占位**（不能删），重启后端 |
| 判不到「充分」 | 论文太短（千字样例） | 换真实论文 |

## 11. 最短路径建议

如果只想尽快验证一次全流程，按这个顺序：

1. 从中国大学生在线下一年赛题 `.rar`，取一道题的 PDF
2. **自己写一篇 8000 字左右的论文**（比找合规论文快），按 6.2 的标题格式组织
3. 照第 4 节造五个 JSON，量规按官方四项标准 + 讲评写
4. 导入 → 发布 → 创建 → 确认 → 看五维和轨迹
5. 对不上就回第 10 节查表

做完这一轮，才算真正验证了「赛题 → 检索 → 选档 → 校验 → 报告」这条链在真实数据上成立。之前用千字样例跑出来的结论，只能证明流程能走通，证明不了判定质量。
