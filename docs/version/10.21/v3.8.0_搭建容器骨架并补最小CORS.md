### 1.2 上一版为什么又白停一版：一条「恰好 3 处」的判据

上一稿写的前置是 `grep -c low_sample backend/app/report/evaluation.py` **应为 3**。执行方实测 **4**，于是判红停版——**停得没错，错的是这条判据**。

同一份文件、同一个字符串，不同参数给出 3～7 个不同的数：

| 命令 | 结果 |
|---|---|
| `grep -c 'low_sample'` | **3** |
| `grep -ci 'low_sample'` | **4** ← 执行方拿到的数 |
| `grep -o 'low_sample' \| wc -l` | **5** |
| `grep -oi 'low_sample' \| wc -l` | **7** |

`-c` 数的是**行**，`-o \| wc -l` 数的是**匹配**，`-i` 会把 `LOW_SAMPLE_THRESHOLD` 也算进来。**"恰好 N 处"根本不是一个确定的量**，把它写成闸门，等于把判据的稳定性交给执行方随手选的参数。

正确的判法有两条，本版都用：

1. **二值化**：`grep -q` 只看有没有，不看几个。前置要回答的问题是「这个能力在不在」，不是「这段文本长什么样」。
2. **跑用例证明能力**：`test_eval_metrics_mark_small_denominator_without_changing_rates` 与 `test_empty_eval_metric_is_not_low_sample` 各自通过，比任何计数都强——计数能证明"有人写过这个词"，用例才能证明"它真的按预期工作"。

**通用纪律**：从本版起，前置闸只许用「存在 / 不存在」「通过 / 不通过」二值判定；凡是需要数数字的，必须写清命令与参数，且优先换成一条用例。

### 1.3 三个决定本版写法的实测事实

| 事实 | 证据 | 对方案的影响 |
|---|---|---|
| **本机没有 Docker** | `docker --version` 无输出 / 命令不存在 | **不许出现任何「构建镜像」「compose up」判据**，全部改静态校验 |
| `compose.yaml` 四服务全是空壳 | 文件内容为 `frontend: {}` / `backend: {}` / `mysql: {}` / `chroma: {}` | 骨架要补，但补完仍不可运行——标注必须显眼 |
| 后端**没有 CORS 中间件** | `grep -rn CORSMiddleware backend` 零命中；`create_app()` 在 `backend/app/api/app.py:36` | 补最小 CORS，否则骨架一进容器就撞同源策略 |

补充事实：`backend/requirements.txt` 13 条全部 pin 版本（含 `chromadb==1.5.9`、`pytest==9.1.1`）；仓库里**没有 Dockerfile、没有 .dockerignore**；前端请求走相对 `/api`，由 `vite.config.ts` 代理到 `127.0.0.1:8077`；`PyYAML 6.0.3` 已在项目环境。

### 1.4 本版的边界：写出来，但不假装它能跑

`§8.1` 对 P24 的裁决是「保留骨架 + backend Dockerfile 草案；不要求四服务可运行、不加健康检查」，理由是它出自《执行手册》的交付物清单而非产品需求，且跑通需要 4 个镜像 + 卷 + 健康检查。

本版**严格遵守这条边界**。所以判据全部是「文件存在 + 内容合规 + 静态可校验」，**没有一条判据依赖镜像真的能起来**。这是有意为之：

> 一台没装 Docker 的机器上，唯一的验证方式就是**把「合规」写成脚本能查的东西**。肉眼检查四个 YAML 字段，和没检查一样。

### 1.5 为什么顺手补 CORS：它不是新功能，是骨架的前提

现在前后端同源问题被 Vite 代理遮住了：浏览器只跟 `5173` 说话，代理转发到 `8077`，所以没有 CORS 也一切正常。

一旦按 compose 的方式起（前端静态文件在另一个容器/端口），浏览器就会直接对 `8077` 发请求，**同源策略立刻生效**，所有接口在浏览器里全红。这不是"以后再说"的事——**它是"骨架到底算不算半成品"的分界线**。

补法要克制：allowlist 从环境变量读，默认只放行本地 `5173` 两个写法，**默认绝不写 `*`**。

## 三、为什么这么设计

**把判据从「能跑」换成「能查」。** 一台没有 Docker 的机器上，「compose 能起来」这条判据永远拿不到证据，写上去的结果只有一个：执行方如实报红，我们花一整版讨论"要不要装 Docker"。改成静态脚本后，同样一台机器能给出确定的、可复跑的结论。

**第 6 条 CORS 用例比第 5 条重要。** 只测「允许的源拿到头」，把 allowlist 写成 `*` 也全绿——那是最常见的错法，因为它"能用"。反过来测「未知源拿不到头」，就把「没有放宽」变成了可执行断言。

**`--factory` 写在注释里，是因为它验不了。** 入口是 `create_app()`，容器 CMD 漏 `--factory` 会直接起不来。本机验不了，但**必须写下来**——写下来是知识，不写就是下一次踩坑。

**四个 `UNVERIFIED` 标注不是形式主义。** 骨架最大的风险不是它不存在，而是**半年后有人以为它可用**。四个服务四行标注，成本四行字，挡的是"把骨架当交付"这一类误判。

**镜像 ≥ 1 GB 这条要提前写。** `chromadb==1.5.9` 加上 onnx 运行时，镜像不可能小。这种代价不写，等真要构建的那天才发现，就会变成"为什么这个决定当初没人提"。

**为什么合成一整段。** 分节版（P0/P1/…/P6）读起来清楚，但复制到执行方那边时经常被截断成"只贴了任务、没贴禁令和判红规则"——上一版裸 `pytest` 的坑，正是判据与命令写法分处两节、执行时只取了其中一节造成的。合成一整段后，闸门、判红规则、任务、禁令、交付在同一屏内，**漏读的成本从"少做一件事"变成"明显看得见"**。
