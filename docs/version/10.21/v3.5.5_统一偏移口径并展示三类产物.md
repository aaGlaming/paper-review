### 1.2 问题一：live 只抽到 0 条

v3.5.4 的 live 验证用了一条已有评审 `6f8dc2be…`，结果 `count=0`、`by_type` 三项全 0、GET 返回 `[]`。它按规则确实没有候选产物，但这意味&#x7740;**「能抽出产物」这条正例只在单元测试里成立，没在真机上跑通过一次**。

原因写在它自己的记录里：写权限规定 `review`/`review_session` 只读，所以没敢新建评审。这个谨慎是对的，但结果是**P21 的核心能力一次都没被端到端验证**。

### 1.3 问题二：前端与后端的坐标不是同一套

产物区间指向 `ReviewSession.paper_text`（含 ATX 标题行与空行的全文）。而前端现在这么做：

```ts
// frontend/src/composables/useOffsetLocator.ts
export function concatSections(sections: PaperSection[]): string {
  return sections.map((section) => section.content ?? '').join('\n')
}
```

**把各段 `content` 用 `\n` 拼起来复现全文**——但拼接结果里没有标题行、没有段间空行，长度和 `paper_text` 对不上，越往后偏得越多。这个文件自己的注释就写着「全文偏移 vs 分段正文的双源风险」，只是当时没有产物需求，靠 `indexOf` 校准糊过去了。

而 `GET /api/reviews/{id}` 返回的 `sections` **只有 `title/section_type/level/content`，没有区间**。区间计算只存在于 extract 端点内部：

```python
# routes.py:776
def _confirmed_sections_with_ranges(paper_text, sections): ...  # 只在 extract 里用
```

所以正确做法不是在前端再算一遍，而是**让同一份区间计算同时供给两处**。

### 1.5 还有一个事实要记住

v3.5.3 的探测表证明：13 份归档 PDF 里只有 **3 份有文本层，而那 3 份全是「X题.pdf」题面**（1,751 / 1,372 / 1,414 字符），10 份论文全是扫描件（0 字符）。所以「PDF 上传」这条路对论文场景是 100% 失败——不是实现问题，是数据形态。文案里必须让用户看到这一点，而不是只看到「不支持」。

## 三、为什么这么写

**为什么把「区间计算只有一份」当成第一件事。** 现在前后端各有一套坐标：后端按 `paper_text` 算，前端靠拼接 `content` 复现。两套坐标在短文本上差不多，在真论文上会越偏越多——而偏移错位的表现不是报错，是**高亮错一段**。用户看到"引用的句子不对"，第一反应是模型胡说，实际是前端算错了。**坐标这种东西，只能有一个真相来源，多一个就是多一个谎报点。**

**为什么 GET 详情允许降级、extract 必须硬失败。** 读取是既有能力，用了半年没出过问题；新增一个区间字段不该让它变成 409。而抽取的输出要落库、要被引用，结构不一致还硬写进去就是脏数据。**同一份数据，读的时候宽松、写的时候严格——这两条不矛盾，是分工。**

**为什么这次要求把演示评审留下来。** 前四版每次验证完就清理，结果是：功能全绿、库里一条产物都没有，截图也拍不出来。P21 的验收需要"打开某条评审能看到三类产物"这个画面，清得太干净反而没法证明。**可验证的产物要留得下，验证的痕迹才叫证据。**

**为什么非要 live 跑出 `count>0`。** v3.5.4 的单元测试写了 18 条，规则全过，但真机上一次都没抽出东西。这两件事的差别在于：单测用的是我构造的 `markdown` 字符串，真机用的是 `paper_text` + 已确认 sections + 真实事务。**中间任何一环接错，单测都是绿的。**

**为什么基线要改写成 153 / 765 / 278。** 146 是 v3.5.1 的数字，之后 E2E 又写进去 7 条。如果下一版还拿 146 做闸门，执行方会在 P0 就判红，然后花一轮去查"谁删了数据"——**过期的基线不报错，它只是让人白跑一轮。**
