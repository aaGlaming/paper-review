## 一、现状：上传卡在一个决策上，而不是卡在代码上

### 1.1 v3.5.0 交了什么

| 项 | 结果 |
|---|---|
| 细则 | `Phase-3-P21-plan.md` 八节齐全；`rg 'cumcm-'` 无匹配 |
| 表 | `review_artifact` 建成，外键 `ON DELETE CASCADE`、唯一 `(review_id, ordinal)`、三类类型常量 |
| 契约 | 只读 `GET /api/reviews/{id}/artifacts`，空表 200 `[]`；**无写接口** |
| 测试 | 新增 7 条（幂等、空列表、非法类型、缺字段、级联、排序、权限） |
| 门禁 | `401 passed` ×2、build/vitest 与 v3.4.2 一致、logs ok、docs 103 |

### 1.2 唯一挡路的东西：限额没有来源

细则 §2.2 的原话是「仓库内没有 P21 的字节上限或页数上限……**因此本细则不编造数值**；v3.5.1 在找回 §9.1 或取得明确决策前，不开放上传」。这个判断是对的——但需求原文确实找不回来，所以本版必须**做一次决策**，并把决策与推导依据一起写进细则。

### 1.3 决策依据：样本实测（我刚量的）

| 类别 | 数量 | 最大文件 | 换算 |
|---|---:|---|---|
| Markdown 样本 | 13 | **122.3 KB / 52,648 字符**（`cumcm-2024-C-c038.md`） | 典型 70–90 KB |
| PDF 归档 | 13 | **9.21 MB**（`A178.pdf`）；已能读出页数的最大 **58 页**（`A242.pdf`） | 4 个读不出（见 1.4） |

据此取默认限额：

| 项 | 决策值 | 依据 |
|---|---|---|
| 单文件字节 | **20 MB** | 最大样本 9.21 MB 的约 2 倍余量；扫描件普遍更肥 |
| PDF 页数 | **80 页** | 已读出最大 58 页的 1.4 倍；再高单篇解析时间不可控 |
| 规范化文本 | **200,000 字符** | 最大样本 52,648 字符的约 4 倍；这一项约束的是解析与模型上下文成本，与 `MEDIUMTEXT` 容量无关 |
| 本版类型 | **仅 `.md`** | docx / pdf 按拆版走 v3.5.2 / v3.5.3，一次只开一种，拒绝理由才说得清 |

**这些是工程决策，不是需求原文。** 写进细则时必须标清来源，并留一句「若拿到 §9.1 原文，以原文覆盖本表」。

### 1.4 顺带发现：13 个 PDF 里 4 个读不出页数

`A178.pdf`、`C038.pdf`、`A053.pdf`、`C063.pdf` 全部报 `PdfReadError: Could not read Boolean object`，用 `strict=False` 也一样，当前 `pypdf 6.20.1`。也就是说**页数上限这条判据在 31% 的归档件上会直接失效**。

本版只登记、不处理，但它给 v3.5.3 提了个醒：**「读不出页数」和「超过页数上限」必须是两种不同的拒绝理由**，混成一个 4xx 会让用户永远不知道为什么传不上去。

### 1.5 还有一个部署事实，和一个路由陷阱

v3.5.0 明确写了：8077 上跑的仍是旧进程，新路由 live 返回 404（只以 TestClient 验证过）。本版要验上传接口，**必须重启**——否则测的是不存在的路由。

更要紧的是：我原本打算用 `POST /api/reviews/upload`，实测返回的是 **405 而不是 404**：

```
POST /api/reviews/upload  →  405  Allow: GET
```

因为 `routes.py:649` 已有 `GET /reviews/{review_id}`，`upload` 被当成 `review_id` 匹配掉了，POST 自然不允许。**这个路径会静默撞车**：写代码时看着没问题，上线后要么 405，要么被动态路由吃掉。

所以本版上传接口改用 **`POST /api/uploads`**（独立前缀、单段路径，不在 `/reviews/{review_id}` 的匹配范围内）。

## 三、为什么这么写

**为什么先做决策，再写代码。** 细则里「不编造数值」是对的，但一个不落地的「待校准」会永远挡住上传。决策和编造的区别不在数值本身，而在**有没有依据、有没有写清来源**：按样本最大值取余量是工程判断，拍脑袋写「10 MB」才是编造。**未知可以先按可解释的默认值推进，前提是把「这是决策、不是需求」写在纸上。**

**为什么本版只开 md。** 三种格式的失败原因完全不同：md 是解码问题，docx 是容器/段落顺序问题，pdf 是页数与文本层问题。一次开三种，用户上传失败时只能看到一句「无法解析」，我们也分不清是哪一层出的错。**一次只加一种格式，错误信息才说得具体。**

**为什么拒绝路径要单列一节。** 上传功能的正确性主要不体现在「能传上去」，而体现在**「传不上去的时候有没有留下垃圾」**：空文件建了一条空评审、编码失败写了一段 `?`、落盘成功但落库失败留了个孤儿文件——这些都要等到用户投诉才发现。先写拒绝路径的测试，再写成功路径，是这类功能唯一靠谱的顺序。

**为什么字节上限和字符上限都要有。** 它们防的不是同一件事：字节上限防的是磁盘与传输，字符上限防的是解析与模型上下文。一个 5 MB 的 md 可能是 200 万字符的极端长文，字节没超、字符爆了，解析会卡住整条链路。**两个维度各自设限，别指望一个数把两件事都管住。**

**为什么 4 个读不出页数的 PDF 要现在记下来。** 它们会在 v3.5.3 变成 31% 的上传失败率，而那时的错误信息如果是「文件不合格」，排查会从「查 pypdf 兼容性」开始而不是从「这 4 个文件有什么共同点」开始。**提前把已知的坑写进文档，是把未来的调试成本挪到现在。**
