# v3.5.3 · 判定 PDF 可读性并给出拒绝口径

> **阶段**：Phase-3 / **P21 第四份**
> **前置**：`v3.5.2` 完成 docx 转换（`docx_to_markdown`、12 条新测试、`427 passed ×2`、live 上传 201）。
> **本版范围**：先摸清 13 个归档 PDF 到底能不能读 → 选一个可声明的 reader → 把 pdf 从「415 不支持」推进到「能判页数、能分清三种失败」→ 实测单页 OCR 代价。**不做 OCR 接入，不做产物抽取。**

## 一、现状：不是「pypdf 有 bug」，是这批 PDF 根本没有文本层

### 1.1 v3.5.2 交付

| 项 | 结果 |
|---|---|
| 转换器 | `backend/app/importing/docx_text.py`，只暴露 `docx_to_markdown(bytes) -> str` |
| 顺序 | 遍历 `document.element.body`，段落与表格保持文档顺序 |
| 标题 | 只认 `Heading N` / `标题 N` / `outlineLvl`，不猜字号 |
| 测试 | 转换器 10 条 + 集成 2 条，全量 `427 passed ×2` |
| live | 重启后匿名 401；上传现场生成的 H1/H2/表格 docx → 201；验证后已清理，`review` 仍 146 |

### 1.2 我上一版说错了：不是 4 个，是 8 个

v3.5.1 那版我写「13 个 PDF 里 4 个读不出」——**那是错的**，因为我当时只按体积取了前 5 个测。v3.5.2 全量枚举后是 **5 可读 / 8 不可读**，我现在重跑确认：

| 文件 | pypdf 6.20.1 |
|---|---|
| `A242`（58 页）、`A196`（34 页）、三份「X题.pdf」 | 可读 |
| `A016`、`A053`、`A163`、`A178`、`C038`、`C063`、`C094`、`C234` | **`PdfReadError`**（`Could not read Boolean object`，`strict` 开关无差别） |

**62% 的归档件连打开都做不到。** 这个数字比 31% 严重得多，直接决定本版必须先解决「读」的问题，而不是先写解析。

### 1.3 更要紧的发现：读得出来也没有文本层

我用 `pdfinfo` / `pdftotext` 抽查了 4 个（含 2 个 pypdf 读不出的），页数都能拿到，但**正文一个字符都抽不出来**：

| 文件 | pypdf | `pdfinfo` 页数 | `pdftotext` 非空白字符 |
|---|---|---|---|
| `A178` | 失败 | **48** | **0** |
| `A242` | 58 页 | 58 | **0** |
| `C094` | 失败 | 58 | **0** |
| `A196` | 34 页 | 34 | **0** |

这不是解析精度问题。这些 PDF 是**扫描版**——每页是一张图，没有文字层。项目里真实论文一直如此（OCR 那条经验就是这么来的），只是这次在 P21 的入口上撞见了。

结论：**「PDF 有文本层就直接抽」这条路，在这批文件上等于不存在。** P21 要支持真论文，终点必然是 OCR；而 OCR 的代价（单页数秒、58 页要几分钟）与「上传后同步返回」的接口形态直接冲突。

### 1.4 还有两个不能忽略的实现事实

- **PATH 上那个 `pdftotext` 是 Xpdf 4.00，不是 poppler**，而且来自 `Git/mingw64` 与 `texlive` 的附带安装——**换台机器就没了**，不能当依赖。
- `pymupdf` / `pdfminer` / `pdfplumber` **都没装**。而 PyMuPDF 是 AGPL、Xpdf 是 GPL——真要引入，许可证得写进文档，不能悄悄 `pip install`。
- `rapidocr-onnxruntime 1.4.4` **可用**，这是 OCR 唯一现成的路径。

### 1.5 所以本版要交付的不是「pdf 支持」，是「pdf 的三种失败分得清」

现在 pdf 上传只会得到一句 415「将在 v3.5.3 支持」。而真实情况有三种，用户需要不同动作：

| 情况 | 用户该做什么 | 当前会看到 |
|---|---|---|
| 页数超过 80 | 拆分成两篇或换短稿 | 415「不支持」 |
| 打不开（结构异常） | 换导出工具重新生成 | 415「不支持」 |
| 扫描件、无文本层 | 等 OCR 能力，或先自行转文字 | 415「不支持」 |

三种混成一句，用户只会反复重传。**本版把它们拆开，并把 OCR 的代价测出来，作为 v3.5.4 是否开工的依据。**

## 三、为什么这么写

**为什么先做探测矩阵，不先写解析器。** pypdf 在 8 个文件上直接抛异常，说明问题在「读」这一层，不在「抽」这一层。这时候写解析逻辑，等于给打不开的文件写更精细的报错。**先确定用哪把钥匙，再研究门后面的房间。**

**为什么坚持三种失败分开报。** 用户看到「不支持」会重传同一个文件；看到「48 页超过 80 页上限」会去拆稿；看到「无文本层，疑似扫描件」会去换源文件或等 OCR。**同一句错误信息对应三种完全不同的下一步动作时，它就等于没说。**

**为什么我自己那版写错了要专门说明。** 上一版我把「抽样 5 个」当成「全量 13 个」，得出 31%，真实是 62%。这种错误不会让代码跑不起来，只会让排期判断错一倍。**样本量写错一次，后面的所有努力都在错误的前提上。**

**为什么本版不接 OCR。** 单页几秒、58 页几分钟，塞进同步上传接口就是把一个 HTTP 请求变成超时炸弹。而且 OCR 会带来页码与字符偏移的映射问题——定位要指回原文，但原文是图片。**这不是「加个库」的活，是接口形态和定位契约都要重做，得单独一版。**

**为什么强调不要依赖 PATH 上的 pdftotext。** 我实测它来自 `Git/mingw64` 和 `texlive` 的附带安装，是 Xpdf 4.00 而不是 poppler。在本机能跑，在别人机器上 `FileNotFoundError`。**工具的来源和它的能力同样重要——一个恰好在 PATH 上的二进制，不是依赖。**

**为什么把决策点明写成 A/B 两条路。** 到了这一步，「继续做 P21」已经不是一个任务，而是一个取舍：要么接受异步接口吃掉 OCR 的几十秒，要么先让产物链路在 docx 上跑通、把 pdf 继续挂账。**取舍要写清代价再选，不要用「先易后难」把它糊过去——那句话对任何两条路都成立，所以它什么也没说。**
