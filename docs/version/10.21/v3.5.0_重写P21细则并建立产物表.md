### 1.2 现有解析链路的真实形状（这决定了 P21 要做成什么样）

| 事实 | 证据 |
|---|---|
| 入口只收**纯文本** | `routes.py:58` `CreateReviewRequest` 只有 `paper_text` 与 `sample_id`，互斥 |
| 章节按 **ATX 标题**切 | `review_graph.py:147` `_parse_sections`：`_HEADING_RE` 找 `#` 开头的行，第一个标题之前算「未分类」 |
| 没有上传 | `grep UploadFile backend/app` → 0 命中 |
| 没有产物表 | `grep review_artifact` → 只命中文档与本项目记忆，代码里 0 命中 |
| 素材是 Markdown | `data/samples/*.md`；原始 PDF 在 `data/papers/<赛题>/` |

一句话：**现在能处理「已经是有标题的 Markdown」，处理不了「用户手里的 docx/pdf」。** P21 的价值就是把中间那一段补上——docx/pdf → 带 ATX 标题的 Markdown → 现有解析链路，顺带把正文里的三类结构化产物抽出来存库。

### 1.3 为什么本版先定表，不先做上传

## 三、为什么这么写

**为什么第一版不写上传代码。** 上传本身不难，难的是它下游连着三样东西：转成 Markdown 的形状、三类产物的定义、产物怎么定位回原文。这三样一旦定错，上传写完也得重写。**先把契约定死，再往契约里灌数据**——尤其是 `review_artifact` 这种会被评分和 P22 对齐同时消费的表。

**为什么要求把「证据来源与缺口」单列一节。** 需求原文已经不在仓库里了。这种情况下最危险的不是缺信息，而是**用一行摘要假装自己读过需求**：「依据 9.1 节」看起来严谨，实际上什么都没说。把缺口写在最前面，后来补原文的人一眼就知道该校准哪几段。**缺什么写在明面上，比补齐更难的是承认它缺。**

**为什么三类产物要各给正例反例。** 「主张」「表格」「引用」这三个词单看谁都懂，落到代码里立刻出现分歧：一个带数字的句子算主张还是引用？三行的表格算不算表格？各给一条真实段落做正例、一条做反例，分歧就没法含糊过去。**定义的可执行性，靠例子而不是靠形容词。**

**为什么本版只开只读接口。** 没有上传就没有合法来源，此时开放写接口，等于给「手工灌产物」留了门——后面每次数据对不上，都要先排除「是不是有人灌过」。**在没有合法写入路径的时候，不提供写入路径本身就是一种约束。**

**为什么建表要幂等、要级联、要稳定排序。** 这三条不是洁癖：幂等决定能不能重复执行（这个项目已经因为非幂等踩过坑）；级联决定删 review 之后会不会留下孤儿产物；稳定排序决定前端和人看到的顺序是不是同一个。**表结构里最贵的错误，是那种上线三个月后才发现的。**
