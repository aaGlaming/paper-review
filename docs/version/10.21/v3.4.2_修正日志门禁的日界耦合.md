### 1.2 红的到底是什么

`check_logs.py` 无参数运行，检查的是**今天**（20261021）。当天实际有日志的目录：

| 有 | 无（其中 4 个是 `REQUIRED_WRITERS`） |
|---|---|
| api / audit / errors / graph / llm / report | **retrieve / scoring / review / importing**、agent / auth / ai_chat / dashboard / frontend |

那 4 个空目录全都**只在跑完整评审时才写**。今天没跑评审——只有大屏与门禁——所以它们空着是正常状态，不是埋点坏了。

### 1.3 这个门禁的注释里，早就写过同样的理由

`scripts/check_logs.py` 第 16–21 行原文：

```python
# 白名单只减不增：auth 已是登录每日常态，从白名单移除；
# audit 只在权限拒绝时写，某天无拒绝即为空，允许空但不许加进必需写入者
# （加进去会让脚本在无拒绝的日子周期性误报）。
# ai_chat 只在教师使用问询时写，无问询的日子为空。
ALLOWED_EMPTY = {"errors", "ai_chat", "dashboard", "audit", "frontend", "agent"}
```

「只在特定操作时写」这个理由，已经用在 `audit` 与 `ai_chat` 上了。`retrieve` / `scoring` / `review` / `importing` 属于**完全相同的类别**——只在评审链路跑起来时写——却还留在必需写入者里。**这不是标准高低的问题，是同一份脚本里两套标准。**

### 1.4 为什么不能「跑一次评审凑日志」

跑一次完整评审确实会写满那 4 个目录，而且能顺带验证 P19 之后的链路。但它不能当**常规解法**：

- 每次门禁红就找人跑一次评审，等于把「日志门禁」变成「今日营业打卡」；
- 周末、假期、纯前端改动的版本，永远没有评审要跑，于是永远红；
- 更糟的是——**一旦红灯会因「今天没人用」出现，真坏了的那天也会被当成「又是没业务」放过去。**

第一点只是费事，第三点是真的会漏故障。所以本版改的是判定语义，不是补一次数据。

### 1.5 改语义 ≠ 放空门禁

改完之后必须仍然能抓住「埋点死了」这件事。所以配套两条：

1. **窗口内必须有过写入**（默认 7 天）。7 天没有任何一条日志，说明这个 writer 大概率坏了；
2. **单测证明每个 writer 的 `log_event` 调用点还在**。静态证据比「今天有没有人用」可靠得多。

`--strict-today` 保留旧语义，供 CI 或不跨日的日检使用——**严格模式不是被删掉，是被显式选择。**

## 三、为什么这么写

**为什么把窗口定成 7 天，而不是「最近一次有就行」。** 没有下界的「最近一次」等于永不报警——只要历史上写过一次，这个 writer 烂掉也看不出来。7 天覆盖一个正常使用周期，既不误报周末，又能在埋点真死掉时于一周内露头。**门禁的价值在它的下界，不在它的上界。**

**为什么坚持 `retrieve`/`scoring`/`review`/`importing` 不挪进豁免名单。** 豁免的意思是「这个模块可以永远不写」，窗口的意思是「这个模块可以几天不写」。前者会让真正的埋点损坏永久隐形，后者只延长了观察期。**同样是变绿，一个改的是观察窗口，一个改的是观察对象。**

**为什么非要加一条静态证据。** 放宽窗口之后，「窗口内有日志」有可能来自三个月前的一次运行。静态检查「每个 writer 至少有一个 `log_event(` 调用点」，把「历史上有过」和「代码里还有埋点」区分开——两者都需要，缺一个门禁就有盲区。

**为什么允许 `--strict-today` 继续红。** 它是显式选择的严格模式，红得正当。删掉它才是删判据；留着它、并如实记录它今天为红，说明我们没有把严格当默认再偷偷放松。**一个门禁可以有不适用于日常的模式，但不能有不适用的日子。**

**为什么这一版不改任何产品代码。** P20 的八模块、接口、权限全都验过了，卡住的是度量工具自身的缺陷。这时候去动产品只为迁就工具，是本末倒置。**工具错了修工具，别让被测对象为尺子让路。**
