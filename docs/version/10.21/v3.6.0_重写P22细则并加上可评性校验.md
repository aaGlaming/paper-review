### 1.2 P22 的现状：一行描述 + 一个会静默降级的入口

`Phase-3-plan.md:482` 现在写的是（2026-10-21 二次修正版）：

> **入口校验**：校验「赛题存在且有已发布量规」，不满足返回 422；确认页显示赛题名与量规版本。**不做内容级「选错题」判定**。

而 `POST /reviews` 现在**什么都不校验**——`create_review_endpoint` 只做 `_resolve_paper_text` → `create_review` → `save_session`，`contest_id` 原样落库。

评分入口的行为更微妙：

```python
# routes.py（resume 段）
use_model = model_available() and inputs["rubric_id"] is not None
...
if inputs["rubric_id"] is None:
    change_list = []; note = NOTE_NO_CONTEST      # "未绑定赛题，无维度可评"
...
results = report_evaluation.deterministic_results(paper_text, dimensions)
```

`load_review_inputs(contest_id)` 在该题没有已发布量规时返回空 `dimensions` 与 `rubric_id=None`，而 `deterministic_results` 遍历的是 `dimensions or ()`——**空列表进、空列表出**。

所以真实行为不是"伪造一份评分"，而是**返回 HTTP 200 + `dimensions: []` + `note: "未绑定赛题，无维度可评"`**，`source` 仍是 `deterministic`。

**这比报错更难发现**：前端如果只渲染维度列表，用户看到的是一片空白；而 HTTP 200 让所有监控、日志、E2E 都认为这次请求成功了。一个 200 的空结果，比一个 422 更容易被当成"页面出 bug"而不是"赛题不可评"。

这才是 P22 要堵的口子。**"选错题"判不出来可以承认，但"不可评却返回成功"不能接受。**

### 1.3 一个硬约束：空 `contest_id` 必须继续允许

| 事实 | 值 |
|---|---|
| `review` 表中 `contest_id=''` 的记录 | **2 条** |
| 它们是谁 | `2446e390…`（smoke）与 `833f43f9…`（planting）——**承载全部 24 条产物的演示评审** |

v3.5.5 建这两条时就没带赛题（只做解析与产物，不进评分）。如果 P22 一刀切「`contest_id` 必填且可评」，这两条记录的重建路径立刻断掉，P21 的证据基础也一并失效。

所以校验必须分两层：

| 入口 | 规则 | 理由 |
|---|---|---|
| `POST /reviews`（创建） | **给了非空 `contest_id` 但不可评 → 422**；**空值允许** | 尽早失败体验好；但解析/产物这类不评分的用途必须能建 |
| `POST /reviews/{id}/resume`（评分） | **无可用量规 → 422，且不产出任何档位** | 评分必须有量规；堵掉 1.2 那个静默降级 |

## 三、为什么这么写

**为什么本版第一件事仍是写细则。** P22 的任务表早随旧计划删掉了，现在只剩一行"校验可评性"。而"可评"这三个字至少牵涉三张表、一个 fallback 分支和一个前端按钮——不写成契约，实现方只能各自理解。**一行摘要能表达意图，表达不了边界；边界不清的功能，实现出来一定和验收对不上。**

**为什么校验要分软硬两层。** 创建时严格到"必须可评"，会顺手废掉两条演示评审——它们本来就不评分，只做解析与产物。而 resume 时宽松到"没量规也能跑"，就是现在这个静默降级的洞。**同一个概念（可评）在两个入口的后果不同：创建时它影响能不能用，评分时它影响给出的东西是不是真的。**

**为什么把"200 的空结果"列为要堵的核心。** 用户选了没量规的赛题，接口返回 200、`dimensions: []`、一句 note，然后前端渲染出一片空白。所有监控都认为请求成功了，用户以为是页面坏了，而真正的原因是这道题不可评。**422 至少会让人去查，200 只会让人重试。** P22 的价值不在于"判断选错题"，而在于**不再把"没评"伪装成"评完了"**。

**为什么空赛题必须保。** 库里有 2 条 `contest_id=''` 的记录，正是 24 条产物的载体。一刀切拒绝空值，等于为了堵一个洞，把 P21 的证据基础一起埋了。**收紧校验之前先看数据里有没有合法的例外——有的话，那不是漏洞，是用法。**

**为什么前端要先禁用按钮。** 后端 422 是兜底，不是交互。用户点了"开始评分"、等两秒、收到一句"没有量规"，这三步里每一步都在浪费信任。**能在点之前说清楚的事，不要留到点之后再说。**

**为什么不许把 422 改成 400。** 请求格式完全合法：JSON 对、字段齐、类型对。问题出在语义上——你指定的题在这套系统里不可评。这是 422 的标准用法。**状态码混用不会立刻出错，只会让前端的错误处理逐渐失准。**
