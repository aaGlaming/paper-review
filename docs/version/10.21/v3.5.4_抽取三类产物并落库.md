| 事实 | 值 |
|---|---|
| `data/samples/*.md` | 13 篇 |
| 其中真实论文 | **10 篇**：`cumcm-2024-A-{a016,a053,a163,a178,a242}`、`cumcm-2024-C-{c038,c063,c094,c234}`、`cumcm-2025-A-a196` |

所以「PDF 只上传一次」在工程上的落点很干脆：**`data/samples/*.md` 就是输入，产物抽取只面向这份 Markdown 文本**，既不需要回填历史，也不需要坐标映射——因为 OCR 已经在上游一次性完成了。

### 1.3 两处现在必须更正的谎

`routes.py:445/447` 的 415 文案里写着「pdf 将在 v3.5.3 支持」，`Phase-3-P21-plan.md §2.1` 也把 pdf 列进输入契约。既然不做在线解析，这两处就是**在承诺一个永远不会来的功能**——比没有文档更糟。本版一并改掉。

### 1.4 一个不能碰的约束

`build_review_graph` 的图是四节点线性 `parse → confirm → retrieve → score`，且 `backend/tests/graph/test_interrupt.py` 锁死这条链路。**产物抽取不许加节点**。它应该发生在 API 层：章节确认之后、进入评分之前——或者更保守，做成一个显式端点。

## 三、为什么这么写

**为什么产出物抽取完全不调模型。** 产物要满足「父块连续子串」级别的定位要求：`paper_text[start:end]` 必须逐字等于这条产物。模型生成的句子再像原文，也可能差一个标点、换一个同义词，而偏移一旦对不上，P22 对齐和前端高亮全部失效。**这一层的价值是「可定位」，不是「判断得准」；判断得准属于评分环节。**

**为什么 claim 的规则要写得这么窄。** 「主张」是最容易被做松的一类：放宽一点，整篇论文每句话都能算主张，产物表里塞进几百条噪声，下游评分反而更糊涂。给「含数字或结果语义词、句长 10–300、每节最多 5 条」这些硬边界，是为了让抽取结果**稳定且可复现**，而不是追求召回率。**先要一个能用的窄定义，再谈扩召回。**

**为什么幂等要用「先删后写」而不是「增量对比」。** 增量对比要先判断「这条是不是上次那条」，而产物没有稳定业务主键，只能靠文本比对；文本一改（重新确认章节），增量逻辑就开始制造重复。删掉重写在一张几百行的表上是毫秒级的事，换来的确定性远超成本。**能用「重算」解决的事，不要用「对齐」解决。**

**为什么明确不许改评分图。** 图是四节点线性且被测试锁死，产物抽取插进去会让「解析失败」变成「评分失败」——两个后果的严重程度完全不同。做成显式端点，用户能看见它失败了、能重试；塞进图里，只会看到整次评分没有结果。**把可能失败的新东西放在主干之外。**

**为什么 pdf 的承诺必须现在改掉。** 一行文案写着「v3.5.3 支持 pdf」，而 v3.5.3 已经取消——这行字会在半年后仍然指着一条不存在的路。文档里最贵的不是空白，是**看起来权威的过期承诺**。
