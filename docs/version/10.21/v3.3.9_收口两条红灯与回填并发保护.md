### 失败 2 不是偶发，是排序本身不确定

```python
# backend/app/chat/store.py
def load_messages(...):
    .order_by(ChatMessage.created_at.asc(), ChatMessage.message_id.asc())
```

`message_id` 是 `uuid.uuid4().hex`——**随机**。测试在同一个事务里连写两条，`created_at` 落同一秒（MySQL 上 `chat_message.created_at` 是 `DATETIME`，精度就是秒），次级排序键是随机 uuid，于是「second, first」还是「first, second」各占一半。单跑 20 次大约一半绿。

生产上的后果比测试更明显：一轮问答里 user 与 assistant 是同一秒写入，刷新历史可能把回答排在问题前面——P19 判据 5 说「刷新后历史仍在」，顺序颠倒在用户眼里就是「对话乱了」。

而 `chat_routes.py:183` 已经有一行补丁：

```python
assistant_message.created_at = max(
    assistant_message.created_at, user_message.created_at + timedelta(seconds=1)
)
```

**它在改数据来掩盖排序缺陷**，而且只救了「一轮问答」这一种场景，`append_message` 的任何其他调用方仍然踩坑。本版把顺序做进结构，然后删掉这行。

## 三、为什么这么写

**为什么两条红灯一条都不能留到 P20。** 门禁的意义是「从现在起每加一个功能，前面的都对」。留着一条随机失败的用例，后面每次红灯都要先判断「是新的还是那条老的」——判断成本一旦出现，红灯就不再有人认真看。**红着的门禁等于没有门禁。**

**为什么红灯 1 要「补齐字段」而不是「改成子集断言」。** 整对象相等断言的价值恰恰在于它会因为**多了字段**而失败——这是它在保护「接口形状没有意外变化」。新字段是有意的，就把期望值改成有意的；改成 `["counts"]` 这种局部断言，等于把这条用例降级成「只关心一个键」，以后真丢字段也发现不了。**判据只有一句：改完是更严还是更松。**

**为什么消息顺序必须加 `seq`，而不是「再补一个秒」或「加 sleep」。** 时间戳精度是秒，同一秒内多条消息是**正常业务**（一轮问答两条、用户连发三条）。把补偿写在 `chat_routes` 里，只覆盖了「一轮问答」这一条路径，`append_message` 的其它调用方照样乱；而 `seq` 是写入时确定的、与时钟无关的序号，谁调都不会乱。**能靠结构解决的，不要靠时钟和 sleep。**

**为什么 `seq` 不加唯一键。** 加了唯一键，两个并发 append 从「顺序可能不对」变成「其中一个直接 500」。顺序不对是可恢复的小问题，写入失败不是。**约束要加在真正能保证它的地方。**

**为什么删掉那行 `timedelta` 补偿。** 它与 `seq` 并存时，两套排序依据同时存在：`created_at` 被人工改过、`seq` 是真实的写入顺序，数据自相矛盾。以后有人查「这条消息为什么时间比下一条晚 1 秒」会查到一段没人记得的旧补丁。**一个机制只能有一个真相来源。**

**为什么 P4 强调「单进程顺序」这四个字。** 上一轮不是脚本坏了，是取证方式坏了：两个进程同时跑，增量是两者之和，`EXIT=1` 也说不清是并发崩的还是脚本逻辑错。**取证方式和被测对象一样重要**——同一个数字，用错方法测出来就是假的。

**为什么专门去改 `progress` 的「### 状态」。** 那段文本是 v3.3.6 的，却躺在 v3.3.8 章节里说「单条详情未命中」。执行方读进度记录只看末尾状态段的话，会得出与验收报告相反的结论。**文档里最危险的不是空白，是过期的、看起来权威的结论。**
