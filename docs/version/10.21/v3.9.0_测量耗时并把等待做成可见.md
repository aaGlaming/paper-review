### 1.2 八条 E2E 红的真实成因，已经查到行

八条全部停在 `confirmed-card` 可见性等待 5000 ms（默认值）。而 `confirmed-card` 只在 `resumeReview()` **返回之后**才渲染：

```
论文解析.vue:258   phase.value = 'running'
论文解析.vue:260   const confirmed = await resumeReview(...)   ← 25～40 s 都在这一行
论文解析.vue:267   phase.value = 'done'                        ← confirmed-card 这时才出现
```

也就是说，**5 秒断言测的不是"对不对"，而是"够不够快"**。而"够不够快"这件事，`§8.1` 已经把判据撤掉了（3 分钟验收不再恢复）。

八条里 **8 处**是正向等待（`toBeVisible()` 无 timeout，一测一处，刚好对上八条失败），另有 **1 处负向断言**（`parse.spec.ts:34` 的 `toHaveCount(0)`——这条必须保持短，它测的是"确认前不该出现"）。

八处正向等待的准确位置（已逐个核到行）：`consistency.spec.ts:15`、`parse.spec.ts:39`、`parse.spec.ts:83`、`scoring.spec.ts:22`、`sketch-fix.spec.ts:13`、`sketch-fix.spec.ts:43`、`suggestions.spec.ts:14`、`visual.spec.ts:33`。其中 `parse.spec.ts` 的两处写的是 `await expect(card).toBeVisible()`（先取了 `const card = page.getByTestId('confirmed-card')`），改的时候别漏掉这种变量形式。

### 1.3 本版的三件事，边界很清楚

1. **测一次真实的**：3 次完整 resume，记 wall time、走的是模型还是确定性路径、`chat_calls`。这类数字现在的版本里全是"历史值"（`report-V3.md:109-118` 的 23.4 s 平均 / 36.6 s 最大、v3.6.0 的确定性 7,284 ms），**没有一个属于当前代码**。
2. **把等待做成可见的**：`StageTracker` 现在 `running` 态只有一句"中间态看不见"。加一个**已等待秒数**和一个超阈值提示——**这是测出来的事实，不是假进度**，与本项目"禁止用定时器伪造进度"的纪律不冲突（伪造的是"点亮了第几步"，不是"过了几秒"）。
3. **给八条一个结论**：改等待策略 + 真跑一次，逐条署名。**这是第七次机会，不许再写"移交 P25"。**

### 1.4 一个必须防的滑坡

改了 timeout 之后，八条会三种结果：全绿（纯超时问题）、部分绿（还混着真缺陷）、仍全红（另有原因）。**三种都要如实写**。最容易犯的错是：看到"改完绿了"就收工，不去问"绿了是因为它真的对了，还是因为我等得够久"。所以本版要求——**绿了之后要抽查一条，确认它断言的内容没被等待时间掩盖**（例如冲突条数仍 ≥1、412 s / 386 s 仍在页面上）。

## 三、为什么这么设计

**基线必须是当前代码的，不能是历史值。** 项目里关于"评审要多久"的数字全部来自别的版本：`report-V3.md` 的 23.4 s 是 Phase-2 的十篇样本、7,284 ms 是 v3.6.0 的确定性路径。**拿历史值当基线，等于用一个已经不存在的系统给现在的系统定标尺。** 所以本版第一件事是测三次，且必须标注路径来源——模型和确定性相差一个数量级，混成一个数就没有意义。

**允许计时器，但要说清允许的是哪一种。** `StageTracker` 里那句"不用定时器假装进度"是项目的一条硬纪律，写得很好。但**"已等待 12 秒"不是进度**，它是实测值。如果不把这条边界在代码注释里写清楚，下一个人很可能会照着纪律把计时器一起删掉——**好纪律被误用的方式，通常不是被违反，而是被扩大解释。**

**八条 E2E 的处置要防"等得够久"这个陷阱。** 把 timeout 从 5 s 抬到 60 s，八条大概率会绿。但"绿了"有两种：一种是本来就对、只是慢；另一种是断言本身依赖时序，等久了就永远成立。所以本版强制**抽查一条看业务内容**——冲突条数、`412 s` / `386 s`、不出现「总分 0」。这一步花两分钟，能挡住一整类假绿。

**负向断言必须保持短。** `parse.spec.ts:34` 的 `toHaveCount(0)` 测的是"确认前不该出现卡片"。给它 60 s，等于让它在 60 s 内一直等到出现为止，**断言方向整个反了**。这类"统一改超时"的操作最容易顺手把负向断言一起改掉。

**本版是 P25，所以"移交 P25"这句话不能再出现。** 前六版一直写"八条移交 P25"，现在到了 P25 自己，如果还写"移交"，那这笔账就永远在纸上。报告里只允许三种词：已修、改等待策略、书面豁免。
