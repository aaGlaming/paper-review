## 一、这条红灯的来历，值得单独写一段

### 1.1 现在错在哪

`frontend/tests/e2e/sketch-fix.spec.ts:65`「`/eval`：三张指标卡的折线 path 互不相同」，第 72 行对三张卡逐一断言 `toHaveCount(1)`，而 `insufficient_evidence_hit` 实际是 **0 条**。

接口实测：

```
band_agreement            26/60  low_sample=false
quote_exact_match         60/60  low_sample=false
insufficient_evidence_hit  0/2  low_sample=true   ← 按契约不画线
```

### 1.2 它为什么躲了六个版本

**一、后端从 `v3.7.2` 起就没重启过。** `v3.7.2` 给 `evaluation.py` 加了 `low_sample`，而 8077 上的 PID 12232 从 P23 一路写到 P25 都是「运行中，PID 12232」。字段从未出现在响应里，前端拿到 `undefined` 当 false，照常画线——**这条用例一直在测旧代码**。

v3.10.1 重启（新 PID 20356）后字段第一次生效，它立刻红了。**这是正确的红灯，只是迟到了六版。**

**二、同名双胞胎只改了一个。** `tests/unit/sketch-fix.spec.ts` 在 v3.7.2 已把 fixture 改成 `2/5`（非小样本），`tests/e2e/sketch-fix.spec.ts` 那份漏改。同一个文件名、两个目录，改的人只看了 unit 那份。

### 1.3 所以修的是断言，不是产品

`low_sample` 时「不画折线、显示样本过少」是 `v3.7.2` 明确决策的结果（`LOW_SAMPLE_THRESHOLD = 5`）。**为了这条用例变绿去改 `MetricCard.vue`，等于把那条决策推翻。** 反过来，把断言改成「两张有线的卡路径不同、第三张没有线且写明样本过少」，既保住了这条用例原有的意图（三条线视觉上不能重合），也保住了新契约。

### 1.4 顺手加一道防"旧进程"的闸

这次假绿的根子是「进程旧」无法从外部看出来。加一条最便宜的检查：在那条用例里先断言 `/api/eval/summary` 每项都带布尔型 `low_sample` 字段——**字段缺失就报"后端进程未加载新代码"，而不是报"折线数量不对"。** 一个字段的 schema 断言，能换来以后不再被同一个问题骗一次。

## 三、为什么这么设计

**断言按字段决定，不按顺序决定。** 原用例写死"三张卡都要有线"，等于把 `low_sample` 的当前取值（0/2）烧进了断言。改成"`low_sample=false` 的画线、`low_sample=true` 的不画线"之后，**将来 gold 补到 5 条以上、这张卡恢复画线，用例自己就跟着变**，不需要再改一次。

**加一道"字段在不在"的断言，是这次最便宜的收益。** 六版假绿的根子是「进程旧」看不出来。`typeof low_sample === 'boolean'` 一行断言，就能把"我测的是旧代码"变成一条明确的报错文案——**比在报告里写一百遍"记得重启"有用。**

**报告里必须留「契约变更审计」这一节。** 契约变更是正常的，同步漏改也是正常的；不正常的是**没人记录它，于是六个版本后一条落后的断言突然出现，看起来像新 bug**。这一节的价值不在解释过去，而在下一次契约变更时有人会想起"同名双胞胎还有一份"。

**不改产品。** 产品那边的行为（不画线 + 写样本过少）是 `v3.7.2` 的明确决策，理由写在当日 findings 里：分母 2 的折线会把噪声渲染成趋势。**验收阶段最忌讳的就是为了让数字好看去推翻一条有理由的产品决策。**
