### 1.2 红灯的真因：我把度量范围写错了

v3.4.0 提示词里我写的是「记 `dist/assets/*.js` 的 raw 与 gzip **总量**」，执行方照做，于是把懒加载的大屏 chunk 也算进了增量。实际分块是这样：

| 文件 | raw | gzip | 是否被 `index.html` 引用 |
|---|---:|---:|---|
| `index-BPiwm0nn.js` | 1117.18 KB | 351.36 KB | **是**（唯一一个） |
| `数据大屏-DCNK5oUO.js` | 533.12 KB | 174.92 KB | **否** |

而路由本来就是懒加载：

```ts
{ path: '/dashboard', name: 'dashboard', component: () => import('../views/数据大屏.vue') }
```

对基线（1115.14 KB / 354.95 KB）算增量：

| 口径 | raw 增量 | gzip 增量 | 结论 |
|---|---:|---:|---|
| 只算首屏入口 chunk | **+2.04 KB** | **−3.59 KB** | 通过 |
| 所有 chunk 求和（v3.4.0 用的） | +535.16 KB | +178.18 KB | 判红 |

**一个首屏只涨 2 KB 的实现被判了红，因为判据没写清量什么。** 这不是执行方理解错，是我没定义。

### 1.3 判据原文与它的动机

计划里三处相关：

- §7.1：「`echarts@5` **按需引入**，不整包——**首期** Element Plus 全量引入已让 bundle 到 1 MB，不能再涨」
- §7.2：「**首屏**加载 ≤ 2 秒（聚合接口加缓存，60 秒 TTL）」
- §7.4：「echarts 按需引入，`npm run build` 的 bundle 增量 ≤ 400 KB（gzip 后 ≤ 120 KB）」

三句连起来读，担心的对象是**首屏**：用户打开系统那一下不能变慢。`/dashboard` 是需要教师权限的二级页面，进它才加载 533 KB，与「首屏变慢」无关。

所以本版裁决：**判据适用于「首屏入口 chunk」，大屏 chunk 单独记录、不进增量；同时补一条更严的实测——非大屏页面首屏实际加载的 JS 字节数不得超过基线 + 10 KB。** 后者可被 Playwright 直接量出来，比「chunk 求和」更难糊弄。

**同时保留 Plan B**：如果坚持「所有 chunk 求和 ≤ 400 KB」，唯一出路是把饼图与仪表盘改手绘 SVG（项目本来就有一套手绘风格插画）、只留折线 + 条形，重测后再收口。走哪条由你定，**但不许改 400 这个数字**。

### 1.4 顺带发现：两条会随机变红的鉴权用例

v3.4.0 里 `test_tampered_signature_rejected` 失败过一次。看代码就明白，它替换的是**第一位**，却拿**末位**做判断：

```python
# backend/tests/auth/test_auth.py:148
tampered = f"{head}.{body}.{'A' if sig[-1] != 'A' else 'B'}{sig[1:]}"
#                          ↑ 比末位                    ↑ 写首位

# backend/tests/api/test_auth_required.py:173 —— 同一处错位
altered = f"{head}.{body}.{'A' if signature[-1] != 'A' else 'B'}{signature[1:]}"
```

只要 `sig[0]` 恰好等于选中的字符，token 就没被改动，401 自然不出现。这与 v3.3.9 那次 `test_tampered_token_has_same_401_message` 的偶发失败是**同一个 bug**，当时被记成「随机」，其实有确定修法。

## 三、为什么这么写

**为什么先裁度量范围，而不是先让它把 533 KB 压下去。** 判据没定义量什么，就等于没定义判据；在这种情况下让执行方去优化，优化出来的东西跟判据没有因果关系——压到 400 也可能只是把某个 chunk 改名换位。**先把尺子定好，再谈够不够长。** 而这次的数字很直白：入口涨 2 KB、gzip 反而降 3.6 KB，首屏没变慢，判红纯属量错。

**为什么裁完还要加一条更严的「首屏实际字节」。** 单说「只算入口 chunk」，会开一个后门：把公共依赖挪进懒加载 chunk、再把大屏 chunk 拆碎，入口数字就永远好看。用 Playwright 数 `/parse` 首屏真实加载的 JS 字节，堵的正是这个后门。**放宽口径的同时收紧观测，才算真的放宽。**

**为什么 Plan B 是「改手绘」而不是「把 400 改成 600」。** 改数字是把问题从判据里删掉，改实现是把问题解决掉。项目本来就有一套手绘 SVG 插画（`components/illustrations/`），饼图和仪表盘改手绘完全可行，风格还更统一。**能靠实现解决的事，不要靠改标准解决。**

**为什么顺手修那两条用例。** 它们每次随机变红，成本不是那一次失败，是接下来每次红灯都要先判断「是新的还是那两条老的」——判断成本一出现，红灯就没人认真看了。而且这次的根因非常明确：**比的是末位、改的是首位**，两行代码的事。**偶然失败的测试比失败的测试更贵，因为它教会所有人忽略红灯。**

**为什么允许「本版不瘦身」。** 八模块是计划 §7.2 的需求，为了一个被量错的指标去砍需求，是本末倒置。真要瘦，应该在新版本里以「性能优化」为目标单独做，而不是混在验收版里偷工减料。**需求与指标冲突时，先确认指标是不是量错了。**
