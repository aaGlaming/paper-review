### 1.4 这条证据改变了三件事

**第一，崩溃不在脚本里。** `scripts/index_review_records.py` 第 174–175 行是 `collection = get_collection(client)` → `before = collection.count()`，**这行在写库之前**。两次正式回填的 stdout 只有接管锁那一行、没有 `collection_count_before=`，说明它们**崩在读 count 的那一秒，从未写入任何东西**。生产库文件 mtime 停在 10-20 18:52，与这个判断一致。

这是唯一的好消息：**库没被写坏，因为它根本没被写。**

**第二，「替换成 SQLite 行数」这类做法彻底出局。** 上一版已禁止拿 sqlite 行数冒充 `collection count`；现在还能补一句更强的理由：`count()` 本身就是崩溃点，任何以它为判据的取证都会把进程打死。

**第三，`381 passed` 证明不了生产库可用。** 测试用的是隔离小库（几百条以内），空库探针也是绿的。崩溃只在**这份 24519 条的索引**上出现。测试通过率衡量的是代码逻辑，不衡量这个 107 MB 二进制文件能不能被这个版本的 Rust 绑定读出来。这两件事以前被混为一谈。

还有一条必须写进 `progress` 的风险，而不是当成「取证瑕疵」：**P19 的定点问答走 MySQL（`load_record_blocks`），不受影响；但 P12 的逐维检索要向量，若库不可读，模型档评审会全维「证据不足」而不会报错。** 这是静默降级，比崩掉更难发现。

### 1.5 冲突的原文在哪

`v3.3.9` 纪律第 1 条：「只允许 P4 的索引回填写入 Chroma 与 `paper_parent`；其它 SQL 一律只读。」
`v3.3.9` P2 第 2 步：「`create_chat_schema` 补列……真实库里有 21+ 条历史行，ALTER 后它们的 `seq` 都是 0。」

**一条要求写 `chat_message`，一条禁止写 `chat_message`。** 执行方停下来问是对的——按前者做是违规，按后者做是没完成。代价是整版空转。本版第一节就要把这件事裁掉。

### 1.6 第二次空转：P0 判红的 3306 是误判

执行方报「MySQL 3306 未检测到 LISTENING」并停版，未执行 P1 及后续。我在同一时点前后复核了三种方法，结论相反：

**MySQL 从未停止。** 报告里没有附命令与原始输出，所以无法断定是命令写法差异（`findstr` 与 `Select-String` 的正则不同、把 `127.0.0.1:3306` 当唯一判据、在服务刚起来的窗口里探测）还是时点问题——但根子不在执行方：**我上一版写的闸门是「netstat 3306 LISTENING」这种半句话，既没给可复制命令，也没要求原始输出。** 闸门写得含糊，执行方只能用自己的写法，红了绿了都不可复核。

这是本版第二次把整版时间花在「确认环境到底有没有问题」上（上一次是 Chroma）。修法三条，已落进 P0：

1. 三类判据（socket / 端口表 / 进程名）各给可复制命令，**至少两条互证**才允许下结论；

## 三、为什么这么写

**为什么权限冲突必须先裁，而不是让执行方自己找个折中。** 规则自相矛盾时，执行方的两个选项都是错的：按 P2 做是违反纪律，不按 P2 做是没完成任务。停下来报告已经是正确行为，代价是整版空转——所以这一节的成本是上版留下的，本版只能先付掉。**修法是把「允许写什么」写成白名单，而不是继续写「除 X 外一律只读」**：前者可判定，后者每加一个功能就要重新解释一次。

**为什么所有探针都在副本上。** 生产目录是唯一数据源，而 `0xC0000005` 是进程级内存访问违规——它可能在崩之前已经把 107 MB 的段文件写到一半。第二次崩溃已经发生过一次，说明这不是偶发噪声。**能复现的问题不该在原件上复现。**

**为什么「count 崩」比「脚本崩」严重一档。** 脚本崩可以读脚本；`count()` 是库里最小的读操作，它崩说明失败发生在 Python 之下的原生层，读源码读不出来。而且它顺带废掉了过去所有以它为判据的取证路线——包括「用 sqlite 行数代替」这种本来就不该用的替代。**当唯一的度量工具自己坏了，第一件事是换工具，不是反复按它。**

**为什么探针 1（空库）不能跳。** 没有它，就分不清「这份数据坏了」和「这个绑定在这台机器上坏了」，而两者的修法完全相反：前者重建数据，后者换版本。**一个对照组能省掉后面所有的猜测。** 这次的对照组恰好全绿，才敢说「坏的是这份索引」。

**为什么给重建开一条路，而不是死等修复。** `0xC0000005` 在 Rust 扩展里，本项目既没有符号也没有源码去修它。能做的只有三件事：隔离、重建、验证后切换。旧目录只改名不删除，是为了在重建失败时能一键退回——**可回滚的重建才算方案，不可回滚的重建只是赌。**

**为什么坚持「不许把弱证据写成通过」。** `sqlite` 里有 24519 行，只能证明「曾经写进去过」；能不能检索是另一件事。把前者当后者用，就是 v3.3.7 那个失败形态的翻版：refs 可点、格式正确、唯一错在指的不是被问的那条。**证据要标明它能证明到哪一步，越界的部分比没有更危险。**

**为什么本版强制交代后端最终状态。** 上一版以「后端保持停止」收尾，于是这一版的第一件事是先考古：它到底停在哪一步、有没有残留锁、数据库连接是不是干净。**每版留一个悬空状态，下一版就得多花半小时确认它是死是活。**

**为什么闸门必须写成「可复制命令 + 原始输出」，而不是「3306 要有监听」。** 这种半句话把判据留在了后者脑子里：用什么命令、怎么算命中、空输出代表什么，全凭执行方自己发挥。于是「一条命令没输出」被读成「环境坏了」，整版停摆，而真实情况是服务好好的。**闸门的可观测性不是给执行方的额外要求，是写闸门的人欠下的债**——判据写不清，红绿就都不可复核。所以本版改成三法互证 + 环境自愈，把「停下」从默认反应改成最后一个选项。

**为什么环境类闸门要自愈，口径类闸门不许自愈。** MySQL 没起有确定修法（`net start` 或 `mysqld --defaults-file`，本机 `StartType=Manual` 是已知坑），拉起来就完事；而「测试数不是 381」意味着代码或文档已经和预期脱节，那种情况强行往下走只会把错误放大。**能修的修，不能修的问，这两类混在一个闸门里就会两头都做错。**
