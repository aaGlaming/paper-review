### 1.2 出口是什么：一个本地代理，而它才是嫌疑人

`.env` 走的是公网域名，但进程里有代理变量：

```
HTTP_PROXY  = http://127.0.0.1:22860
HTTPS_PROXY = http://127.0.0.1:22860
```

DNS 把 `api.siliconflow.cn` / `api.deepseek.com` 解析到 `198.18.0.x`（TUN 代理的 fake-ip 段）。也就是说：**应用 → 127.0.0.1:22860 → 上游**。代理一停，所有模型调用同时死，与模型服务商本身无关。

我在 13:50 前后实测（当时链路正常）：

| 探针 | 结果 |
|---|---|
| 代理端口 `127.0.0.1:22860` TCP，15 次 | **15/15 成功**，均值 0.016 s |
| `GET https://api.siliconflow.cn/`，10 次 | **10/10 返回 404**，0.11–0.21 s |
| `client.embed(["ping"])`，3 次 | **3/3 成功**，1024 维 |

所以现在是好的。问题是**它不总是好的**，而三轮取证都没有在失败的那一刻记录出口状态。

### 1.3 三种失败形态，指向同一个嫌疑人

| 场景 | 现象 | 耗时 | 读数 |
|---|---|---|---|
| v3.3.12 哨兵 | `WinError 10061` 积极拒绝 | 瞬时 | 代理端口**没在监听** |
| v3.3.12 P2 ×2 | `both_attempts_failed` | 8.6 / 8.5 s | 两次尝试各约 4 s，**挂起**而非拒绝 |
| v3.3.12 P3 | 500，`http_status=null` | 4.4 s | 同上 |
| v3.3.11 P2 ×2 | `http_status=null` | 2.1 s | 更早的同类形态 |

「拒绝」和「挂起」是两种不同的故障，但它们同时出现在 `chat` 与 `embed` 上、同时消失又同时恢复——**同一时刻全链路一起坏，只能是出口，不是某个模型**。这一条要写进 progress，否则下一轮还会有人去查 API key。

### 1.4 E2E 的 8 条不是 8 笔债，是 7 个症状 + 1 条过期断言

八条失败的 assertion 原文都是 `getByTestId('confirmed-card') not found`，而同期 `POST /api/reviews/{id}/resume` 返回 500、`llm` 日志 `http_status=null`。也就是说：**它们根本没走到各自要测的东西**，是被同一个出口故障提前掐断的。

唯一例外是 parse 那条：`Expected: 3; Received: 10`——样例列表已从 3 扩到 10，这是一条**真的过期断言**，与网络无关。

所以网络一稳，7 条应当自然转绿；剩下 1 条需要改断言（按接口数据校验，而不是写死 3）。这也是为什么要先修出口再谈视觉基线：**在断掉的链路上判断「圆画歪了」，判断不了。**

### 1.5 还有一笔时间账

v3.3.10 到 v3.3.12，每一版都为同一件事多花了一轮：沙箱里先跑一遍（`unable to open database file` / `spawn EPERM`），提权后再跑一遍。v3.3.12 的 P6 里 pytest、build、vitest 三条全部是「沙箱失败 → 提权成功」。**本版直接从提权开始，别再交这个学费。**

## 三、为什么这么写

**为什么先写采样器，而不是再试一次问答。** 前三轮的失败都发生在「请求发出到收到响应」这一段，而这段时间里我们唯一没记录的就是出口状态。没有这份时间线，任何归因都是猜：说是模型服务商挂了，可十分钟后它自己好了；说是代码 bug，可测试全绿。**采样器把「猜」换成了「对表」——请求失败的时刻，出口是不是也在失败，一看就知道。**

**为什么区分「拒绝」和「挂起」。** `WinError 10061` 是代理端口没人听，4 秒挂起是代理连上了但上游不回。前者是代理进程死了，后者是代理活着但链路堵了，处置方式不同（重启进程 vs 换节点/换线路）。把它们都叫「网络不好」，等于放弃诊断。

**为什么 P2 要「先 3 连通再发请求，最多 3 次」。** 无脑重试的问题不是次数，而是**不知道重试的是什么**。带前置检查的重试，每次都有一次「当时出口确实通」的旁证；连着三次「前置通、请求挂」，那结论就不是网络抖，而是请求路径本身有问题。**重试必须带条件，否则只是把不确定性摊平。**

**为什么 E2E 这次要用「预期剩 1 条」来验证假设。** 前两版把 8 条当 8 笔债逐条定性，花了整整一版。如果它们真是同一个故障的传染症状，那么网络一好就该批量转绿——这个预测可被证伪：要么只剩 1 条，要么说明还有别的坑。**把假设写成可验证的预期，比写一段「疑似」有用得多。**

**为什么 parse 那条不许把 3 改成 10。** 写死数字的断言，本质上是在测试「样例不会变」。样例本来就该变。改成按接口数量校验之后，这条用例测的才是「页面渲染出的数量等于接口给的数量」，那才是它想守的东西。**测试写死了实现细节，就是给自己埋雷。**

**为什么直接提权。** 三版、三次、每版一轮：沙箱先红，提权再绿。这不是严谨，是把同一个已知结论重新验证三遍。**已知的假红灯不该每次都重放一遍。**

3. 空态由组件判定，接口 0 条返回 `200` + 空数组。
4. bundle 增量 ≤ 400 KB，`echarts/core` 按需注册。
5. 大屏只从 MySQL 取数，不依赖 Chroma。
