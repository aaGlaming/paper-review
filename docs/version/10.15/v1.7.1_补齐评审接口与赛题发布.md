### 1.1 缺口一：赛题只有一道，且是 draft

| 项 | 现状 | 总验收要求 |
|---|---|---|
| 入库赛题 | 1 道（`cumcm-2024-A`，`draft`） | **三道可选**，即三道均 `published` |
| 对应的量规 | 1 条（`cumcm-2024-A-v1`，`draft`） | 各自 `published` |
| 磁盘上的数据包 | `data/contests/` 下**四道**：`cumcm-2024-A`、`cumcm-2024-C`、`cumcm-2025-A`、`fixture-extra` | 前三道入库；**`fixture-extra` 不入** |

**这不属于代码缺陷，是数据装载没做。** 用已冻结的现有接口就能完成，**不需要改任何代码**：

- 导入：`POST /api/imports`，体为 `{"package_dir": "data/contests/<id>"}`
- 发布：`POST /api/contests/<id>/publish`
- 核对：`GET /api/contests`（默认只返回 `published`）

**顺序不能颠倒**（实测 `catalog.py:388` 的 `_write_package`）：它**总是**把量规建成 `status="draft"`，并且会**先删掉该赛题已有的全部量规与维度再重建**。所以必须**先导入三道、再统一发布三道**。反过来做，已发布状态会被打回 `draft`。

### 1.2 缺口二：两条冻结接口未实现，链路断在 `save_review` 无调用方

执行手册第 141～143 行冻结的评审三条路径：

| 方法 | 路径 | 实测状态 |
|---|---|---|
| POST | `/api/reviews` | **未实现**。`routes.py:4` 的模块注释白纸黑字：「不实现 `POST /api/reviews`（属后续版本）」 |
| POST | `/api/reviews/{review_id}/resume` | **未实现**，路由表里没有 |
| GET | `/api/reviews/{review_id}` | 已实现（`routes.py:59`），但只读 `review` 表 |

**为什么这是硬缺口**：`report/store.py` 已经提供了

- `save_review(review_id, *, contest_id, rubric_id, rubric_version, model_name, dimensions, session)` → 第 74 行
- `load_review(review_id, *, session)` → 第 135 行

两者逻辑完整（含「旧记录一律不回写」）。但实测调用点是这样的：

| 函数 | 应用代码里的调用方 | 事实 |
|---|---|---|
| `save_review` | **没有** | 只有 `tests/report/test_report_and_eval.py` 在调（201、282、293、304、324 行）。**没有任何接口会写入评审记录** |
| `load_review` | `routes.py:62`（`GET /api/reviews/{review_id}`） | 读的是一条永远不存在的记录 |

于是：没有写入方 → `review` 表 0 行 → `GET /api/reviews/{id}` 对任何 id 都返回 404。整条「创建 → 确认 → 评分 → 落库 → 读回」在 HTTP 层是断的。**P7 的测试之所以全绿，是因为它自己直接调 `store.save_review()` 造数据，绕开了 HTTP 这条链路。**

### 1.3 硬约束：执行手册第 27 行的「进程重启后从暂停处继续」与 `InMemorySaver` 相冲

执行手册第 27 行原文：

> 章节树由人确认后才评分。检查点按 `review_id` 保存，**进程重启后从暂停处继续**。

而 `InMemorySaver` 的检查点只在**进程内**存在。我在 `agent-task` 环境跑了独立探针，实测三条还原路径（探针已删）：

| 做法 | 实测结果 |
|---|---|
| 新进程 + 新 saver，直接 `resume_review` | **抛 `ValueError`：找不到评审单 … 的检查点，无法继续** |
| `update_state(cfg, 快照, as_node="parse")` 再 resume | **成功**。还原后 `next == ('confirm',)`、`status == '待确认'`、章节树 7 条；resume 后 `status == '完成'`、`score_node_calls == 1`、`retrieve_node_calls == 1`、**`parse_node_calls` 保持 1（没有重新解析）** |
| `update_state(cfg, 快照, as_node="confirm")` | `next == ('retrieve',)` —— **人工确认被整个跳过，直接进检索与评分**。绝不可用 |
| 用同一个 `review_id` 重新 `create_review` 再 resume | 能完成，但 `parse_node_calls` 被重置、会重解析一遍；只作兜底，须记 Ruling |

**结论**：恢复必须走 `update_state(..., as_node="parse")`，且需要把快照（`paper_text` + `sections` + 三个调用计数）落到库里。这既解决「重启后继续」，也顺带满足「已确认章节树仍可查看」——后者正是我在《项目进度报告V2》§4 里标为高优先级的那条缺口。

## 3. 为什么提示词要这么写（给你复核用）

| 约定 | 来源 | 为什么写进提示词 |
|---|---|---|
| 把「赛题装载」单列一节并声明**不改代码** | **实测**库里只有 1 道 draft | 现有接口已经够用（`POST /api/imports` + `publish`）。不点明的话，AI 很可能去写个 seed 脚本，凭空多出一套目录与代码路径，而它本可以零代码完成 |
| 固定「先导入三道、再统一发布」的顺序 | **实测** `_write_package` | 它**总是**把量规建成 `draft`，且先删光该赛题已有量规再重建。顺序颠倒会把发布状态打回 draft——而且**表面看不出错**，直到 `GET /api/contests` 少一道才发现 |
| 明令**不导入** `fixture-extra` | 需求「三道赛题可选」 | 磁盘上有四道包，顺手 `glob` 一遍就会导入四道，列表变四道，与需求不符 |
| 新接口必须走 `Depends(get_session)` | P7 已有的测试夹具 | 测试靠 `dependency_overrides[get_session]` 注入 sqlite 事务。接口里自己开 `db.session_scope()` 就绕过覆盖，**测试会打到真实 MySQL** |
| 新增 `get_graph()` 依赖 | **实测**（新 saver 直接 resume 抛错） | 「创建」和「继续」是两次请求。若各拿一个新图，第二次必找不到检查点。单例 + 可覆盖，两个需求同时满足 |
| 图导入放函数内部 | 工程判断 | `api → graph → retrieve` 会拉起向量库。放模块级会让应用启动与既有报告测试在导入期付这个代价 |
| 把三条还原路径的实测结果全列出来 | **实测** | `as_node="confirm"` 能把 `next` 变成 `('retrieve',)`——**等于绕开人工确认**，而这恰好是本项目最核心的一条约束。不写死，AI 很自然会在 `parse` / `confirm` 之间随便挑一个 |
| 明令图不可改 | P1 的 `test_interrupt.py` 不在允许范围 | 改图的缺省行为会让「未注入模型时 status == 完成」变红，而 AI 无权改那个测试文件——又是一次死锁。和 P5 那次是同一类坑，这次提前堵 |
| `GET /api/reviews/{id}` 改成两段式 | 执行手册第 27 行的应急要求 | 「重启后已确认章节树仍可查看」原本无处落。用既有路径承载，**不必新增冻结清单之外的路径** |
| 量规从**库**读、不从文件读 | 计划书 §7.2 的版本语义 | `review` 表存 `rubric_id` 与 `rubric_version`，就是为了「发布新版量规不影响旧评审单」。从文件读会让版本语义整个失效 |
| 明确标 `model_name="deterministic"` 与 `source` | `.env` 的 `LLM_*` 全空 | 和 v0.8.0 那条诚信线一脉相承：假模型跑出来的档位不许说成模型结果，写进请求记录里更是污染 |
| `review_session` 挂 `ReportBase` | `retrieve/models.py` 先例 | 建表入口只能有一个（`create_report_schema()`）。新建第二套会让测试的内存库建表漏表 |
| 测试第 7 条「行数等于量规维度真值」 | 本次判断 | 写死 5 会掩盖「维度没落库」和「落了别的赛题的维度」两种错。用真值比才有鉴别力 |
| 完成定义里「用例数不得少于 117」 | v0.5.1 的教训 | 删测试是最省事的变绿手段。给一条硬下限 |
| 「用 `git diff --stat` 自证未改两个测试文件」 | 本次判断 | 「我没改」这种话不可验证。让机器验证 |
