### Chroma 1.5.9 实测结论（本版最大的坑）

| 事项 | 实测结果 | 对本版的要求 |
|---|---|---|
| 自定义 `EmbeddingFunction` | ✅ 可用，**不会下载模型** | 测试一律用假 EF，`add`/`query` 时都显式传 `embeddings` |
| 标量元数据 + `$in` 过滤 | ✅ 正常返回 | 过滤按 `section_type` 单值做 `$in` |
| **数组元数据 + `$in` 过滤** | ⚠️ **能写入、读回是 `list`，但过滤静默返回空、不报错** | **绝不能用数组存 `section_types`**，这是"数据进去了、搜不到、还不报错"的静默失败 |
| `doc_type` 白名单 | ⚠️ Chroma **完全不校验**，`paper_parent` 也能写进去 | 白名单必须**代码自己拦** |
| 集合名规则 | 需 3–512 字符，仅 `[a-zA-Z0-9._-]`，首尾须字母数字（`'p'` 被拒） | 集合名取如 `paper_child_blocks` |
| `EmbeddingFunction` 子类 | 1.5.9 会警告 "does not implement `__init__`" | 假 EF 显式实现 `__init__` |

## 3. 为什么提示词要这么写（给你复核用）

| 约定 | 来源 | 为什么写进提示词 |
|---|---|---|
| 把 Chroma 的数组元数据陷阱写成硬规则 | **本机实测** | 数组元数据**能写入不报错**，但 `$in` 过滤静默返回空。不写死的话，实现会"看起来对、跑起来永远搜不到"，排查成本极高 |
| 明说 Chroma 不拦 doc_type 白名单 | **本机实测** | 实测 `paper_parent` 也能写进 Chroma，白名单只能代码拦。不点明，AI 很可能以为存储层会兜底 |
| 单列「表结构与修改范围冲突」 | 任务文档 §9 + 实测 | 本版需要 `paper_parent`，但允许修改范围不含 `importing/`。这是**规范内部的冲突**，不写死处置，AI 要么越界改 `importing/`，要么卡住不动 |
| 明令不得改 `importing/db.py` | 允许目录清单 | 复用引擎只读导入即可；一旦改它，就破坏了 v0.3.0 已验收的模块边界 |
| 假 EmbeddingFunction 必须显式传 embeddings | 任务文档 §9「不要为了测试去下载嵌入模型」 | Chroma 默认 EF 会下载 ONNX 模型，联网失败就整个测试挂掉；自定义 EF 实测可完全离线 |
| 留出重排位置但本版不实现 | 任务文档 §9 与 §10 分界 | 防止本版顺手把 P4 的重排做掉；同时保证"过滤先于排序"这个不可逆的顺序约束在签名上就立住 |
| 「过滤先于截断」单独成一条用例 | 需求第十二章 + 风险清单 | 这是整条检索链最容易写反的地方——先截断再过滤，就会把别的赛题的子块筛进来 |
| 返回项必须带 chunk_ids | 需求 §12.3 溯源要求 | 后续"点开原句定位到切片"要用；本版不留，P5 的引用校验就得返工 |
| 两张图必须标明父块去向 | 任务文档 §9 任务 3 | 数据流图画错（把父块画进向量库）会误导后续所有实现 |
