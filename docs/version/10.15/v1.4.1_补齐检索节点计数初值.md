## 1. 遗留问题诊断（实测）

### 1.1 现象

| 项 | 实测值 |
|---|---|
| 命令 | `python -m pytest backend/tests -q` |
| 结果 | **`1 failed, 73 passed in 4.89s`** |
| 失败用例 | `backend/tests/retrieve/test_rerank_cap.py::test_unconfirmed_sections_never_reach_retrieve_node` |
| 报错 | `KeyError: 'retrieve_node_calls'` |

### 1.2 失败用例原文

```python
def test_unconfirmed_sections_never_reach_retrieve_node():
    retriever = RecordingRetriever()
    graph = build_review_graph(retriever=retriever)
    review_id = create_review(PAPER_TEXT, graph=graph)
    config = {"configurable": {"thread_id": review_id}}

    snapshot = graph.get_state(config)
    assert snapshot.next == ("confirm",)
    assert retriever.requests == [], "未确认时不进 retrieve"
    assert snapshot.values["retrieve_node_calls"] == 0   # ← 这里 KeyError
    assert snapshot.values["score_node_calls"] == 0
```

### 1.3 根因（已定位，非推测）

`backend/app/graph/review_graph.py` 的 `create_review()` 在建初始状态时**预置了两个计数键，漏了第三个**：

| 行 | 代码 | 说明 |
|---|---|---|
| 328–339 | `resolved_graph.invoke({... "score_node_calls": 0, "parse_node_calls": 0}, config=config)` | 初始状态字典**只有这两个计数键** |
| 104 | `retrieve_node_calls: int`（`ReviewState` 声明） | 键在类型里声明了 |
| 272 | `"retrieve_node_calls": state.get("retrieve_node_calls", 0) + 1` | 节点内部会累加 |

**推断链**：图在未确认时停在 `confirm`，`retrieve` 节点从未执行 → 那个"累加"语句从未跑过 → 该键从未写入状态 → `snapshot.values["retrieve_node_calls"]` 抛 `KeyError`。

**行内反证**：紧接着的 `snapshot.values["score_node_calls"] == 0` 之所以不报错，正因它在初始状态里被预置了。**两行相邻、写法相同、结果相反——这一对照本身就是根因证明。**

**排除项**：`retriever.requests == []` 已通过，说明 retrieve 节点**确实没被调用**。所以这不是"未确认却进了检索"的功能缺陷，而是**初始状态缺一个键**的契约缺陷。

### 1.4 为什么不改测试

把断言改成 `snapshot.values.get("retrieve_node_calls", 0) == 0` 只需一个字符的改动，看起来更省事。**不要这么做**：

- `get(key, 0)` 在"键不存在"和"计数为 0"之间不加区分；
- 若某天 `retrieve` 节点被改成不累加（即计数器根本没接上），这条断言**照样通过**——它变成了一句永远为真的话；
- 这条用例存在的意义正是"证明检索节点没被执行"，一个永远为真的断言**不再证明任何事**。

正确的做法是把**缺的键补上**，让严格断言 `== 0` 读到真实值：检索节点若被误调用则累加为 1，断言立刻失败。**保留严格取值，这条测试才是活的。**

## 3. 为什么提示词要这么写（给你复核用）

| 约定 | 来源 | 为什么写进提示词 |
|---|---|---|
| 先复现再动代码 | 任务文档 §3.2 第 3 条 | 项目规矩是"先看失败、再写实现"。此处已有一处失败，更要先确认失败**原因**，否则可能按错误假设去修 |
| 把根因接到具体行号 | 本次实测 | 根因不是"某处有问题"，而是 `create_review` 的初始状态字典少一个键。写到这一层，修复就没有自由度，也就没有返工 |
| 明令禁止改测试 | 本次判断 | 一行改测试就能"变绿"。不写死的话，这是 AI 最可能走的路——**把红灯拆掉比把 bug 修掉省事得多** |
| 解释 `.get` 为什么不行 | 本次判断 | 说"不许改"不如说清"为什么"。`.get(key, 0)` 会让断言退化为永真，这条测试就死了 |
| 实现改动限定"只允许一行" | 任务文档 §3.1 补丁规则 | 补丁不得夹带下一版的功能。限定单行改动，是最容易验证的边界 |
| 台账补齐单列一节 | 任务文档 §3.2 第 7 条 | v0.5.0 的问题**有一半在台账**：`progress.md` 没有这一节、`task_plan.md` 还标「未开始」。光修代码，状态依然是错的 |
| 要求如实记 v0.5.0 为"退出码 1" | 任务文档 §3.2 第 7 条 | 项目规矩是"退出码 0 才写通过"。v0.5.0 首次确实没过，就该留失败记录——**掩盖失败史等同于丢掉调试线索** |
| 新增状态键的"只判断不扩改" | 任务文档 §3.2 第 4 条 | 顺带排查同类隐患很有价值，但顺手改掉就变成扩范围。要求"只写结论、不改代码"，两头兼顾 |
| 完成定义里要求"用例总数不少于 74" | 本次实测 | 防止通过删测试来变绿 |
