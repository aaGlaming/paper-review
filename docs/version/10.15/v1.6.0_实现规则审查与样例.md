### 1.2 动手前必须知道的：两个误报陷阱

**陷阱一：「同单位即冲突」是错的。**
烟幕样例里 `1.5 s`（投放）、`3.6 s`（起爆）、`20 s`（有效时间）、`22.4 s`（摘要）、`18.6 s`（正文）**全都是秒**。只按单位归组，会把合法的前三个也报成冲突——**报了一堆假冲突，真冲突反而被淹没**。

**陷阱二：「按单位匹配约束」也是错的。**
无人机速度约束的 `unit` 是 `m/s`，而正文里的**导弹速度 300 m/s 同样是 `m/s`**。只按单位匹配，`300 m/s` 会被误报为越界（约束是 70～140）。**必须按指标匹配，不能只按单位。**

两条都要配套"不误报"的反向断言，否则错误实现照样能通过正向验收。

## 3. 为什么提示词要这么写（给你复核用）

| 约定 | 来源 | 为什么写进提示词 |
|---|---|---|
| 把约束数据的三种 `params` 形状贴出来 | **实测** `data/contests/*/constraints.json` | 三种 `check_type` 的形状已在 v0.3.0 冻结。不给出真实形状，实现很可能自造一套键名，于是"照数据驱动"变成"照自己想的驱动" |
| 两个误报陷阱各占一节 | **本次分析** | 这是本版真正的技术难点。**朴素实现能通过正向验收，却报一堆假冲突**——正向验收全绿、质量全废。必须配套反向断言 |
| 明确要求"反向断言" | 本次判断 | 只说"别误报"没有约束力。写成测试用例，才可验证 |
| 禁止字面量清单 | 任务文档 §12 任务 6 的推广 | 任务文档只禁题号分支。但样例数字更容易被写进实现（`if 412 in text`）。一并禁掉，并划清"只允许出现在样例正文与测试期望值里" |
| 样例稿要求"位置分散" | 阶段验收"两处偏移不同" | 若 412 和 386 挨在一起，偏移不同这条自己就满足了，测试失去鉴别力。要求分散，偏移断言才有意义 |
| 明确"不读文件、不连库" | P5 的 `weighted_sum` 先例 | 规则审查最自然的写法是"自己去找 constraints.json"。但 `data/contests/` 不在本版允许范围，一读就有越界风险。纯函数 + 调用方传参，边界干净 |
| 12 篇只要求"能读入" | 任务文档 §12 任务 5 | 档位对比是 v0.8.0 的事。本版若顺手做了，就把评测指标口径提前定死，后面难改 |
| 完成定义含"用例不少于 91" | P4 补丁的经验 | 防止靠删测试变绿 |
| 要求关掉密钥仍通过 | 阶段验收原文 | 这条验收的正确用法是"把密钥清空再跑一遍"。写清楚才能验证 |
