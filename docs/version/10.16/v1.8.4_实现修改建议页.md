### 1.1 本版可用的接口与类型

```ts
getReview(reviewId: string): Promise<ReviewArchive>   // 存档只有 7 字段，不含 change_list
```

类型（`frontend/src/api/types.ts` 已定义，两组字段皆可选，**页面必须先判形状**）：

```ts
ChangeEvidence { char_start?; char_end?; text?; band?; status?; chunk_ids? }

```

### 1.2 三段与两类条目（实测 `change_list.py`）

后端 `build_change_list()` 产出，`SECTION_ORDER` 固定为三段：

| section | 对应的需求措辞 | 本页展示 |
|---|---|---|
| `题目约束与数字冲突` | 先改硬伤 | 审查类条目（数字冲突 / 越界 / 未提到条件 / 缺少情形 / 引用缺失） |
| `证据不足` | 再补证据 | 维度类条目（`band === 证据不足` 的维度） |
| `表述` | 最后改表述 | 维度类条目（`presentation` 维且 band 为 基本/不足） |

两类条目的形状差异（**同页两类都要渲染**）：

- **审查类**：带 `finding_kind`（数字冲突 / 越界 / 未提到条件 / 缺少情形 / 引用缺失），`evidence[]` 是 `{char_start, char_end, text}`；`upstream_id` 形如 `finding:数字冲突:盘入终止时刻`。
- **维度类**：带 `dimension_code`，**没有** `finding_kind`；`evidence[]` 是 `{text, band, status, chunk_ids}`；`upstream_id` 形如 `dimension:presentation`。

页面按 `section` 分三段、段内按后端顺序逐条渲染；**条目顺序就是修改顺序，前端不重排**。

## 3. 为什么提示词要这么写（给你复核用）

| 约定 | 来源 | 为什么写进提示词 |
|---|---|---|
| **三段全部、不重排** | `change_list.py` 的 `SECTION_ORDER` + 需求第 261 行 | 修改顺序是后端定的，前端一旦 sort 就会打乱「先改硬伤、再补证据、最后改表述」。明确"顺序就是修改顺序"能防止 AI 自作主张按 kind 或字母重排 |
| **两类条目都要渲染、先判形状** | `types.ts` 的两组可选字段 + 实测 | 这是 v1.8.0 就记下的坑（change_list 两种形状）。修改建议页是**唯一同时渲染两类**的页面，最容易只写一种 |
| **空段仍渲染标题** | 本次判断 | 三段框架是"修改顺序"的骨架，缺一段会让用户以为页面漏了数据。但也要防止 AI 在空段塞假条目——所以空段显示「本段无建议」而非造数据 |
| **复用 v1.8.3 偏移定位** | 组件复用原则 | 审查类证据的定位逻辑上一版已做，本版不应重写一份。写清"复用"避免两份不一致的定位实现 |
| **upstream_id 可见化** | 需求 §12.3 | "每条建议指回上游"是硬验收。把它显示出来既满足验收，也让用户能追溯 |
| **空态文案禁建议字样** | 阶段验收同源 | 与前面几页一致，文案里的词会污染"无建议"断言 |
| **`views.spec.ts` 名单减为只剩评测对照** | 读源码 | 占位页断言逐版收窄 |
| **禁题号分支** | `source-scan` | 种植策略金额是数据不是分支 |
