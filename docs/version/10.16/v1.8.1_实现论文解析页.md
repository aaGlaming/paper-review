### 1.3 需求缺口：解析页要的三样，后端从未实现

需求文档原文：

> （第 235 行）负责把上传的论文拆开。输出**章节树、关键主张、表格、文内引用和参考文献**。主张要记下所在章节，以及后文可能用到它的位置。
> （第 258 行）**agent1-论文解析.html** — 左侧章节树，右侧**主张、表格和引用**。……板凳龙样例会标出一条错误假设。

执行手册第 50 行同样写着解析节点产出「章节树、主张、表格、文内引用、参考文献」。

**实测**：后端 `POST /api/reviews` 只返回 `sections`（`title` / `section_type` / `level` / `content`）。全仓库搜不到主张（claims）、表格抽取、文内引用的结构化产出——`backend/app/review/consistency.py` 里那个 `check_citations` 是**审查阶段查参考文献是否缺失**用的，不是解析产物，也不进 `POST /api/reviews` 的响应。

**本版的处置（默认做法，理由见 §3）**：

- 页面**只渲染接口真给的东西**：左侧章节树（可改类型），右侧选中章节的**正文原文**（`white-space: pre-wrap` 原样呈现，表格与引用在正文里**看得见**，但不是结构化字段）。
- **不做前端重新解析**：在页面里自己抽主张/表格/引用，等于把解析逻辑抄一份到前端，会与服务端语义分叉——这正是任务文档反复强调"页面不在这里重写档位或加权"的同一类问题。
- 「主张 / 表格 / 引用」三块在右侧栏**预留位置**（后续后端补产出时直接落进去），本版显示一行说明：该部分由后端解析产出，当前接口未提供。
- 「解析页标出一条错误假设」同理：它需要审查结果（findings），而 findings **不进 `POST /api/reviews` 的响应**。本版不做，记挂账。
- 在 `docs/plan/findings.md` 记 Ruling（原文见第六节）。

> **如果你希望本版就把这三样做出来**，那就必须先给后端加一条"解析产物"接口——那属于**改后端**，超出 P8 的允许范围，且执行手册 §3.6 的冻结接口清单里没有这条路径。正确顺序是先改执行手册与任务文档、再单开一版补后端，然后才轮到页面。**默认按上面的处置执行。**

### 1.4 章节类型词表要前端镜像一份

章节确认时用户可以改 `section_type`，所以下拉要列出全部合法值。但后端**没有"取词表"的接口**（§3.6 的 11 条路径里没有），而 P8 不许改后端。

因此前端硬编码一份，内容**必须**与后端 `backend/app/graph/review_graph.py` 一致：

```text
假设 / 模型 / 求解 / 结果 / 检验 / 参考文献      六个类型
未分类                                          判不出类型时的兜底
```

这份镜像**只能有一处定义**，并加用例锁死（多一个、少一个、改成别的字都算失败）。它是一处"双源"，写进 Ruling。

一、页面结构与交互（论文解析页）
这是「校样稿」工作台的第一页。版心 1040px（--pr-measure），**左栏章节树 + 右栏正文**两栏布局。

一.1  输入区（页面上部）
- **赛题下拉**：唯一数据来源是 listContests()。**未选赛题时「开始解析」不可提交**（按钮禁用并给出原因：
  未绑定赛题就没有量规，确认后拿不到任何维度）。不要自作主张给一个默认赛题。
- **三篇演示，一键填入**：数据来源是 listSamples(true)。按钮文案取接口的 `title`，
  **不要把「板凳龙」「种植」「烟幕」写死在源码里**；点击后用 `sample_id` 提交。
- **或粘贴正文**：一个 textarea + 「用这段正文解析」，用 `paper_text` 提交。
- `paper_text` 与 `sample_id` **互斥**（接口规定，两者都给或都不给都是 400）。
  UI 上把两条路做成互斥的两块，提交时只带其中一个；两个都填/都空时按钮禁用并说明。
- 提交中禁用重复提交。

一.2  创建评审（POST /api/reviews）
- 请求体：{ sample_id, contest_id } 或 { paper_text, contest_id }。
- 成功后把 review_id / sections / contestId 写进共享状态，并在页面上进入「待确认」态。
- **响应里没有任何档位字段**，页面在这一步也**不得渲染任何档位、分数或加权**。
- 失败时用 ApiError 的 message 显示错误（它已经带上了后端的 detail）；
  坏包类响应还带 filename / field，能拿到就一并显示。

一.3  章节树（左栏）
- 每条显示：`title`、`section_type`、层级用**缩进**表达（`level` → 缩进档）；
  **不要用 01 / 02 / 03 这类装饰性编号**（这不是序列，是层级）。
- `section_type` 用下拉可改，选项就是自检第 2 条那份镜像词表。
- 改动只改**本地待提交的 sections**；提交时把改后的完整 sections 一起发给 resume。
- 点击某条 → 右栏显示该条的 `content`。

一.4  正文（右栏）
- 用 `white-space: pre-wrap` **原样呈现** `content`，不做 Markdown 解析（本版不引 Markdown 库）。
- 右栏在正文上方预留「主张 / 表格 / 引用」三块的位置，本版显示一行说明：
  该部分由后端解析产出，当前接口未提供（`POST /api/reviews` 只返回章节树与正文）。
  **不要在这三块里放占位假数据。**

一.5  确认与继续（POST /api/reviews/{id}/resume）
- 按钮「确认章节树，进入分项评分」。点击后用**改后的 sections** 调 resumeReview。
- 成功后**不自动跳转**（分项评分页在下一版才实现，跳过去只会看到占位，看起来像坏了）。
  改成在原地显示一张「已确认」结果卡：状态、维度数、量规版本、来源（`source`），
  再加一个指向 /scoring 的文字链接，标注「该页在下一版实现」。

## 3. 为什么提示词要这么写（给你复核用）

| 约定 | 来源 | 为什么写进提示词 |
|---|---|---|
| **把「三处会被打破的断言」单列一节** | 读 `views.spec.ts` / `app-shell.spec.ts` 源码 | 这两处断言是 v1.8.0 为**五个占位页**写的，解析页变成真页面后必然红。不写清，AI 要么卡住，要么把断言整条删掉而不补真实断言——那就是"放宽意图" |
| **`app-shell.spec.ts` 会真挂载解析页** | 同上 | 它 `push('/parse')` 且挂载整个 App，而 jsdom 里没有后端。所以"取数失败必须被捕获"不是风格建议，是**这条既有用例能否继续绿的前提** |
| **`h1` 必须无条件渲染、恰好一个** | `smoke.spec.ts` 的断言 | E2E 对五个页面都断言 `h1` 文案 = 导航名。解析页一旦把 h1 放进"有数据才显示"的分支，smoke 立刻红，而报错会指向"页面标题不对"，不指向根因 |
| **需求缺口单列 §1.3 并给默认处置** | **实测**接口只返回 `sections` + 需求原文第 235/258 行 | 需求明说解析页要展示主张/表格/引用，执行手册第 50 行也这么写，但后端从没产出。不说清，AI 极可能在页面里自己写一套正则去抽主张——**那等于把解析逻辑抄一份到前端**，和服务端语义分叉，且后端补齐时要重写 |
| **明确"不许在前端重解析"** | 任务文档 §14「不在页面里复制一份评分逻辑」的同源要求 | 这条纪律后端那侧已经写死过（页面不重写档位与加权）。解析产物是同一个道理，只是换了个对象 |
| **章节类型词表允许镜像、但必须只一处定义 + 用例锁死** | **实测**没有取词表的接口 | 下拉必须给全合法值，而拿不到词表 → 只能镜像。镜像无法避免，但**可以防止它悄悄漂移**：一处定义 + 用例锁死六个+未分类 |
| **共享状态用 composable + sessionStorage，不装 Pinia** | 本次判断 + v1.8.0 被 TS 挖坑的教训 | 要跨页传的只有四项，Pinia 的收益（devtools、插件、模块化）用不上；而每多一个依赖就多一份版本相容风险，上一版刚吃过一次亏。**这条要写进 Ruling/理由**，否则后续版本可能"顺手"把它换成 Pinia，让两种状态方案并存 |
| **不自动跳转到 /scoring** | 本次判断 | 下一版才实现评分页。自动跳过去只会看到占位页，**演示时看起来像坏了**。原地显示结果卡 + 一个标注清楚的链接，既真实又不误导 |
| **步骤指示器只准诚实** | **任务文档** §14 任务 9 + 需求 §12.4 | 「分步看到」与「同步接口」之间有张力：接口不报中间态。**"看到假进度"比"看到不确定态"更糟**——它会让超时时的页面显示一个从未发生的"已完成到第 N 步"。所以禁止定时器伪造，并写成可扫描的用例 |
| **E2E 必须真跑完整链路（创建 + 确认）** | 任务文档 §14 任务 3 + 阶段验收 | "确认调用 `resume`"是本版的核验点之一。只做组件测试等于没验过 HTTP 那条链——v0.8.1 就有过"测试自己造数据绕开 HTTP"的教训 |
| **E2E 写库污染写成 Ruling 而非"加清理接口"** | 冻结清单里没有删除路径 | 顺手加 DELETE 接口就是越界改契约。**接受污染 + 如实记录行数 + 挂账**，比偷偷加接口干净 |
| **明确"不引 Markdown 库"** | 本次判断 | 正文原样呈现（`pre-wrap`）就够本版验收；引库要重新过一遍版本相容（刚踩过 TS），且会引出"表格该不该结构化成字段"的新问题——那属后端 |
| **`package.json` 一行未变写进完成定义** | 上一版被新依赖坑过 | 把"零新依赖"变成可核对的硬条件，而不是一句口头要求 |
| **progress.md 用「阶段 n/6」** | 与 v1.8.0 一致 | 不发明新的里程碑号：三份文档都以 v0.9.0 = P8，分段只是执行方式 |
| **列 Ruling 时给可照抄的原文** | 项目 `findings.md` 的格式要求 | 「决定 — 原因 — 做错的代价」三段式。不给原文，AI 会写一条不痛不痒的记录 |
