# v3.3.6 · 修正向量库并发崩溃与门禁回补

> **阶段**：Phase-3 / P19（修正版；**前端顺延为 `v3.3.7`**）
> **前置**：`v3.3.5` 代码已完成但门禁未通过——真实 Chroma 出现原生 access violation，全量 pytest 与真机问答被打断，E2E 降到 24/24。
> **本版范围**：判定崩溃归属 → 数据是否丢失的**正确**验证方式 → 运行隔离或重建 → 把 356 passed / 40-8 两项门禁补回来。**不做**前端。

## 一、现象与我已实测到的证据（2026-10-20 20:35）

| 观察 | 实测值 | 含义 |
|---|---|---|
| `pytest --collect-only` | **356** | 测试确实加到了 24 条（回答 12 + 聚合 12） |
| 实际全量 pytest | 中途崩（原生 access violation） | 不是断言失败，是进程被带走 |
| 向量库 `chroma_data/chroma.sqlite3` 的 `embeddings` 行数 | **16347** | **数据没丢** |
| `segments` 分组 | VECTOR **1** + METADATA **1** | 结构完整，没有半截段 |
| `chroma_data/` 下的段目录 | **4 个 UUID**，只有 1 个被 sqlite 引用 | 另 3 个是历史遗留，不被读取 |
| 8077 后端 | **在跑**（PID 18580） | 关键变量 |
| 后端在跑时，另一进程 `get_collection().count()` | **SIGSEGV（exit 139）**，无任何输出 | 可复现 |
| 同一时刻的「副本」探测 | exit 0，但 `count 0` | **副本不可信**，见下 |

**结论已经很接近了：** 数据在、结构完整、单一进程读写正常；**只要后端占用着同一个 `chroma_data` 目录，第二个进程一打开就崩**。而 `pytest` 里确有测试会打开真实 Chroma（`test_review_indexing` 等），全量跑到那里就整进程死掉——所以「356 条全绿」这件事根本无法完成，跟代码对错无关。

**一条必须写下来的教训：副本不能当证据。** 我刚用 `cp -r chroma_data /tmp/cc` 做副本探测，得到 `count 0`，差点据此判断「数据被清空了」。实际是：`chroma.sqlite3` 有 **66 MB**，后端正在写，`cp` 拷到一半就是一份撕裂文件——sqlite 能打开、能查表，但 `embeddings` 查出来是 0。**验证数据量必须直连原始库只读查询（`mode=ro`），或者先停写再备份**；任何「边跑边拷」的副本都不能用来下结论。

## 三、为什么这么写

**为什么第一件事是「停后端再备份」，而不是先改代码。** 崩溃属于「进程被带走」这一类事故，最怕的是在拿到证据之前乱动：改一版、崩一次、再改一版，最后没人知道原始状态是什么。先把 `embeddings` 行数记下来、把目录原样留一份，后面无论走隔离还是重建，都有退路。**事故处理的第一原则是不要扩大损失。**

**为什么专门强调「副本不能当证据」。** 我自己刚踩过：`cp -r` 出一份副本，查出 `count 0`，差一点写成「向量数据被清空」。真实原因是 `chroma.sqlite3` 有 66 MB、后端还在写，拷到一半就是撕裂文件——sqlite 打得开、表也在，但关键的 `embeddings` 是 0。**这种「看起来确凿、其实是被测量方式污染的结论」，比没有结论更危险。**

**为什么首选「测试隔离」而不是「跑测试前记得停后端」。** 后者是纪律，纪律会被忘；而且它把「能不能跑通测试」变成了「有没有记得关服务」。隔离之后，测试永远在临时目录里跑，与生产库零接触——既不会崩，也不会因为某条测试写坏了索引污染真实数据。这是把「靠自觉」换成「靠结构」。

**为什么 `delete(where=...)` 要改成显式 id 列表。** `where` 过滤删除要先扫段、再定位、再标记删除，路径长；而我们的 id 规则是确定的（`rr-{review_id}-{dim}`），完全可以先 `get` 拿 ids 再按 id 删。**能不做全段扫描的地方就不要做**——尤其在「幂等」这种每次回填都会走到的路径上。

**为什么门禁回补要写「后端保持运行」这个前提。** 之前 356 条之所以跑不完，正是因为后端在跑时第二个进程打开同一目录会崩。如果修完之后仍然「先把后端停掉再跑 pytest」，那等于没验证修复——**必须在不改变现场条件的前提下把门禁跑绿**，才能证明隔离真的生效。

**为什么 E2E 要单独查。** 24/24 这个数字很奇怪：既不是 0（说明大部分用例能跑），也不是 40（说明有一批没跑成）。这种情况八成是「一批 spec 全部失败在 setup 阶段」——通常是后端起不来或端口被占。它能暴露「向量库崩了之后后端进程残留」这类连锁问题，所以必须单独看一眼，不能因为 pytest 绿了就当作没事。
