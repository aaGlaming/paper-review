## 一、为什么合并

前两份提示词是分开的：`v3.3.2` 做回答、`v3.3.3` 做聚合。但 `v3.3.2` 没跑，`v3.3.3` 的 P0 又把它当前置，于是两头都停——**这不是执行的问题，是我把一个连续动作切成了两段还写了硬前置**。

合并的理由不只是「省一次往返」：

- 两者的共用件是同一套东西：`search_records`（检索）、`chat_fn`（模型调用，只注入一次）、引用校验（同一份代码）、`ai_chat` 日志（同一次会话）。
- 分开做会写两遍引用校验，而**第二遍一定会和第一遍不一致**——这是这类「同一逻辑两个入口」最常见的漂移。
- 合并后仍有清晰的分批验收点：先绿「回答」，再绿「聚合」，最后绿「摘要」。**一个版本内可以分批，但共用逻辑只能写一份。**

代价要认：本版代码量约 450～550 行，接近单版可完成上限。所以 P5 的测试明确分成两批，任一批红就先修完再动下一批，不许全写完再一起跑。

=== P1 回答服务（backend/app/chat/answering.py 新建） ===

    answer_question(
        session_db, *, session_row, question: str, contest_id: str,
        search_fn=None, chat_fn=None,
    ) -> dict          # {content, refs, model_name, notes}

流程（顺序不许改）：
1. 校验由路由层做：question 去空白后 1~2000 字；contest_id 必填。
2. 检索：`search_fn(question, contest_id=contest_id, limit=8)`
3. **空命中 → 不调模型**，返回固定文案：
       content = "这些记录里没有相关信息。可以换一个说法，或确认赛题范围是否正确。"
       refs = []，notes = {"retrieved": 0, "model_called": False}
4. 非空 → 拼 messages：
       system（四条纪律，逐字使用，不许改措辞）：
           你是竞赛论文预审工作台的记录助手，只能依据下面提供的评审记录片段回答问题。
           1. 不得编造片段里没有的事实；片段不足以回答时，直接说“这些记录里没有相关信息”。
           2. 每条结论后面必须用 [review_id=xxx dim=yyy] 标注它来自哪条记录的哪个维度，格式照抄。
           3. 不输出奖项、名次、获奖概率等推测性评价。
           4. 用中文回答，控制在 300 字以内，先给结论再给依据。
       user：`【可用记录片段】` + 每条 `[i] review_id=… dim=… 档位=…` + 片段正文（每条截断 800 字）
             + `【问题】` + question
   片段**最多 8 条**（search_fn 返回更多也要截断）。
5. 调 `chat_fn(messages)`，异常时**重试 1 次**（只一次）。
6. 两次都失败 → 抛 `AnswerError("问询失败，请重试")`，路由层转 502。
7. 引用**双向校验**（这是 v3.3.2 与 v3.3.3 共用的逻辑，只写一份，供摘要复用）：
       允许集合 = 本次检索片段的 {(review_id, dimension_code)}
       文本里出现但不在集合中的标记 → 从正文剔除，记 notes.rejected
       在集合中但未被引用 → 记 notes.unused（数量）
       两者都写日志，都**不判整次失败**
8. 返回 refs（去重保序）。

- 成功：同一事务里**先落 user 消息、再落 assistant、再 touch_session**
- 502：**什么都不落**（一条没有回答的 user 消息会变成下一轮上下文里的悬空节点，且重试会留两条重复）

1. 先调 P2 三个函数拿到**全部数字**
2. 拼 prompt：system「只能使用下面给出的统计数字与引用；不得新增任何数字；不输出奖项名次；
   中文 300 字内，先结论后依据」+ user 三段统计 +「可用引用」≤8 条 + 任务要求（结尾标至少 3 条证据）
3. 调 `chat_fn`（复用 P1 的重试策略：只重试一次）
4. **引用校验复用 P1 第 7 步的同一个函数**（只保留可用集合内的标记，剔除记 rejected）
5. 有效引用 < 3 → `notes.evidence_short = 实际条数`，并在答案末尾追加固定提示：
       （可用证据不足 3 条，已如实标注 n 条）
   **不许让模型凑数，也不许你替它补引用。**
6. 传了 `session_id` → 校验归属后落库 assistant 消息；没传 → 不落库（导出场景）

## 四、为什么这么写

**为什么合并，而不是让 v3.3.2 先跑再跑 v3.3.3。** 两者共用四样东西：检索入口、`chat_fn` 注入、引用校验、`ai_chat` 日志。分两版做，第二版一定会「照着第一版再写一遍引用校验」，而**两次手写必然不一致**——第一次剔标记、第二次忘了去重，最后同一个问题在不同入口给出不同的 `refs`。合并的成本是多写 200 行，收益是这段逻辑全世界只有一份。

**为什么合并后仍要分批绿。** 24 条测试一次写完再跑，红了之后你会面对一片红，无法判断是回答链路的错还是聚合的错。拆成「第一批 12 条 → 绿 → 第二批 12 条」，任何失败都落在 12 条的范围内，定位成本低一个量级。

**为什么明写「体量闸」。** 这一版比平时大一倍，最大的风险不是写错，是**为了赶完而少写测试**。把「做不完就停在批次边界并报告」写进纪律，比事后追责有用——它给了执行方一个体面的止损点。

**为什么 `INSUFFICIENT_BANDS` 要强调「只定义一次」。** 库里有 76 条「证据不足」和 18 条「不足」。如果 `compare_bands` 用常量、`evidence_gaps` 里又顺手写了 `band == "证据不足"`，两处结果就对不上，而**看数字的人不会知道哪个对**。这类不一致最贵的地方在于它不报错。

**为什么摘要复用同一个引用校验函数。** 摘要的引用和问答的引用是同一个问题：标记是否来自本次可用集合。写两份的后果是——问答剔了、摘要没剔，于是摘要把一个不存在的记录写进了教研会材料。**判据里「引用必须可追溯」是同一件事，实现就该是同一段代码。**
