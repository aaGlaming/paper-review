=== P1 日志底座 ===

新建 backend/app/observability/ 包（如果已有类似目录就复用，不要并列造两套）：

    backend/app/observability/__init__.py
    backend/app/observability/logging.py      核心：配置、JSON 格式化、按天滚动、清理

对外只暴露三个东西：

    log_event(module: str, event: str, level: str = "INFO", **fields) -> None
    setup_logging() -> None                    幂等，启动时调一次
    MODULES: tuple[str, ...]                   十五个模块名

`MODULES` 必须严格是这十五个（顺序照抄 Phase-3 计划 §3.1）：

    api, graph, agent, llm, retrieve, scoring, review, report,
    importing, auth, ai_chat, dashboard, errors, audit, frontend

**目录创建**：`setup_logging()` 里 `mkdir(parents=True, exist_ok=True)` 逐个建。
不能靠 git 保留，因为 `logs/` 将被 gitignore，git 不跟踪空目录。

**路径与开关走环境变量，禁止硬编码**：

| 变量 | 默认 | 作用 |
|---|---|---|
| `LOG_DIR` | `<项目根>/logs` | 日志根目录 |
| `LOG_DISABLED` | 空 | 设为 `1` 时 `log_event` 直接返回，不建文件、不建目录 |
| `LOG_LEVEL` | `INFO` | 低于该级别的丢弃 |
| `LOG_RETAIN_DAYS` | `30` | 启动时清理更早的 `*-YYYYMMDD.log` |

**每行一个 JSON 对象**，必须含四个字段：

    {"ts":"2026-10-20T09:07:31.412+08:00","level":"INFO","module":"scoring",
     "event":"dimension_scored","review_id":"...","dimension_code":"assumption",
     "band":"不足","chat_calls":1,"quote_ok":true,"elapsed_ms":1830}

- `ts` 用带时区的 ISO 8601（`datetime.now().astimezone().isoformat(timespec="milliseconds")`）
- `level` 固定取 `DEBUG/INFO/WARNING/ERROR` 之一
- `module` 必须在 `MODULES` 里，不在就抛 `ValueError`（防止拼错目录名，静默丢日志）
- `event` 用 snake_case 短语
- 其余 `fields` 原样并入；值必须能被 `json.dumps(..., ensure_ascii=False)` 序列化，
  不可序列化的转 `str()`
- **中文直接写，不要 `ensure_ascii=True`**

**文件命名与滚动**：

- `<module>-YYYYMMDD.log`（如 `scoring-20261020.log`）
- 单文件超 **50 MB** 滚动为 `.1` `.2` …，最多 **5** 个
- 跨天自动换文件
- 启动时删除早于 `LOG_RETAIN_DAYS` 天的 `*-YYYYMMDD.log`

实现建议：自己写一个 `logging.Handler` 子类（`emit` 里按日期判断换文件、按大小判断滚动），
复用 `self.acquire()` / `self.release()`，**不要引第三方库**。
`TimedRotatingFileHandler` 只管时间不管大小，`RotatingFileHandler` 只管大小不管日期，
两个都不满足，别硬凑。

**三条硬约束**：

1. **写日志失败绝不能影响业务**。`emit` 内部或 `log_event` 外层必须 try/except，
   异常降级到 `sys.stderr` 一次性提示后静默，不许让请求 500。
2. **`setup_logging()` 必须幂等**。重复调用不重复加 handler（重复加会让每条日志写多遍）。
3. **不得记录**：`LLM_API_KEY` / `EMBEDDING_API_KEY` / `RERANK_API_KEY` / `MYSQL_DSN` 的值；
   论文全文；密码哈希。只记 `review_id` 与切片编号。

## 四、为什么这么写

**为什么 P16 要拆三份。** P16 的完整范围是「15 个日志目录 + 结构化格式 + 切割保留 + 5 个模块埋点 + 3 个监听端点 + 5 条完成判据」。一份提示词塞完，执行方通常在埋点做完就想收工，监听端点草草了事。按 Phase-2 的验证，一份提示词对应 200～350 行代码是可完成的上限。所以拆成：

| 版本 | 内容 | 依赖 |
|---|---|---|
| **`v3.0.0`（本份）** | 日志底座 + 全链路埋点 | Phase-2 收口 |
| `v3.0.1` | `/health` `/readyz` `/metrics` | 本版通过（`/readyz` 要用到本版的 DB 与 Chroma 健康检查封装） |
| `v3.0.2` | 日志门禁脚本化、15 目录核对、P16 完成判据逐条取证 | `v3.0.1` 通过 |

**为什么 P0 要停下来问一句。** Phase-2 是「四条通过 + 判据 5 部分满足」，而纪律写着「未通过不前强」。这个矛盾执行方不该自己裁决——它要么硬闯（违反纪律），要么卡死（白跑一轮）。把决定权显式交给用户，是一行字的事，能省掉一整轮返工。

**为什么测试隔离要单独占一节。** 231 条测试里大部分会走 API 与图节点，加完埋点后**每跑一次测试就在项目里写 15 个目录的日志文件**。一天跑二十次，`logs/` 就成垃圾场。更麻烦的是：如果按天切割 + 30 天保留的逻辑写在 `setup_logging()` 里，测试时可能触发清理，把开发者本地正在看的日志删掉。这不是小概率，是必现。

**为什么「日志不含密钥」的测试要显式开日志。** 与上条相反——如果全局 `LOG_DISABLED=1`，那条测试断言的是「空文件里没有密钥」，永远通过，永远测不到东西。这种「测试写得很认真但什么都没验」的情况最危险。

**为什么 `path` 要记路由模板。** 记真实路径的话，`/api/reviews/{id}` 有多少条评审就产生多少个不同的 path 值。等 `v3.0.1` 接上 `/metrics`，这就是指标基数爆炸的标准姿势，Prometheus 会先被自己的标签撑死。

**为什么 `guard_downgraded` 值得单独记。** Phase-2 判据 5 卡了三轮，全是因为「critique 到底有没有降过档」拿不到真实数据——只能靠跑模型碰运气。日志里把 guard 的降档结果记下来，以后这个问题一条 `jq` 就答了。可观测性最实际的价值就在这里：**把当初靠猜的问题变成能查的问题。**

**为什么自己写 Handler 而不用现成的。** `TimedRotatingFileHandler` 只管日期不管大小，`RotatingFileHandler` 只管大小不管日期，两个都不满足「按天 + 50 MB + 5 个备份」。硬凑要么写两套 handler 互相打架，要么引入 `loguru` 这类新依赖——而本项目的依赖清单一向克制，为一个日志切割引库不值得。

## 五、本版之后

本版通过后写 `v3.0.1`，核心是把 `/readyz` 做成「能指出哪个依赖不通」而不是笼统 503。这个端点看着最简单，实际最容易写成摆设：只返回 `{"status":"ok"}` 的 `/readyz`，和没有一模一样。

`/metrics` 那部分我会明确要求**手写 Prometheus 文本格式**，不引 `prometheus_client`。理由是本版已经建立了零依赖的日志底座，指标只是把计数器用固定文本格式吐出来，几十行的事。

P16 三份全部通过后，P16 才算收口，才允许进 P17（登录与权限）。
