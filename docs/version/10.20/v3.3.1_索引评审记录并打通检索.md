**三个必须先想清的坑：**

1. **`_where()` 无条件加 `rubric_id`。** 论文检索按「赛题 + 量规版本」过滤是合理的；但问询是「这道题的所有记录」，而同一赛题下可能有多个量规版本（`rubric_version` 不同 → `rubric_id` 不同）。如果强行传一个 `rubric_id`，就会漏掉别的版本；传空串又会变成 `rubric_id == ""` 的精确匹配 → **0 结果**。所以要改成「非空才加这个条件」。这是本版唯一动到既有检索函数的改动，`test_parent_child.py` 里断言 where 结构的用例要一起看。
2. **`ParentBlock` 没有 `dimension_code`。** 回答要求引用带 `[review_id=… dim=…]`，而检索回来的父块只带 `review_id`。解法是把维度编进 `parent_id`：`rr-{review_id}-{dimension_code}`（32 + 3 + 13 ≈ 48 字符，远小于 64），检索后解析出来。**不要**为了这个去改 `ParentBlock` —— 那个结构被 8 个模块与一堆测试依赖着。
3. **Chroma 的重复写入。** 回填脚本要能反复跑。`collection.add` 对同一 id 的行为在不同版本间不一致（有的覆盖有的报错），所以 `index_review_record` 必须先按 `review_id + doc_type` 删除旧块，再写入——幂等的判据是「跑两次，`count()` 增量等于第一次的增量」。

## 三、为什么这么写

**为什么把「索引与检索」从「回答」里拆出来。** 这两件事的失败现象完全不同：检索没通，回答会一本正经地说「没有找到」（看起来像 prompt 太保守）；prompt 没写好，检索通着也会答得空泛。混在一版里，你没法判断到底是哪一层的问题。先让「给一句话，能取回对的片段」这一步绿灯，回答层的调优才有意义。

**为什么 `_where` 的 `rubric_id` 必须条件化，而不是给问询硬塞一个值。** 同一赛题下会存在多个量规版本（`rubric_version` 变了 → `rubric_id` 变了）。问询问的是「这道题的所有提交」，硬塞任何一个 `rubric_id` 都会悄悄漏掉另一个版本——**而它不会报错，只会少返回结果**。传空串更糟：它变成 `rubric_id == ""` 的精确匹配，结果恒为 0。改成「非空才加」，既保住了论文检索的原行为（那边永远传真实值），又让问询能跨版本。

**为什么维度要编进 `parent_id`。** 引用格式要求 `[review_id=xxx dim=yyy]`，但检索回来的 `ParentBlock` 只有 `review_id`。加字段是最直观的解法，可 `ParentBlock` 是 `search_children_then_parents` 的返回契约，被 8 个模块和一批测试依赖——为一个新场景改公共结构，会把「引用必须可回溯」那条红线的测试全部拖下水。把维度编进 id（`rr-{review}-{dim}`）只影响新类型，解析用 `rsplit("-", 1)`，代价是两行代码。

**为什么用 `section_type="评审记录"` 而不是真实章节名。** `_require_single_value` 只要求单值，但它背后有个隐含语义：`section_type` 是论文的章节类型（假设/模型/求解/结果/检验/参考文献）。给评审记录硬套一个章节名，会让「按章节收窄检索」的逻辑在将来出现「评审记录也有『假设』章节」的荒谬结果。用一个不属于该词表的值，反而更安全——**故意让它不可能匹配到章节过滤**。

**为什么回填脚本要求「跑两次增量 0」。** 幂等不是洁癖：这个脚本以后会在每次新增记录后跑（P24 容器化时可能变成任务），如果它每次都给同一批记录再加一份块，向量库会以每次 475 条的速度膨胀，检索质量随重复度下降。判据写成「增量 0」，比「看起来没有重复」可验证得多。

**为什么本版不做 `user_id` 过滤。** 计划 §6.2 说「检索时必须带 `contest_id` / `user_id` 过滤」，但教师当前可见范围就是全部记录，`user_id` 过滤没有实际约束力；而给 `ChildChunk` 加 `user_id` 元数据会动到论文索引那条链路。取舍是：**现在只按赛题隔离，把 `user_id` 的需求写进 findings 等「班级隔离」真正要做时再加**。这条必须写下来，否则会被读成「忘了做」。

## 四、本版之后

P19 调整为四份（原计划三份后端 + 一份前端，现把后端拆成三步）：

| 版本 | 内容 |
|---|---|
| `v3.3.2` | 回答链路：system prompt 四条纪律、单轮最多 8 段、引用解析与校验（`[review_id=… dim=…]` 必须来自本次检索片段）、检索空 → 直接回「没有找到」不调模型、模型失败重试一次；`POST /sessions/{id}/messages`；覆盖能力 1 / 2 / 5 |
| `v3.3.3` | 聚合类问法（能力 3 / 4 / 6）：横向对比、冲突汇总、教研摘要，**聚合走 SQL 不过模型**，摘要必须带三条证据引用 |
| `v3.3.4` | 前端 `/chat` + P19 五条判据取证 |
