## 一、这一轮为什么停

执行方的 P0 输出逐条对照：

| 检查 | 结果 | 判定 |
|---|---|---|
| `pytest --collect-only` | **332** | 不符——`v3.3.3` 里写的是「≈344」 |
| 数据库 | `review` 102、`review_dimension` 510；档位 346 / 70 / 18 / 76 | 与实测一致 |
| `change_list` 类型 | `str` → `json.loads` 后 `list`，`raw_len 657` | 正是 `v3.3.3` 预警的坑 |
| 3306 | LISTENING | 通过 |
| `check_logs.py` | `[ok] 15 dirs, 8 writers, 0 issue`，EXIT=0 | 通过 |
| `/api/chat/sessions` | 401 | 通过 |

**根因不是执行方的判断，而是我的提示词序列。** `v3.3.2`（回答链路）还没跑——库里没有 `chat/answering.py`、`chat_routes.py` 仍是 4 条、`progress.md` 止于 `## v3.3.1`。而 `v3.3.3` 的 P0 把「上一版完成后约 344」写成了一条**硬预期**，于是 332 被读成「不符」。执行方停在 P0，完全正确。

**顺带一件事：中文乱码不是数据坏了。** 执行方看到的档位输出里，四个中文档位名显示成了方块或问号，那是 PowerShell 控制台按 GBK 去解 UTF-8 的显示问题——**数值 346 / 70 / 18 / 76 与我实测完全一致**，说明数据本身是好的。看到乱码先怀疑终端编码，不要怀疑库里的数据；否则很容易顺手去「修数据」，那才是真的坏事。下一节给出正确看法。

## 二、四条判据改法

| 旧写法（会误判） | 新写法 | 为什么 |
|---|---|---|
| 「全量测试应 ≈344」 | 「与**上一版 progress 记录的末行数字**相等」；不等就先查前序是否执行 | 绝对数字是某一时刻的快照，跨版本必然过期。写成相对判据，前序没跑会立刻暴露成「基线对不上」，而不是「版本本身坏了」 |
| 「用 python -c 打印档位分布」 | 写 UTF-8 文件再读，或 `python -X utf8 -c ...` / 先 `chcp 65001` | 控制台按 GBK 解中文会变成方块或问号，看起来像数据损坏 |
| 只在 P0 里查数据库与服务 | 先查**前序产物是否存在**（文件、路由条数、progress 章节） | 文件缺失是最硬的证据，比测试数更早暴露问题 |
| 「缺任一项就停」 | 「缺任一项就停，并说明**需要先跑哪一版**」 | 「停」本身不解决问题；带上「该跑哪一版」才能闭环 |

=== P-1 前序版本闸（先跑这个，再跑 P0） ===

     不要在本版顺手补做前序内容。

2. 前序产物在不在（按本版依赖填具体文件）：
       ls backend/app/chat/answering.py                    # v3.3.2 的产物
       grep -c "@router" backend/app/api/chat_routes.py    # 应为 5
   缺任何一个 → 同上，停。

3. 测试基数对不对：
       上一条命令 `pytest --collect-only | tail -1` 的数字，

       控制台里中文显示成方块或问号 → 那是终端按 GBK 解 UTF-8，**不是数据损坏**。

           python -X utf8 -c "..."                        # 3.7+ 强制 UTF-8 模式

           chcp 65001                                     # 先把控制台切到 UTF-8

## 五、为什么这么写

**为什么把「预期数字」改成「与上一版记录相等」。** 提示词里的绝对数字是某一刻的快照，只要中间多一个版本就会过期。更麻烦的是：过一个版本后，「332 不等于 344」这个现象**同时**可能是「前序没跑」「有人删了测试」「新版本没加测试」三种原因——而它们需要的处置完全不同。写成「与上一版 progress 记录的末行相等」，三种情况立刻分得开：不等就去看前序章节在不在。

**为什么把前序检查提到 P0 最前面。** 文件存在性是最硬的证据，比测试数更早、更准：`ls backend/app/chat/answering.py` 一秒钟就能回答「上一版做了没有」，而测试数还要先跑 5 秒收集、再去比对。**先用最便宜的手段排除最可能的原因。**

**为什么专门写一条「乱码不等于数据坏」。** 这次执行方看到的中文档位名变成方块，完全可能是数据真的坏了（这个项目历史上就因为编码事故丢过 661 个汉字）。但这次不是——数值对得上就说明只是显示层。**在「看起来坏了」的现场，先给一个不破坏数据的确认方法（`-X utf8` / 写文件），比事后补救便宜得多。**

**为什么修正版要单独占一个版本号。** 因为它改变的是**后续所有提示词的检查方式**（前序闸 + 相对基线），不只是这一版的一次性补丁。写成 `v3.3.4` 并调整后续编号，是为了让「为什么前端从 3.3.4 变成 3.3.5」有据可查；如果把修正塞回 `v3.3.3` 原文里，下一次有人翻文档只会看到一份「本来就是这样」的提示词，学不到这条教训。
