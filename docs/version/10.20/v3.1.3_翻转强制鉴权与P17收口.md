## 三、为什么这么写

**为什么注入身份而不是改用例。** 翻转后「无 token 也能建评审」这个前提没了，任何调这四个端点的用例都会 401。可选方案只有两类：给 279 条用例各加一个 `headers=`，或者在一处补上身份。前者等于把「登录」这件事散落到每个用例里，而且以后每次改 token 格式就要改几百行；后者只需要一个 fixture。`v3.1.1` 把解析逻辑抽成 `_resolve()` 的时候，就已经为今天这道缝做了准备——**请求时才查模块属性**，所以 monkeypatch 才会生效。

**为什么默认身份给教师，而不是学生。** 既有测试里大量读写评审记录，其中 80 条历史记录 `user_id` 是 NULL；按本版收紧后的规则，无主记录只有 `review:read:all` 能读。如果默认给 student，这些用例会大面积变 404，而它们的断言跟权限无关——那时你就分不清是「鉴权写错了」还是「身份选错了」。给 teacher 才等价于翻转前的匿名效果，**翻转前后唯一的变化就只剩「必须有身份」这一条**，变量的数量才控制得住。

**为什么那条「匿名建评审存 NULL」的测试必须改写，而另两条只加 marker。** 加 marker 的两条测的是「无 header → 401」，翻转后这个行为依然存在（只是没人能真的无 header 调通），marker 让它绕开注入即可。而「匿名建评审成功并落 NULL」这条测的是一个**被本版取消的行为**——如果只是加 marker 让它继续跑，它要么失败，要么逼你把翻转做回去。正确做法是承认规格变了：HTTP 层的断言改成 401（更严），存储层的意图（空串必须落 NULL）用一条直调 store 的测试继续覆盖。**判断「改断言」是不是放宽，只看一条：改完是更严还是更松。**

**为什么连 `optional_user` 整个函数都要删掉。** 翻转最怕的不是漏翻一处，而是留一个「反正还能用」的后门。只要函数还在，下一个人遇到「这个接口 E2E 不方便带 token」就会顺手用它，而它没有任何注释能阻止这件事。删掉之后，想放行就得重新写一个函数、重新解释一遍，成本高到不会顺手做。

**为什么 `agent-steps` 的 `missing_ok=True` 保留。** 这是两件不同的事：`missing_ok` 说的是「记录不存在返回 200 空列表」，属于接口契约；「无主记录放行」说的是权限，属于安全边界。前者是既有测试锁住的，后者是本版要收紧的。把两者混在一处改，会顺手把契约也改掉。

**为什么 P17 收口报告要求逐条贴原始输出。** 六条判据里有一半是「跑过就绿」的东西（建表幂等、门禁退出码），另一半是「看起来绿其实没验」的东西（错误文案不泄露、新记录带 user_id）。后者只有贴出真实的 curl 响应与 SQL 结果才能证明，否则半年后有人问「当时怎么确认的」，答案只剩一句「应该没问题」。

## 四、本版之后

P17 收口后进 **P18 · 教师端记录总览**（`v3.2.x`）。开工前已经能预见三件事：

| 预见 | 说明 |
|---|---|
| 列表强制服务端过滤 | `GET /api/reviews?user_id=` 不许信前端传的 `user_id`；学生传别人的 id 仍只拿到自己的。这条在 `v3.1.1` 的 `_check_review_access` 里已有同构逻辑，照抄语义即可 |
| 80 条无主记录怎么显示 | 教师能看到，学生看不到。列表接口要么把它们标成「首期遗留」，要么按时间截断——P18 开工前先定，不要等页面画完了再改查询 |
| 分页与排序 | `GET /api/users` 那两条已经踩过：排序必须稳定（created_at 倒序 + 主键升序），否则翻页会重复或漏行 |

另外提醒一句：P17 之后 `AUTH_STRICT` 这类开关**不存在**——本版刻意没做环境变量开关，因为「默认关闭的鉴权」迟早会在某个环境里默认关闭。
