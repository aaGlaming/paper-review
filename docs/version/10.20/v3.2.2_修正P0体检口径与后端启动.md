## 二、两处都是判据的错，不是执行环境的错

### 1. `grep -c "path: '"` 数出来的 12 是假的

`router/index.ts` 里 `path: '` 这个字符串出现在两个地方：

```text
34~53 行：routes 数组里的 9 条路由记录          → 9 处
72/81/85 行：守卫里的 return { path: '/login', query: ... }  → 3 处
```

**9 + 3 = 12。** 而真实路由条数是 9，权威判据早就在测试里：

```text
frontend/tests/unit/router.spec.ts:47
expect(routes).toHaveLength(9)
```

所以「路由基线」这件事**不该用文本计数来验**——文本计数会把守卫、注释、内联对象一起数进去。正确做法是拿 `router.spec.ts` 的结果当基线，改路由时同步把那个数字从 9 改成 10。

这条教训值得记住：**凡是「有测试断言过的量」，P0 就用测试去问，不要另写一个近似的手工计数。** 两个数字对不上时，你无法区分「代码变了」和「数法变了」。

### 2. `curl` 返回 000 是「没连上」，不是「接口返回了 000」

`curl -w "%{http_code}"` 在连接失败时输出 `000`，退出码 7（`Couldn't connect to host`）。上一版收尾时把 8077 停了（`v3.1.5` 的进度记录里有「验证结束后再次停止，8077 已释放」），而我这一版的 P0 却默认它还在跑。

修法不是「下次记得起」，而是**把「没起就起」写进 P0**，并加一条明确的自检：起完之后 `/api/auth/me` 必须返回 **401**（不是 000、不是 500）。这三个值对应三种完全不同的故障：

| 返回 | 含义 | 处置 |
|---|---|---|
| **000 / exit 7** | 进程没起 / 端口没监听 | 起后端，等就绪 |
| **500** | 起了但连不上 MySQL 或启动异常 | 查 3306 与 DSN |
| **401** | 正常，鉴权生效 | 继续 |

## 四、为什么这么写

**为什么把「路由基线」从 grep 换成测试。** `routes` 数组里有 9 条记录，但 `path: '` 这个字符串在守卫里还出现 3 次（`return { path: '/login' }`）。用文本计数当基线，等于用一个**近似量**去卡一个**精确量**——数字对不上时你无法判断是代码变了还是数法变了。而 `router.spec.ts` 里那句 `toHaveLength(9)` 本来就是为这件事写的，它跟着代码一起改，天然同步。**凡是有断言的量，就别再造一个手算版本。**

**为什么把 curl 的 `000` 单独解释一遍。** `-w "%{http_code}"` 在连接失败时输出 `000`，看起来像「服务器返回了 000」，实际是 `curl` 自己没连上（退出码 7）。如果 P0 只写「应为 401」，执行方看到 000 只知道「不符」，不知道是「没起」还是「起了但库坏了」。把 000 / 500 / 401 三值三义写进表里，下一次遇到就不用猜。

**为什么让后端在本轮结束时不要停。** 本版有一步真机验证要看 `/api/reviews` 在真实 MySQL 上的返回（`total=81`、`scope`）。停掉再起一次只是多花 30 秒，但如果忘了起，就又回到今天这种「000 卡住 P0」的局面。记 PID 进 progress 是让下一个人接手时知道端口上是谁。

**为什么 `owner` 参数、重定向 `/parse`、教师 E2E 推迟这三件事照抄 `v3.2.1`。** 它们和这次的两处判据错误无关——判据错误只影响「怎么验」，不影响「做什么」。把设计决策重写一遍反而容易走样，所以本版只修 P0，其余引用原文。

**为什么 `router.spec.ts` 的数字 10 必须在 P4 里点名。** 这个数字现在成了 P0 的基线。如果有人改了路由却忘了改它，下一轮 P0 就会「测试 failed」，而真正的根因是「忘了同步断言」，不是「路由坏了」。把它写在改动同一段里，是最不容易漏的位置。
