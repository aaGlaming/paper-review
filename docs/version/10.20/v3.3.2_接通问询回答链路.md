**三处口径先说清：**

1. **`contest_id` 由每次请求带，不写进会话表。** 会话表刚建好且是空的，加一列技术上很便宜——但「一个会话只能问一道题」这个约束是错的：教师完全会在同一个会话里先问 A 题、再问 B 题。所以 `POST .../messages` 的请求体带 `contest_id`（必填，缺失 400），会话表不加列。
2. **先跑回填再验证。** 库里 **102** 条记录，已索引 **95** 条，差 7 条。本版真机验证前先跑一次 `python scripts/index_review_records.py --all`（幂等，增量只会补那 7 条），否则拿新记录提问会得到「没有找到」，看起来像检索坏了。
3. **失败时两条消息都不落库。** 模型两次都失败 → 返回 502，历史里不留「有问无答」的半截记录。理由：一条没有回答的 user 消息会在后续对话里变成「模型上下文里的悬空引用」，且用户重试一次就会留下两条同样的问题。宁可让用户重发。

## 三、为什么这么写

**为什么检索为空时坚决不调模型。** 直觉上「让模型看着空结果说没有找到」更自然，但这是花钱买一个已知答案：模型要读 prompt、要生成、还有概率说「虽然没找到，但根据经验……」——而这恰恰是这套系统最不能出现的行为。固定文案 + `refs=[]` 零成本、零编造。测试里用 mock 计数把这条钉死，是因为它太容易被「顺手统一处理」重构掉。

**为什么引用要做双向校验。** 单向（只剔除模型编出来的引用）能防「假引用」，但防不了「检索到了却不引」——后者才是判断 prompt 效果的唯一客观信号：如果每次检索 8 条、只引 1 条，说明片段组织或问题理解有问题。把 `unused` 记进日志，就有了调 prompt 的量化依据。**只做剔除，等于把一个持续变差的过程做成静默。**

**为什么剔除引用标记而不是整段作废。** 一条 300 字的回答里有 5 个引用、1 个是编的，整段丢掉浪费了 4 条真实依据；只剔标记 + 记审计，用户拿到的仍然是有用答案，而审计日志能告诉你「这个模型开始编了」。判失败的门槛应该留给「模型根本没答出来」，不是「引错一条」。

**为什么失败时不留半截消息。** 一条 user 消息没有配对 assistant，会在下一轮拼上下文时变成「用户说了话、助手没回应」，模型要么忽略它、要么困惑。而用户重试一次就会留下两条一模一样的问题，历史看起来像出了故障。**宁可让用户重发，也不要在历史里留悬空节点。**

**为什么 `contest_id` 不写进会话表。** 一眼看去「一个会话绑一道题」很整齐，但教师真实用法是「围绕本周教研会，先问 A 题再问 B 题」。绑死之后要么开两个会话，要么改表。让每次请求带范围，代价是前端多传一个参数，收益是省掉一次将来的表结构变更。

**为什么重试只允许一次。** 模型超时通常分两类：网络抖动（重试能救）与服务端过载（重试只会加倍压力）。一次重试覆盖前者，连续两次基本可以确定是后者。给 5 次重试不会提高成功率，只会让接口的平均延迟变成 5 倍，还会在被限流时把额度烧光。

## 四、本版之后

| 版本 | 内容 |
|---|---|
| `v3.3.3` | 聚合类问法（能力 3 / 4 / 6）：横向对比「这道题多少学生假设维证据不足」、冲突汇总「数字冲突最多的是哪几处」、教研摘要「整理成一段给教研会的摘要」。**聚合走 SQL，不过模型**；摘要必须带三条具体证据引用 |
| `v3.3.4` | 前端 `/chat`：左侧会话列表、右侧消息流、引用可点回记录详情、可见范围提示「你正在问询全部 N 条提交记录」、空态三例；P19 五条判据取证 |

**给 `v3.3.3` 的两条预警：**

1. 聚合类问法**不能走「检索 + 模型数数」**：模型数不准，而且同一问题两次答案会不同。必须先用 SQL 得到数字（`group by` 计数），再让模型只负责把它讲成一句话。判据里「按人数排」这种需求，排序必须在 SQL 里完成。
2. 摘要导出的「必须带三条具体证据引用」是个硬约束。如果聚合结果里证据不足三条，应当**如实说明只有几条**，而不是凑数——这条也要写进测试，否则模型一定会凑。
