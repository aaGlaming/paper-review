**三处必须先说清：**

1. **档位有「不足」和「证据不足」两种写法。** 库里 `证据不足` 76 条、`不足` 18 条。做「证据充分性」聚合时若只匹配一种，会**静默漏掉 18 条**。聚合层必须把两者都算进去，并把这条数据不一致记进 `findings.md`（真正的清洗是后续独立的活，不在本版顺手改数据）。
2. **聚合绝不走模型。** 计划 §6.3 的能力 3/4/6 全是「数数 + 排序」，而模型数不准、两次答案还会不一样。本版所有数字都来自 SQL 或 Python 聚合，模型只出现在摘要一处，且只负责「把已算好的数字讲成一段话」。

## 三、为什么这么写

**为什么聚合坚决不过模型。** 「这道题有多少学生的假设维是证据不足」这种问题，模型只能靠读检索片段去数——它既数不准，也不会告诉你它数漏了。而 SQL 一条 `group by` 就能给出确定答案。更关键的是可复现：同一个问题问两次，SQL 给同一个数，模型可能给两个数。**能用一次查询解决的，不要用一次推理。**

**为什么档位要写一个 `INSUFFICIENT_BANDS` 常量。** 库里 `证据不足` 76 条、`不足` 18 条，两种写法并存。如果聚合里写死 `band == "证据不足"`，那 18 条会被静默漏掉——结果看起来完全正常，只是数字偏小。把两种写法收进一个常量，是为了让「以后有人想加第三种写法」时只有一个地方要改，也让这个不一致在代码里显式可见。

**为什么只兼容、不改数据。** `UPDATE review_dimension SET band='证据不足' WHERE band='不足'` 一条 SQL 就能统一，但那是在**改动已落档的评审结果**——而这些记录是模型跑出来的历史证据，改了以后再也说不清「当时到底判的是什么」。数据清洗要单独做、要有审计，不能顺手夹在功能版里。

**为什么不做意图识别。** 让模型判断「这句话是横向对比还是冲突汇总」，猜错了用户会得到一个语法通顺、语义错位的结果，而且没有任何日志能告诉你它猜错了。显式端点把这层不确定性去掉：三个按钮三个接口，点错了是用户的操作，点对了结果就一定对。**在数据类功能里，可控比聪明重要。**

**为什么 `change_list` 的读法要单独提醒。** 用 `select change_list from review` 取回来是**字符串**（JSON 列在驱动层被序列化了），`len()` 得到的是字符数（657），不是条目数。这个坑我实测踩过：按字符数统计得到的「101784 条」看着像个合理的大数，实际上把 341 条膨大了三百倍。**如果只写「解析 change_list」，执行的人八成会直接 `len()`。**

**为什么摘要的引用不足要有那句固定提示。** 计划要求「必须带三条具体证据引用」。当聚合结果里只有 1 条可引用时，模型有很强的倾向去凑第 2、3 条（编造或重复）。代码层面把它压住（校验剔除）+ 文字层面如实说明（固定提示），比只在 prompt 里写「不许编造」可靠得多——**prompt 是请求，校验是约束。**

P19 只剩前端一份：

| 版本 | 内容 |
|---|---|
| `v3.3.4` | 前端 `/chat`：左侧会话列表（新建 / 切换 / 删除）、右侧消息流（用户右对齐、助手左对齐、**引用可点回记录详情**）、顶部可见范围提示「你正在问询全部 N 条提交记录」、空态三例、三个聚合入口按钮（横向对比 / 冲突汇总 / 摘要导出）；P19 五条判据取证 |

**给 `v3.3.4` 的三条预警：**

1. 引用可点回详情，要跳到 `/records` 并**自动打开对应记录的抽屉**——抽屉现在只接受行点击，路由参数（如 `/records?review=<id>`）这一层还没有，需要顺手补。
2. 三个聚合按钮的结果形态不同（表格 / 排行 / 一段文字），别硬套一个组件；摘要那块要能把 `notes.evidence_short` 的提示显示出来，否则用户会以为系统在敷衍。
