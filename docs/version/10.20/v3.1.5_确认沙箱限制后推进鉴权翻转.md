## 一、这一轮实际发生了什么

执行方的 P0 三连与四项快检，逐项复述：

**但「停住」不该是终点。** 基线这件事其实已经有答案了：

> **2026-10-20 17:16–17:20，同一台机器、另一个 shell 里已实测过全量**

所以本版不再等「人类贴回基线才能开工」——**基线已有，只是不是在本 shell 里跑的**。这中间有一条必须守住的诚实边界：`progress.md` 里要写明「基线来源：17:19 由另一执行器实测，非本轮本地复跑」，**不能写成自己跑过**。

## 二、两个判断，先把话说死

**判断一：EPERM 是这个执行环境的稳定属性，不是偶发。** a 与 c 同时 EPERM、中间 b 正常，说明拦截点在「创建子进程」这一层，而浏览器二进制、Playwright 版本、node 全部正常。这类限制在当前沙箱里不会因为重试或换参数消失，反复试只是浪费时间。

**判断二：翻转可以做，但收口前必须有一次真浏览器回归，而且这次回归只能外送。** 原因是这次改动会影响**前端**的鉴权路径：

- 翻转后四个评审接口全部要求 `require_user`；
- 后端 pytest 之所以还能过，是因为 conftest 注入了身份、**绕过了 HTTP 鉴权层**；
- 前端是不是每条请求都真的带上了 `Authorization`（`storageState` 有没有过期、`page.request` 上下文有没有漏、`api/index.ts` 的 `request()` 有没有漏注入），**pytest 一条都测不到**，只有真浏览器能证明。

所以流程不是「能跑 E2E 才准翻转」，而是「**翻转先做，E2E 作为收口前的最后一道外送检查**」。

**还有一个必须先拆的雷：** 现在 8077 上还挂着一个进程（PID **28088**），它跑的是**翻转前**的代码。`playwright.config.ts` 里 `reuseExistingServer: true` 会直接复用它——那样 E2E 全绿也证明不了翻转生效，因为后端根本没重启。外送前必须先把 8077 清掉。

## 五、为什么这么写

**为什么这次不再把 E2E 当开工前置。** 上一版把「本地跑出 37/8」设成 P0 门槛，结果是：环境明明不可用，门槛永远不过，整条链路停摆。门槛的意义是「防止在错误的状态上开工」，而不是「必须在某个 shell 里得到某个数字」。既然同一台机器、同一份代码、同一批依赖下已经有 17:19 的实测 37/8，那这条门槛其实已经满足——**只是证据来自另一个执行器**。承认这一点，比死等一个永远拿不到的输出更接近工程判断。

**为什么仍然必须外送一次 E2E。** 前面已经说过：pytest 走的是注入身份，把 HTTP 鉴权层绕过去了；前端到底有没有在每条请求上带 `Authorization`，只有真浏览器能回答。本版恰好动的是鉴权，这层「看不见的缝」正是最危险的地方——`storageState` 的 token 过期、`page.request` 上下文不带头、`request()` 漏注入，三种都在 pytest 的盲区里。

**为什么要求先清 8077 进程。** `reuseExistingServer: true` 的设计初衷是「跑测试时别重复拉起服务」，代价是它会**默默复用你手工起的那个进程**。现在 8077 上恰有一个翻转前的实例，如果不先清掉，外送的 E2E 会在旧后端上全绿——那不是「验证通过」，是「验证了上个版本」。这类假绿比红灯更贵，因为它不会有人去查。

**为什么外送命令要带 `Tee-Object` 落文件。** 让人类在终端里复制 40 行输出，十次有三次会漏掉失败用例名。落一个 `e2e-run.txt`，再 `Select-Object -Last 40`，既能贴回又留了本地存档；以后要复盘「当时到底哪 8 条红」，不用靠记忆。

**为什么进度记录必须写清基线来源。** 「37/8」这个数字会在后续十几个版本里被反复引用。如果记录里写成「本轮实测」，几个月后有人发现那一版其实跑不了浏览器，整条证据链就全废了。**写清来源不是形式主义，它是让这个数字以后还能被信任的唯一办法。**
