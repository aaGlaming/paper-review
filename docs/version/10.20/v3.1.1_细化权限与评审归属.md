**本版最大的坑是「一加强制鉴权，269 条测试全红」。** 既有测试全是 `TestClient(create_app())` 裸调，不带 `Authorization`。计划 §4.5 要求「新记录必填 `user_id`，从 token 取，不许前端传」——但真按「必填 + 强制鉴权」写，`POST /api/reviews` 立刻 401，269 条里涉及评审创建的全部挂掉，而纪律又不许改既有断言。

所以本版**分两步走**，这一步只做「可归属」，不做「强制」：

| 动作 | 本版（v3.1.1） | 翻转到强制 |
|---|---|---|
| `POST /api/reviews`、`resume` | **可选鉴权**：带 token 就落 `user_id`，不带就落 NULL | `v3.1.2` 末尾（前端能带 token 后）配合 conftest 的 autouse 注入一起翻 |
| `GET /api/users`、`GET /api/users/{id}` | **强制鉴权**（新接口，没有历史包袱） | 本版即最终形态 |
| `GET /api/reviews/{id}` | 有 `user_id` 就判归属；NULL 记录按「无主」处理 | 不变，NULL 只是历史数据 |

**`optional_user` 的语义必须精确**，这是本版最容易写错的一处：

- 没有 `Authorization` 头 → 返回 `None`（匿名，允许）
- 有头但解析失败 / 过期 / 用户停用 → **401**，不许静默降级成匿名

理由：前端拿着过期 token 提交评审，如果被当成匿名，记录会落成 NULL 无主，事后查不到是谁提交的——这比直接 401 难查十倍。

## 三、为什么这么写

**为什么本版不敢加强制鉴权。** 269 条测试全是裸调 `TestClient`，一条 `Depends(current_user)` 就能让涉及评审的那些全部 401。规矩是「既有断言不许改」，那就只剩两条路：要么这一版先只做「可归属」（带 token 就记，不带就 NULL），要么把翻转放到前端能带 token 之后、配合 conftest 的 autouse 一次性做。选前者，因为 P17 的价值在于「记录能追溯到人」，强制登录的收益要等前端登录页存在才有意义。

**为什么 `optional_user` 必须区分「没带头」与「带了坏头」。** 前者是合法的匿名调用（E2E、旧脚本、内部工具），后者是**明确的错误**。如果两者都返回 None，前端拿过期 token 提交评审，记录会静默落成无主，事后没人能证明是谁提交的——这种 bug 在生产上表现为「偶尔有几条记录查不到人」，极难复现。区分开来只需要在同一个函数里多判断一次，成本几乎为零。

**为什么详情接口给 404、列表给 403。** 列表接口本身就是「教师专用入口」，学生访问被拒是常识，403 不泄露任何额外信息。但详情接口的 id 是用户可控的：如果学生查 `u_other` 得到 403、查 `u_notexist` 得到 404，他就获得了一个「这个 id 存不存在」的探测器。统一成 404 之后，两种情况在响应上完全一致——测试里用「逐字节相同」来锁这一条，是因为这种差异一旦出现，肉眼几乎看不出来。

**为什么空串要存成 NULL。** 「无主」如果同时存在 `NULL` 与 `''` 两种表示，以后每条「查无主记录」的 SQL 都得写两个条件，而且一定会有人只写一个。加列的时候顺手把 `str(user_id) or None` 写进去，以后就不用记这件事。

**为什么 audit 不进「必需写入者」。** 那八项目录是「每次预审必然产生日志」的模块，少一条说明埋点坏了。`audit` 只在权限被拒绝时写——某天没有人越权，它就该是空的。把它加进必需项，脚本会在一个完全正常的星期天报警，然后下一个人就会把它从必需项里删掉，顺带把别的也删了。**白名单的每一项都要能说清「为什么允许空」，说不清就不该在名单里。**

**为什么要在这一版补一份 8 行的 `report-P16.md`。** P16 实际是「四条满足、判据 5 部分满足」，但这个结论只存在进度记录的段落里，验收目录下没有任何文件。下一个人翻 `docs/plan/acceptance/` 会以为 P16 没验收过。补 8 行不是形式主义——它是「这个阶段结束了、以什么条件结束的」唯一的书面凭据，而完整取证报告本来就是另一件事。
