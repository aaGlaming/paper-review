    const user = ref<AuthUser | null>(null)     // {user_id, username, role, permissions}

    login(username, password): Promise<AuthUser>   // 调 api，存 token，写 user
    logout(): void                                  // 清 token + user，不调后端也可（仍要调一次 /auth/logout，失败忽略）

## 三、为什么这么写

**为什么登录用 storageState 而不是每条用例先登录。** 45 条 E2E 每条都从 `page.goto('/parse')` 开始，加守卫后它们会全部落到登录页。如果按「每条用例 beforeEach 里登录」来修，就要动 45 个文件的公共部分——而这恰恰是纪律不让碰的区域，且每次跑多 45 次登录请求。`storageState` 是 Playwright 自己的机制：登录一次、把 localStorage 序列化、所有 page 带上。**改动只在两个地方（global-setup + config），用例一个不动。** 这也是「约束越硬，方案越标准」的典型例子。

**为什么 token 放 localStorage、还要专门写代价。** 放 sessionStorage 会让「新标签页打开」变回未登录，放内存则刷新即丢——两种都比 localStorage 更难用。localStorage 的代价是任何 XSS 都能读走 token。这个权衡本身没有更好的选项（除非上 HttpOnly Cookie + CSRF token，那要改后端返回方式与 CORS，属于下一阶段量级的改动），所以**把它写进 findings，而不是假装没有风险**。

**为什么教师的三个入口做成 disabled 而不是直接隐藏。** 计划 §4.4 要求教师能看到三个入口，但那三个页面 P18/P19/P20 才有。做成可点链接 = 点出 404；做成隐藏 = 计划里的功能在界面上完全不可见，评审时无法证明「角色菜单生效」。disabled 加一行 `title="P18 上线"` 是唯一同时满足「可见」「不误导」「能测」的形态。

**为什么只允许改两条单测。** 这两条被改的原因是客观的：路由从 7 条变成 9 条、导航多了用户区，原断言必然失败——这不是「测试写错了」，是「规格变了」。但一旦开口子，很容易顺手把「5 项 toEqual」改成「大于 0」，那就变成了掩盖。所以要求是：**原有断言一条不删，只追加**，并且追加的更严（守卫跳转、退出清 token、角色可见性）。其余 15 个 spec 不许动，用来兜住「api 层契约没被改坏」。

**为什么 401 不在 api 层跳转。** 如果 `request()` 遇到 401 就 `window.location = '/login'`，那守卫、恢复会话、登录页自身的错误提示全都会互相打断——登录失败（401）会直接把页面刷走，用户看不到「用户名或密码错误」。职责分开：api 层只负责把状态码与 detail 抛出去，跳不跳由守卫和使用方决定。

**为什么把强制鉴权翻转拆到 v3.1.3。** 翻转要同时做三件事：把 `optional_user` 换成 `require_user`、给 282 条后端测试注入身份、确认 E2E 也带 token。这三件事与前端页面改动放在一版里，任何一处出问题都分不清是「页面写坏了」还是「鉴权拦住了」。拆开之后，本版出问题只可能出在前端，下一版出问题只可能出在鉴权。

**已经能预见的两个难点，先记下来：**
